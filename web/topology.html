ShopEdge// cluster topology

A real-world OxiDB deployment for a mid-size e-commerce platform. Three shards, nine nodes, single ingress — write-heavy checkout served by per-shard masters, read-heavy browsing fanned out across replicas, time-series events pruned by TTL, hot-path counters in OxiMem.

FIG. 02

Data layout

collection shard key routing notes
customers _id CRC32(_id) → 256 chunks → shard natural per-customer partition
orders customer_id CRC32(customer_id) → 256 chunks → shard co-located with customer; order history is single-shard
carts customer_id CRC32(customer_id) → 256 chunks → shard checkout TX pinned to master only
events customer_id CRC32(customer_id) → 256 chunks → shard TTL 30d via _ts · auto retention · scatter-gather for cross-customer reports
products — unsharded → shard A (replicas) catalog is small & hot · cached · serves all browse traffic
categories — unsharded → shard A (replicas) navigation / taxonomy
inventory — unsharded → shard A master only stock counts need strong consistency · writes serialised
_blobs — shard 0 (A) only S3-style object storage · not sharded today · order receipts & product images
unsharded collections route to shard A by convention — change with OXIPOOL_PRIMARY=A in router env
FIG. 03

Key request flows

FLOW · 01
Browse catalog
API→router→shard-A pool→A1 · A2 (RR)
Catalog is unsharded — request hits products on shard A. SELECT classifies as a read, never touches A0.
FLOW · 02
Add to cart
API→router→CRC32(customer_id)→shard-B pool→B0 (write)
Hash of customer_id picks one shard. Single-shard write — no scatter, no fanout.
FLOW · 03
Checkout transaction
API→router→shard-X pool→X0 [pinned]→commit_tx
begin_tx pins the connection to one master for the entire TX so SELECTs see uncommitted writes. Replicas not consulted.
FLOW · 04
Order history
API→router→find{customer_id:42}→CRC32→B2
Query carries the shard key. Read goes to one shard, picks a replica via round-robin. Latency = single hop.
FLOW · 05
Cross-customer scatter-gather
API→router→fanout→A? · B? · C?→merge
Query without customer_id (e.g. find{status:"pending"}) — fanned to all 3 shard pools, results merged at the router. Use sparingly.
FLOW · 06
Real-time dashboard
browser→WebSocket→A0 · B0 · C0→onSnapshot
Dashboards subscribe per-shard to change events. API multiplexes the 3 streams. WAL-shipped writes propagate to replicas in the background.
FLOW · 07
Hot-path counters · OxiMem
API→RESP→X0:6379→ZADD score=epoch_ms
Cart-abandonment timers, rate limits, session counters live in OxiMem on each master. ZRANGEBYSCORE for time windows. Pub/Sub bridges to MQTT for IoT.
