# ADR 0003 — 1.0 stability surface and scope

**Status:** Accepted
**Date:** 2026-05-18
**Related:** [ADR-0001](0001-julia-no-dbinterface.md), [ADR-0002](0002-mongodb-bench-in-network.md);
README "WARNING — not production-ready" block.

## Context

OxiDB ships at `0.x`. The top of the README is explicit:

> ⚠️ **WARNING — not production-ready.** OxiDB is under active development. The on-disk data format, the wire/server protocol, the client SDK surface, and the JSON document query language are all subject to **breaking changes between releases** with no migration path or backward-compatibility guarantee. … treat any production-like use as experimental until a `1.0` release explicitly commits to stability.

This block by itself is enough to disqualify OxiDB from every adoption conversation that requires multi-year stability — CERN-grade institutional databases ([the analysis in this thread][cern-thread]), enterprise procurement, regulated industries, and most "could we build on this?" evaluations. The fix is a real 1.0 commitment, but a 1.0 that tries to stabilise *everything* the project currently does would take the better part of a year and produce a brittle promise covering too many evolving subsystems.

This ADR scopes 1.0 deliberately narrowly so it can ship in 3-4 months instead of 9-12, by drawing a sharp line between a small **core surface** that gets backward-compat guarantees and a clearly-labelled **experimental surface** that is allowed to evolve under feature gates.

[cern-thread]: https://github.com/parisxmas/OxiDB/issues  (the in-chat analysis; capture as an issue later if needed)

## Decision

### 1.0 covers (stable surface — backward-compatible across the 1.x series)

**Engine — document core:**
- Document CRUD: `insert`, `insert_many`, `find`, `find_one`, `update`, `update_one`, `delete`, `delete_one`, `count`
- JSON query operators: `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$exists`, `$regex`, `$elemMatch`, `$all`, `$size`, `$not`, `$type`, `$mod`, `$and`, `$or`, `$nor`, `$expr`
- Update operators: `$set`, `$unset`, `$inc`, `$mul`, `$min`, `$max`, `$rename`, `$currentDate`, `$push`, `$pull`, `$addToSet`, `$pop`
- Aggregation pipeline stages currently shipping in master (`$match`, `$group`, `$sort`, `$skip`, `$limit`, `$project`, `$count`, `$unwind`, `$addFields`, `$lookup`, `$out`, `$dateHistogram`) and accumulators (`$sum`, `$avg`, `$min`, `$max`, `$count`, `$first`, `$last`, `$push`, `$addToSet`, `$percentile`)
- Single-field, unique, and composite indexes
- Transactions (OCC with the 3-phase commit currently in `src/transaction.rs`)
- Document full-text search (`text_search` with TF-IDF, default settings)
- Blob storage core API (`create_bucket`, `list_buckets`, `delete_bucket`, `put_object`, `get_object`, `head_object`, `delete_object`, `list_objects`)
- Encryption at rest (AES-GCM via `OXIDB_ENCRYPTION_KEY`)

**Wire / protocol:**
- TCP OxiWire — with a 1.0 handshake that negotiates version + feature set
- TLS (`OXIDB_TLS_CERT` / `OXIDB_TLS_KEY`)
- SCRAM-SHA-256 authentication (RFC 7677 stored-verifier model, PR #15)
- RBAC: Admin / ReadWrite / Read roles

**On-disk format:**
- `.btree`, `.wal` (v1 + v2 records), `.fidx`, `.cidx`, transaction commit log, blob layout (`_blobs/<bucket>/<id>.data` + `.meta`)
- Each file type carries a version header; engine refuses to open a newer format and reads all currently-deployed formats

**Configuration (env vars):**
- `OXIDB_ADDR`, `OXIDB_DATA`, `OXIDB_POOL_SIZE`, `OXIDB_IDLE_TIMEOUT`, `OXIDB_ENCRYPTION_KEY`, `OXIDB_TLS_CERT`, `OXIDB_TLS_KEY`, `OXIDB_AUTH`, `OXIDB_AUDIT`
- Lazy-sync knobs: `OXIDB_LAZY_SYNC`, `OXIDB_SYNC_INTERVAL_MS`

**Official client SDKs (each freezes its own 1.0 public surface):**
- Python TCP (`oxidb`), Python embedded (`oxidb-embedded`)
- Go (`oxidb-go` / OxiWire)
- Julia (`OxiDb`, `OxiDbEmbedded`) — already document-only and Tables.jl-aligned (ADRs 0001, see PRs #24-#29)
- .NET (`OxiDb.Client.Tcp`, `OxiDb.Client.Embedded`, `OxiDb.Linq`)
- JS/TS (`oxidb` npm)
- Java (`com.oxidb:oxidb-client`)
- PHP (`OxiDb`, `OxiDbFFI`)
- Swift FFI bindings (`oxidb-client-ffi`)

### Explicitly NOT covered by 1.0 (experimental — may evolve under flags)

These ship behind feature flags, env vars, or "Experimental" namespaces. They are *not* removed; they are just not bound by the 1.0 backward-compatibility promise. They may stabilise into 1.x minors.

**Engine — opt-in subsystems:**
- **PITR** (`OXIDB_PITR`) — recently landed, format and CLI may evolve
- **Raft cluster mode** (`OXIDB_NODE_ID`, behind `--features cluster`) — needs Jepsen-style hardening before commitment
- **FDW / linked collections** (PRs #13–#20) — very new; adapters, auth passthrough, write proxy surface all in motion
- **OxiScript stored procedures** — DSL likely to evolve
- **Vector search** (`vidx`) — APIs and on-disk format may change
- **Security rules** + **JWT auth** — Firebase-like layer, opt-in via `OXIDB_JWT_SECRET`
- **TTL indexes** — semantics largely stable but eviction cadence + edge cases need pinning before promotion

**Alternate / additional wire protocols:**
- REST HTTP API (`OXIDB_HTTP_PORT`)
- WebSocket (`OXIDB_WS_PORT`)
- OxiMem RESP (`OXIDB_OXIMEM_PORT`)
- MQTT v3.1.1 (`OXIDB_MQTT_PORT`)
- S3 API (`OXIDB_S3_PORT`)
- GELF ingest (`OXIDB_GELF_PORT`, `OXIDB_UDP_PORT`)

These work and ship, but a 1.x minor can break a request/response shape under any of them. They are individually candidates for stabilisation in 1.x.

**Query/auxiliary features:**
- Aggregation stages not in the stable list above (any new stages are experimental until promoted)
- Change streams / `watch` (transport semantics may change)
- Procedure scheduler

### Phase plan

| # | Phase | Output | Estimate |
|---|---|---|---|
| 0 | **Scope** | This ADR merged | 1-2 weeks |
| 1 | **On-disk format freeze** | Versioned headers per file type + `docs/format/*.md` specs + "refuse-newer / read-older" tests | 3-4 weeks |
| 2 | **Wire handshake** | OxiWire `hello` handshake; `/v1/` URL prefix for REST; subprotocol versioning for WS; compat matrix doc | 2-3 weeks |
| 3 | **Client SDK freeze** | Per-client public-API audit, `experimental`-marking, `api/v1.json` snapshot + CI diff test | ~2-3 weeks (parallel across the 9 clients) |
| 4 | **Migration tool** | `oxidb migrate` CLI; auto-detect format version; in-place or copy-out; backup-before-mutate; CI upgrade tests | 2-3 weeks |
| 5 | **Policy docs** | `docs/SEMVER.md`, `docs/STABILITY.md`, `docs/DEPRECATION.md`, `docs/SECURITY.md`, LTS branch convention | 1 week |
| 6 | **1.0-rc cycle** | `1.0.0-rc1` → 4 wk soak → `rc2` if needed → `1.0.0` GA | 1-3 months |

Aggregate: **~3-4 months optimistic** (this scope, parallel Phase 3) up to **~6-9 months conservative** (more surface area pulled into 1.0).

### CI built up across Phases 1-3 (running by RC time)

- **Format compat tests** — old `.btree` / `.wal` fixtures committed into the repo; every commit verifies the engine still opens them.
- **Wire compat matrix** — docker-compose-driven: `{client v0.28, v1.0} × {server v0.28, v1.0}` to verify both new-server-old-client and old-server-new-client cases.
- **API surface tests** — `diff` against `api/v1.json` per client; PR fails unless an intentional-bump label is set.
- **Migration round-trip** — generate data on the previous minor, migrate, assert byte-identical (or semantically equivalent) on the new minor.
- **Perf regression CI** — `julia/benchmarks/sqlite_vs_oxidb.jl` and `tests/comparison-mongodb/` produce numbers each release; sudden regression fails.

## Rationale

**Why aggressive experimental-gating instead of full stabilisation?**

Stabilising every surface OxiDB currently exposes — PITR, Raft, FDW, OxiScript, vector search, REST/WS/MQTT/S3 — would take 9-12 months and produce a 1.0 that promises forward-compat over multiple subsystems still actively being shaped (FDW landed *this month*, PRs #13–#20). That promise would either:

1. Be honored at the cost of slowing those subsystems' evolution before they are mature, or
2. Be broken — and a broken 1.0 commitment is worse than no 1.0.

The opposite trap is **never shipping 1.0** because there is always one more subsystem nearly ready. The cost is concrete: every "could we build on OxiDB?" conversation today ends at the README's warning block.

The narrow-1.0 / experimental-gate model is how PostgreSQL, Kubernetes, and most successful infrastructure projects ship: a small, sharp, slow-moving core; feature flags for the frontier; documented graduation criteria from one to the other.

**Why now (i.e., why not wait):**

The core surface listed above has been stable in shape for many minor releases. The "instability" today is mostly in the new subsystems — exactly the ones this ADR scopes *out*. There is no engineering reason the core can't ship 1.0 today; what's missing is the policy + tooling (handshake, migration, compat tests, deprecation docs).

## Consequences

**Positive:**

- A real "1.0 commitment" answer for evaluation conversations — and a written, linkable scope so the answer isn't hand-wavy.
- The README's warning block can become much narrower: "1.0 core is stable; these subsystems are experimental and behind flags."
- The experimental subsystems get genuine room to evolve without breaking 1.0 users — Raft, FDW, etc. can iterate freely.
- The migration tool + format versioning unlocks the entire `oxidb migrate` story, which is a hard prerequisite for any operational team.
- The CI machinery (compat tests, API snapshots) keeps the promise honest going forward.

**Negative / accepted trade-offs:**

- Some prominent features (Raft, PITR, FDW, REST API) are not under 1.0 protection — adopters using them know they may move. This is honest but reduces the apparent feature set covered by the headline.
- Phase 3 (per-client API freeze) is real work × 9 clients. Without volunteer / maintainer help per client, this is the longest pole.
- The deprecation window (2+ minor releases) constrains future cleanups — once a surface is in 1.0, removing it takes a year+.

## Open questions (decide before Phase 0 closes)

These don't block this ADR's merge, but Phase 0 must answer them in writing:

1. **Promotion criteria.** What does an experimental subsystem need to demonstrate before it moves into 1.x stable? (Suggested floor: 6 months on master with no breaking changes, documented format spec, test coverage threshold, one production user.)
2. **LTS length.** 1.0 series LTS for **how long** — 12 months? 18? 24? CERN-grade conversations want 24+. Tie to release cadence.
3. **Major-version cadence.** 2.0 in 12 months? 24? Never until needed? PostgreSQL ships major yearly; SQLite hasn't bumped major in over a decade.
4. **Maintainer surface for the 9 clients.** Are all 9 clients in scope for 1.0, or do some ship as 1.0-rc / 1.0-experimental? The Swift FFI and PHP-FFI lines, in particular, are thinner than the others.
5. **What counts as a "breaking change" for the JSON query/update DSL.** Adding an operator is obviously additive; changing operator precedence or implicit type-coercion semantics is breaking. Needs a written line.

## Revisiting

Revisit this ADR if:
- A 1.x experimental subsystem reaches the promotion criteria — write a separate ADR moving it into the stable surface (e.g., "ADR-00NN: promote Raft to stable in 1.4").
- A 1.0 stable surface needs a breaking change — that's the 2.0 trigger, and gets its own ADR.
- The phase plan slips materially — record the actual scope cuts in an amendment.
