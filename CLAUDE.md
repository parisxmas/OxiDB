# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OxiDB is a fast, embeddable document database engine written in Rust. It supports both SQL and JSON-based queries. It can run as an embedded library, a standalone TCP server, or be accessed via client libraries (Python, Go, Julia, .NET, Swift/iOS via C FFI).

## Build Commands

```bash
cargo build --release                    # Build core library
cargo build --release -p oxidb-server    # Build TCP server
cargo build --release -p oxidb-client-ffi # Build C FFI shared library (.dylib/.so/.dll)
cargo build --workspace --features ocr   # Build with OCR support
```

## Testing

```bash
cargo test                               # All tests (workspace)
cargo test -p oxidb                      # Core library tests only
cargo test -p oxidb-server               # Server tests only
cargo test <test_name>                   # Single test by name
cargo test -- --nocapture                # With stdout output
```

Unit tests are inline (`#[cfg(test)]` modules in source files). Integration tests for the server are in `oxidb-server/tests/` (ACID and security tests).

## Workspace Structure

Cargo workspace with three crates:
- **Root (`oxidb`)** — core database library
- **`oxidb-server/`** — TCP server with SCRAM-SHA-256 auth, RBAC, TLS, audit logging
- **`oxidb-client-ffi/`** — C-compatible FFI (`cdylib`) for language bindings

Client libraries: `python/`, `go/`, `julia/`, `dotnet/`, `swift/`, `oxibase-dart/` (Dart/Flutter, see below)

## Architecture

### Core Engine (`src/engine.rs`)
`OxiDb` owns a `RwLock<HashMap<name, Arc<RwLock<Collection>>>>`. Per-collection locking enables concurrent reads. Collections are auto-created on first insert.

### Multiple Databases (`src/database_manager.rs`, ADR-0012)
`DatabaseManager` hosts many isolated `OxiDb` instances, one per subdirectory of `OXIDB_DATA`: default database `oxidb` (alias `postgres`), server-global `_auth`/`_audit` at the top level, flat legacy layouts auto-migrated into `oxidb/` on open (never overwriting). Wire: optional `db` field per request, `use_db` sets the session default, plus `create_database`/`drop_database`/`list_databases` — and the SQL-text equivalents `CREATE/DROP DATABASE`, `SHOW DATABASES`, `USE` (both surfaces parse into one `DbIntent` in `oxidb-server/src/db_admin.rs`; create/drop are Admin-only). RBAC supports per-database roles (`db_roles`, `grant_db_role`/`revoke_db_role`). The SQL engine is per-database too: default db at `OXIDB_SQL_DATA` (`${OXIDB_DATA}/sql`), others at `${OXIDB_DATA}/<name>/sql` (`sql_bridge` registry). Cluster mode replicates database DDL and scopes writes via `OxiDbRequest::Scoped`; TTL/alert threads run per database; REST takes `?db=<name>`, WS a per-message `"db"` field; transactions are bound to the database they began on. OxiMem keyspace and S3 buckets are intentionally global.

### Collection (`src/collection.rs`)
Each collection owns:
- **Storage** (`storage.rs`) — append-only file with `[status:u8][length:u32 LE][payload]` records; soft-delete flips status byte in-place
- **WAL** (`wal.rs`) — write-ahead log with CRC32 checksums; entries tagged with transaction IDs; 3-fsync protocol (WAL → data → checkpoint)
- **In-memory document cache** — `HashMap<DocumentId, Arc<Value>>` (JSON deserialized once, then refcounted)
- **Field indexes** — `BTreeMap<IndexValue, BTreeSet<DocumentId>>` per indexed field
- **Composite indexes** — multi-field B-tree for prefix scans
- **Version map** — per-document version counters for OCC

### Query Engine (`src/query.rs`, `src/pipeline.rs`)
Query AST with field conditions and logical operators ($and, $or, $nor). Operators: $eq, $ne, $gt/$gte/$lt/$lte, $in, $nin, $exists, $regex, $elemMatch, $not, $all, $size, $type, $mod. Top-level $expr for cross-field comparisons. Key optimizations:
- Index-backed sort: BTreeMap iteration is O(limit) instead of O(n log n)
- Index-only count: returns set size without touching documents
- Early termination: `update_one`/`delete_one` stop after first match

Aggregation pipeline: $match, $group, $sort, $skip, $limit, $project, $count, $unwind, $addFields, $lookup, $facet, $setWindowFields (window functions — document `{documents: [lo,hi]}` AND value/time `{range: [lo,hi], unit?}` frames), $dateHistogram (time-bucketed group + empty-bucket fill), $ohlcv (tick→candle OHLCV with symbol partitioning and LOCF gap fill), $densify (gap-generating docs on a numeric/date axis; fixed units only), $fill (locf / linear / constant null-filling per partition).

### Updates (`src/update.rs`)
Field operators ($set, $unset, $inc, $mul, $min, $max, $rename, $currentDate) and array operators ($push, $pull, $addToSet, $pop). Supports dot-notation for nested fields.

### Indexes (`src/index.rs`, `src/value.rs`)
`IndexValue` enforces cross-type ordering: Null < Bool < Num < DateTime < String. Dates are auto-detected from ISO 8601/RFC 3339/YYYY-MM-DD strings and stored as epoch ms.

### Transactions (`src/transaction.rs`, `src/tx_log.rs`)
OCC with 3-phase commit: prepare → validate versions → commit. Writes are buffered until commit. Deadlock-free via sorted collection locking (BTreeSet). Recovery uses transaction log + WAL replay on startup.

Isolation: backward-validating OCC over item read-sets — committed transactions are serializable w.r.t. the items they read/wrote; phantoms and torn reads for non-tx observers are admitted for plain `find`/`count`. The exact guarantee, anomaly scorecard, and application rules live in `docs/isolation.md`, pinned by `tests/isolation_characterization.rs`.

### Read snapshots — MVCC-lite (`src/snapshot.rs`, ADR-0017)
Read-path-only snapshot visibility; the write path (OCC, `find_for_update`, group commit) is untouched. `aggregate` is snapshot-consistent by default: optimistic latest-state run, proven valid when no write raced it (`SnapGate::changed_since`), else an always-correct resolve-and-recheck fallback — a concurrent aggregation can never see half a transfer. Explicit API `begin_snapshot`/`snapshot_find`/`snapshot_count`/`snapshot_aggregate`/`end_snapshot` (wire: `snapshot_begin`…`snapshot_end`, Read-role tier; the snapshot id is a token, not session state). Mechanics: a snapshot begins under `commit_lock.write()`; every writer records displaced prior bytes into the gate under its `commit_lock.read()` scope (storage layer, `btree_storage.rs`) — that RwLock is the visibility boundary. No snapshot open (the default) costs one relaxed atomic load per write; the version map exists only while a snapshot is open and prunes to the oldest live one. `OXIDB_SNAPSHOT_MAX_SECS` (default 300) hard-expires snapshots — dead-snapshot reads fail with `SnapshotExpired`, writers never wait. Pinned by `tests/snapshot_reads.rs` (torn-sum test proven red pre-feature).

### Full-Text Search (`src/fts.rs`)
Background worker thread receives indexing jobs via `sync_channel(256)`. Supports HTML, XML, JSON, PDF, DOCX, XLSX, images (OCR with `ocr` feature). TF-IDF ranking. Persisted as `_fts/index.json`.

### Blob Storage (`src/blob.rs`)
S3-style bucket interface. Objects stored as `_blobs/<bucket>/<id>.data` + `<id>.meta`. ETags are the first 16 bytes of the payload's SHA-256, hex-encoded (not S3's MD5). A full S3-compatible HTTP API (`OXIDB_S3_PORT`) covers Put/Get/Head/Delete/Copy, ListObjectsV2 (prefix/delimiter/continuation), multipart upload, Range + If-[None-]Match, object tagging, `Expiration/Days` lifecycle, SSE-S3/SSE-C, and SigV4 auth (headers + presigned URLs) — so `aws-cli`, `boto3` and the MinIO SDKs work unmodified. No versioning/ACL/S3-Select; path-style addressing only.

### Encryption (`src/crypto.rs`)
Transparent AES-GCM encryption at the storage layer. Optional—enabled by passing an encryption key to the engine.

### Point-In-Time Recovery (`src/pitr.rs`, `src/archive.rs`)
Opt-in via `OXIDB_PITR`. `ArchiveSequencer` (`pitr.rs`) hands every durable WAL write a global, monotonic, wall-clock-stamped GSN (persisted in leases via `_gsn`); WAL records carry it in the **v2** record format (`wal.rs`). The WAL rotates: `Wal::seal()` atomically renames the live `.wal` to a numbered sealed segment under the WAL lock. A background archiver (`archive.rs`, spawned by the engine) copies sealed segments into `_archive/segments/*.seg` (verbatim bytes + trailer) with a self-healing `manifest.json`. `backup()` embeds a `base.meta` GSN watermark. `OxiDb::restore_to_point` extracts a base backup then `archive::replay_into` advances it to a `Gsn`/`Timestamp`/`Latest` target with transactionally-consistent cuts. Off = zero cost.

### Server Protocol (`oxidb-server/`)
Length-prefixed JSON over TCP (max 16 MiB). Auth via SCRAM-SHA-256. RBAC roles: Admin, ReadWrite, Read. Configurable via env vars:
- `OXIDB_ADDR` (default `127.0.0.1:4444`)
- `OXIDB_DATA` (default `./oxidb_data`)
- `OXIDB_DISK_FIRST` (default ON since 0.38-line: document bodies live in an mmap'd `.bdat` with only a ~24 B/doc offset index resident; `0` restores the always-resident `.btree` mode. Existing collections keep their created format — `.bopts`/on-disk format is authoritative over the env). Since 0.38.10 the `.bdat` is **uncompressed by default** (per-record zstd cost scans/aggregations 4-8x); `OXIDB_DISK_COMPRESSED=1` opts back into zstd. Composite indexes are disk-backed too (`.mcidx`, 0.38.9), and full-collection `$group` aggregations covered by a composite index are answered without reading documents (0.38.3-7).
- `OXIDB_DOC` (default **ON** — the only engine switch that is; `0`/`false`/`no`/`off` runs the server **without the document engine**: no document data dir, no TTL/alert/scheduler threads, document commands refused by name (`ping` still answers). Idle server 9.8 MB RSS / 8 threads vs 14.2 MB / 23. Refuses to start with neither `OXIDB_SQL=1` nor `OXIDB_TSDB=1` (nothing to serve), with any document-backed listener configured (REST/WS/S3/MQTT/AMQP/GELF/MsgPack/OxiMem — named individually with the reason), or in cluster mode. `OXIDB_ADDR` and `OXIDB_PG_PORT` both work without it. `doc_engine.rs`, `tests/doc_disabled.rs`)
- `OXIDB_POOL_SIZE` (default 4 worker threads)
- `OXIDB_IDLE_TIMEOUT` (default 30s, 0 = never)
- `OXIDB_AUDIT` (default off; set to `true`/`1` to enable audit log)
- `OXIDB_AUDIT_MAX_BYTES` (optional; rotates audit log when live file reaches this many bytes)
- `OXIDB_AUDIT_MAX_AGE_SECS` (optional; rotates after this many elapsed seconds since file became active)
- `OXIDB_AUDIT_CALENDAR` (optional; `hourly` / `daily` / `none` — UTC calendar boundary)
- `OXIDB_AUDIT_COMPRESS` (optional; `true`/`1`/`yes`/`on` to gzip rotated audit files; default off)
- `OXIDB_SLOW_QUERY_MS` (optional; record wire commands slower than this many ms into `_profile` with a TTL index; default off)
- `OXIDB_PROFILE_TTL_SECS` (optional; retention of `_profile` records, default 86400)

Diagnostics: `{"cmd": "explain", "inner": {...find/count/aggregate...}}` returns the query plan (strategy, index used, examined/returned, post-filter operators) plus real run timing. Prometheus exposition at `GET /metrics` on the REST listener.

**Dart/Flutter client (`oxibase-dart/`, package `oxibase` 0.1.0).** Mobile apps talk to a project the way the browser does: `OxibaseClient(url, key, ref, authUrl)` → `.from(table)` (PostgREST grammar → documents or a SQL table, server-dispatched), `.series(measurement)` (tsdb profile), `.sql(text, params)`, `.textSearch`/`.createTextIndex`, `.storage.from(bucket)` incl. `.search()` over file contents, `.subscribe()` realtime (one shared socket; the auth frame carries `db`; reset on identity change but **not** on rotation, or every hourly refresh would drop every subscription), and `.auth` (password, magic link, OAuth URL for a deep link, Google ID token, `sessionFromRedirect` for the fragment). Two deps, both already in a Flutter tree: `http`, `web_socket_channel`. **The JS client's auth bugs are designed out**: refresh is single-flight, a request whose token rotated mid-flight retries instead of re-refreshing (`_tokenGeneration`), and every rotation is emitted on `onAuthStateChange` so a stored session stays current — `setSession` deliberately does not emit, or a persist-listener loops. `OxibaseException` keeps the server's distinctions: `isRateLimited` (429 + `retryAfter`) separate from `isDenied` (401/403), `isConflict` (409) for a unique-index duplicate. 17 tests: URL building (incl. `eq."42"` quoting, and `is.null` *not* quoted — a real bug the test caught), single-flight refresh, rotation reporting, the spent-token regression, and an opt-in live suite (`OXIBASE_URL`/`OXIBASE_KEY`) covering documents, ranked search and storage search. MIT, like the other clients; `dart analyze` and `pub publish --dry-run` clean, **not published to pub.dev**.

**Full-text search over REST (0.39.27).** The engine's BM25 index (`src/fts.rs`, k1=1.2/b=0.75, Lucene defaults) was wire-only, so no OxiBase project could use it: `POST /api/{col}/text_search` (`{query, limit≤500, highlight}` → documents with `_score`, and `_highlights` `<mark>` snippets when asked) and `POST /api/{col}/text_index` (`{fields}`) close that. **Gating differs from `aggregate` on purpose**: a text search returns whole documents, so a row-level read rule *can* be honoured — matches are filtered like `find` does rather than the request being refused (a filtered search may return fewer than `limit`; the alternative leaks how many matches the caller may not see). `read:false` is refused outright. Searching is a read (`rest_permitted` allows it for Read/Authenticated alongside `aggregate`); **building the index is not**, so it needs ReadWrite/service_role — otherwise a published browser key could index anything. Unindexed collection = explicit error, not an empty result, so a client can fall back. `oxibase-js` 0.3.0: `.textSearch(col, q, {limit, highlight})` / `.createTextIndex(col, fields)`. **Disk-first text indexes did not survive a restart (0.39.28)** — found the moment the surface was used for real: `btree_collection::create_text_index` never called `save_index_metadata` (its `collection.rs` sibling always did, and `list_indexes` already reported the index), and the open path had no `"text"` arm, so every deploy silently dropped every project's index and searches answered "no text index". Only the *definition* is persisted; postings are rebuilt by one document scan at open, paid only by collections that asked for full-text search. Pinned by `tests/fts-rest.e2e.mjs` (19 assertions: ranking, highlights, both refusals, row-level filtering, service-key bypass, and surviving a restart via `OXIDB_RESTART_CMD`). **Blob/bucket FTS over REST too (0.39.29):** `POST /api/storage/_search` (`{bucket, query, limit≤200, highlight}` → `{bucket, key, score}` + `highlights`) searches the text extracted from uploaded files (HTML/XML/JSON/PDF/DOCX/XLSX, OCR'd images with the feature) — indexed automatically on every `put_object`, so nothing is built first. **The bucket is required**: a bucket's read rule is per bucket, so a cross-bucket search could report keys out of a `read:false` bucket; per-bucket makes the check exactly `read_allowed`, the one a download already passes. Matched ahead of the storage delegate because `POST /api/storage/{x}` already means "create bucket x", so `_search` is not a usable bucket name on this surface. `oxibase-js` 0.4.0: `.storage.from(bucket).search(query, {limit, highlight})`. Pinned by `tests/fts-storage.e2e.mjs` (13 assertions: ranking, bucket-scoped hits, missing bucket/query 400s, `<mark>` snippets, `read:false` refusing the *search*, service-key bypass, and surviving a restart).

**PostgREST-compatible auto-REST (`oxidb-server/src/rest/postgrest.rs`, ADR-0019).** A wire-compatible PostgREST surface over the document engine at `/rest/v1/{table}` (a table = a collection), so `@supabase/postgrest-js` and PostgREST clients talk to OxiDB unmodified. Pure **URL-grammar → query-AST translation** — no new engine state; compiles to the existing `find_with_options`/`insert_many`/`update`/`delete`. Grammar: filters `col=eq.42`/`gt`/`gte`/`lt`/`lte`/`neq`, `not.` negation (inverse ops `$ne`/`$nin`, else `$not`), `in.(a,b)`, `is.null`/`is.true`/`is.false`, `like`/`ilike` (→ anchored `$regex`; SQL-native `%`/`_` wildcards **and** PostgREST's `*` alias — the real `postgrest-js` emits `%`), `match`/`imatch` (raw regex), `or=(…)`/`and=(…)` (nestable), `select=name,price` (+`alias:col`), **resource embedding** `select=*,related(cols)` (nested docs via `$lookup`-style stitch — belongs-to inferred from a parent `<singular(target)>_id` field → single object, else has-many `<singular(parent)>_id` on the child → array; explicit `related!fk(...)` names the FK; nested embeds rejected), `order=price.desc,name`, `limit`/`offset`; full CRUD (`POST`/`PATCH`/`DELETE`), `Prefer: return=representation` echoes rows, `Content-Range` on reads. `cs`/`cd` array containment (`tags=cs.{a,b}` → `$all`/`$in`, the Postgres array literal `postgrest-js` `.contains()` emits — quote-aware, so `{"a,b"}` is one element and `{"2024"}` stays a string). Schemaless value coercion (null/bool/int/float/string; `eq."42"` forces string). Guardrails: `OXIDB_PGRST_MAX_ROWS` (default 1000) hard-caps a read; `?db=<name>` targeting inherited (ADR-0012). **Read-side gates (0.39.21, from an anon-key audit):** `POST /api/{col}/aggregate` now consults `read_access` — a pipeline reads the collection, and `$group` cannot be filtered after the fact, so a collection with a row-level read rule is **refused** to untrusted keys rather than answered from rows they may not see (before this, `$group` over a `doc.owner`-scoped collection returned every owner's values to the public key). `_`-prefixed **system collections are closed to untrusted keys** in both `check_access` and `read_access` — skipping the rules there was meant for the server's own bookkeeping, but let any anon key read the request log/slow-query profile and create unlimited `_`-named collections, which are also exempt from the project's collection quota. `GET /api/rules/{col}` is admin-only (the policy is not for the key it constrains). **Read policy now spans every engine (0.39.22):** the rules store is keyed by *name*, so a rule on a SQL table, a time-series measurement or a storage bucket governs reads of it exactly as a collection's does — `read:false` or `auth != null` makes it private. No rule still means readable (as for documents); what changed is that these could not be closed **at all** before. Only the document engine can honour a *row-level* rule, so a `doc.`-referencing rule on the other engines is a refusal rather than a silent no-op. `/api/sql` is gated per **referenced table** (`oxidb_sql::referenced_tables` walks FROM/JOIN, derived tables, CTEs and set operations), so a join, subquery or UNION cannot reach around the rule of any table it touches; an unparseable statement is refused for untrusted callers rather than passed through. **Safety reuses the existing gates**: `rest_permitted` (Read role → GET only) then `rules::check_access` per request (the RLS analog — `read:false` → `403`). **Rate limits in a rule (0.39.24):** a rule may carry `"rate": {"create": "10/min", "delete": "30/hour"}` (units sec/min/hour/day), enforced **per identity** (`auth.username`) per operation per collection — so one account flooding a collection cannot throttle everyone else, which the per-project `max_requests_per_min` would. Checked *after* the expression, so a write the rule refuses never consumes budget; a refused write answers **429 with `Retry-After`** (PostgREST surface) rather than 403, because "no" and "not yet" are different answers. service_role bypasses, as it bypasses rules. Fixed window, in-process (two nodes each allow the limit — the usual trade for not putting a write on every request's hot path); specs are validated at save time so an unparseable limit is an error rather than a rule that silently never applies. **Rule namespaces:** `doc.<field>` is the stored row and `newDoc.<field>` the incoming one; on **create** `doc.` binds to the row being created (there is no stored one), which is what makes `create: auth.username == doc.owner` — "you may only create rows you own" — expressible at all. Before 0.39.19 it denied every insert, and `newDoc.` was rejected by the validator despite the evaluator reading it, so ownership on create could not be written in any form. Native `/api/...` surface untouched. **Phase 2b — SQL engine under the same grammar** (`oxidb-server/src/rest/postgrest_sql.rs`): when `OXIDB_SQL=1` and `{table}` names a SQL table (`sql_bridge::sql_table_exists`), `/rest/v1/{table}` is served by the SQL engine — the same URL grammar → **parameterized SQL** (values always bound `?`, identifiers validated `^[A-Za-z_]\w*$` as the name-injection guard), CRUD → `INSERT`/`UPDATE`/`DELETE`, `{columns,rows}` reshaped to array-of-objects. A collection and a SQL table never collide, so dispatch is unambiguous; SQL-off keeps the document path byte-for-byte. SQL authz is RBAC-only (no per-row rules, like `/api/sql`) — which is exactly why **a write to a SQL table through `/rest/v1` requires a ReadWrite/service_role key** (0.39.20): the gate lets Read/Authenticated writes through so the *document* rules can adjudicate them, and a table has no rules to adjudicate with, so before this a published anon key could insert into and delete from any table. Same fix and reasoning as the tsdb profile. **SQL resource embedding** (Phase 2c) infers the relationship from **catalog foreign keys** (`sql_bridge::sql_foreign_keys`): FK current→target = belongs-to (object), FK target→current = has-many (array), `related!fk(...)` names the column; each embed is one batched `SELECT … WHERE fk IN (…)` stitched in Rust (not a JOIN — exact join columns from the declared FK, no naming-convention guessing). **SQL write-representation**: `Prefer: return=representation` appends `RETURNING *` to the INSERT/UPDATE/DELETE and echoes the affected rows (projected by `?select=`), else minimal (`201 []`/`200 []`/`204`). **TSDB under the same grammar** (`oxidb-server/src/rest/postgrest_tsdb.rs`, Phase 2d): selected by PostgREST's **schema profile** — `Accept-Profile: tsdb` / `Content-Profile: tsdb` (what `postgrest-js` `.schema('tsdb')` emits) routes `/rest/v1/{measurement}` to the time-series engine (profile-routing, not existence-routing, since a measurement only exists after its first write). Read: `select=<field>` (the field), `tag=eq.value` (tag equality), `ts=gte./lt.` (time range `[start,end)`), extension params `agg`/`interval`/`group_by`/`p`; the series result is flattened to `{ts, value, <tags…>}` rows, with `order=ts.*`/`limit` post-flatten. Write: flat `{ts, host:"x", usage:0.5}` → ts/time=timestamp, string→tag, number/bool→field (or nested `{ts,tags,fields}`). PATCH/DELETE → `405` (append-only; use retention). RBAC-only, `OXIDB_TSDB=1` — and because "RBAC-only" means there are no per-row rules to fall back on, **writes under the tsdb profile require a ReadWrite/service_role key**: the browser-safe anon key may read series but never append to them (0.39.17; before that it could, which let a published anon key poison a project's series). **Nested embeds** (`authors(name,books(title,chapters(name)))`) work on both the document and SQL engines — a child's `select` recurses through the same projection path (`project_top`/`project_sql`) at `depth+1`, bounded by `MAX_EMBED_DEPTH` (5). The whole surface (**all three engines**, incl. 2-level nesting) is verified against the real unmodified `@supabase/postgrest-js` client (`tests/postgrest-js-test/`, 26 assertions). ADR-0019's mapped grammar is functionally complete.

**OxiBase control plane (`oxidb-server/src/platform/`, ADR-0020).** A multi-tenant provisioning layer — the Supabase-platform analog on top of the `/rest/v1` data plane. Off unless `OXIDB_PLATFORM=1` **and** `OXIDB_PLATFORM_SECRET` (the platform master secret that signs developer sessions). Route family `/platform/v1/*`: `signup`/`login` (developer accounts, stored in a `_oxibase` system database opened directly outside `DatabaseManager`), `POST/GET/DELETE projects` (a project = one isolated tenant database via `DatabaseManager::create_database`). Each project gets its **own** `jwt_secret`, generated at creation and stored **AES-GCM encrypted** in `_oxibase.projects` (`crypto::EncryptionKey::from_bytes`). **Two-secret boundary (ADR-0021):** `OXIDB_PLATFORM_SECRET` signs developer sessions (control-plane only); `OXIDB_SEAL_KEY` seals/unseals per-project secrets — the data-plane hook `project_secret` unseals with the seal key **alone**, never the session-signing master (falls back to master when `OXIDB_SEAL_KEY` unset, single-binary skeleton). Two API keys per project, minted as JWTs signed with that project secret at a fixed `iat` (deterministic/stable): `anon_key` (role `read`, browser-safe) and `service_role_key` (role `admin`, server-only, bypasses rules). **The one data-plane change:** the REST listener resolves the JWT verification secret **per target database** — a `?db=<ref>` request to an OxiBase project verifies with that project's secret (`platform::project_secret`), everything else with the global `OXIDB_JWT_SECRET`. Isolation modes recorded per project: `shared` (many logical databases in one process, the default and OxiDB's density advantage) vs `dedicated` (a process per tenant, future). Addressing v1 is `<host>/rest/v1?db=<ref>` (works today); per-project subdomains are a v2 behind a wildcard cert. **Hardening:** `POST /platform/v1/projects/{ref}/keys/rotate` re-mints both keys under a fresh project secret so a leaked key dies immediately (keys carry a stored `key_iat` = creation-or-rotation time, kept deterministic); per-project secrets are cached (`secret_cache`) and invalidated on rotate/delete so a revoked secret can never keep verifying; signup is guarded by an 8-char minimum password, a per-actor rate limit (forwarded client IP via `X-Forwarded-For`/`CF-Connecting-IP`, `OXIDB_PLATFORM_SIGNUP_RATE`/min), an optional invite code (`OXIDB_PLATFORM_SIGNUP_CODE` — private signup), and a global account ceiling (`OXIDB_PLATFORM_MAX_ACCOUNTS`); login has a per-email brute-force lockout (5 fails → 5-min 429); projects-per-account is capped (`OXIDB_PLATFORM_MAX_PROJECTS`, default 100). Deployment specifics (hosts/secrets) stay in env, never committed. **Separate-service migration (ADR-0021, landed):** the generic HTTP types + parsing + a thread-pooled `serve` listener + a blocking JSON client are a standalone dependency-free **`oxidb-http`** crate (server's `s3::http` re-exports it). The control plane is now its own lean binary — the **`oxibase`** crate (deps: `oxidb-http` for its listener, `oxidb-client` for the wire, small crypto — **no engine**): it serves `/platform/v1/*` and reaches the data plane over OxiDB's **native OxiWire protocol** (a new standalone **`oxidb-client`** crate: length-prefixed JSON over TCP + client-side SCRAM-SHA-256 + a self-healing connection **`Pool`** with typed errors — `Connect` retryable / `Io` not / `Wire` healthy — so a stale pooled connection re-dials safely; zero engine deps) as an admin client — tenant databases via `create_database`, its own accounts/projects stored in an `oxibase` metadata database. Config: `OXIBASE_UPSTREAM` (`host:port`), optional `OXIBASE_UPSTREAM_USER/_PASSWORD` (SCRAM); the shared secret between the planes is now just `OXIDB_SEAL_KEY` (+SCRAM creds) — no shared JWT. `upstream.rs` isolates the transport, so the earlier REST version was a one-file swap. The data plane keeps **only** the `tenant_auth::project_secret` hook (`oxidb-server/src/tenant_auth.rs`, ~140 lines: reads that shared `oxibase` db locally, unseals with `OXIDB_SEAL_KEY`, short TTL cache since the control plane is out-of-process) and no longer serves `/platform/v1`. Config: `OXIBASE_ADDR`, `OXIBASE_UPSTREAM_URL`, shared `OXIDB_JWT_SECRET` (oxibase's admin token) + `OXIDB_SEAL_KEY`, control-plane-only `OXIDB_PLATFORM_SECRET`. Proven two-process end-to-end (signup → provision → service_role/anon keys work against the data plane's `/rest/v1`). ADR-0021 migration complete. **End-user social sign-in (`oxibase/src/oauth.rs`)**: per-project Google/GitHub OAuth for an app's *own* users — the developer stores the provider's client id + **sealed** secret on the project row (`oauth.{google,github}`, owner-only `GET/PATCH /platform/v1/projects/{ref}/auth/providers`), and users sign in through the authorization-code redirect (`/auth/authorize/{provider}` → provider → `/auth/callback/{provider}`) or, for Google, a browser ID token (`POST /auth/oauth/google`, no secret needed). The session is handed back on a **pre-registered** `redirect_urls` entry in the URL *fragment* (tokens never reach a server log); the allow-list is mandatory and its `*` can only extend a path, never widen a host. State is a stateless HMAC blob (10-min TTL) bound to project+provider, so the callback is CSRF-safe with no server-side session table. Accounts link by **verified** email only (GitHub's primary-verified address, Google's `email_verified`), so password-then-Google lands in one account. `GET /auth/settings` is the public discovery endpoint. **Magic links** (passwordless): `POST /auth/magiclink {email, redirect_to}` mails a 15-minute single-use link, `GET /auth/magiclink/verify?token=` burns it and redirects to the app with a session — the destination is validated and stored *when the mail is sent*, so a tampered link cannot move the session, and re-checked on click so a revoked URL stops working. The click doubles as signup + address verification. `mail.rs` gained a dev/test transport (`OXIBASE_MAIL_SINK` writes messages to a file instead of SMTP) so the whole email surface is testable without a mail server. **Session rotation (0.39.26)**: access tokens are short-lived (`OXIDB_PLATFORM_ACCESS_TTL`, default 1h) and `POST /auth/refresh` **rotates** the refresh token — it revokes the presented one, which is what makes a replayed token detectable. Two consequences were breaking real apps. (a) A client must persist *every* rotation, not just what sign-in returned; `oxibase-js` had no way to say a rotation happened, so an app storing the session in `localStorage` kept the token spent by the first refresh and every reload past the first hour 401'd forever with no recovery but re-login. The SDK now has `auth.onAuthStateChange(cb)` (`signedIn`/`tokenRefreshed`/`signedOut`) — `setSession` deliberately does *not* fire it, so a persist-on-event listener cannot loop. (b) Concurrent requests each 401ing on the same expired access token all POSTed the same refresh token, so one rotated and the rest were told "invalid" — a page whose feed fires 8 queries lost 7 of them. Fixed on both ends: the SDK coalesces refreshes into one in-flight promise and retries (rather than re-refreshes) a request whose token was rotated while it was in flight (a `tokenGen` counter), and the server honours a *just-consumed* token for `REFRESH_GRACE_SECS` (10) — a race is forgiven, a later replay is not. Consumed rows carry `used_at` and are swept, scoped to the user, on their next issued session; every revocation path (password reset/change, user delete) still deletes all of a user's rows, so grace never outlives a revoke. Pinned by `oxibase/test/auth.e2e.mjs` (rotation/grace/replay) and `oxibase-js/test/refresh.mjs` (offline, stub server: coalescing + the stale-persisted-token regression). **Per-project request rate limiting (0.39.16)**: the same model-B split as the size quotas — the value lives on the project row (`max_requests_per_min`, `PATCH /projects/{ref}/limits`, env default `OXIDB_PROJECT_MAX_RPM`), enforcement is in the data plane at the one point a request is attributed to a tenant (`rest/mod.rs`, right after the tenant db resolves), so every surface on that listener (REST, `/api`, storage, SQL) is covered by one check and refused before any work happens: `429` + `Retry-After`. Fixed one-minute window per project in `tenant_auth::rate_limit_hit` (one lock, one counter; refusals do not extend the window; stale windows swept past 4096 tracked projects). **0 = unlimited is the default** — throttling is opt-in, never a surprise an upgrade delivers under load. Remaining OxiBase work is additive: the web dashboard is a static React+TS+Vite SPA (`oxibase-dashboard/`, matching the OxiDB Studio stack; served outside Rust) — v1 has auth + project management (list/create/keys/rotate/delete), with a table/SQL editor over `/rest/v1` next, (B) JWKS/asymmetric verification for multi-node, and anon-with-rules.

**PostgreSQL wire protocol (`oxidb-server/src/pg/`, ADR-0023).** A tenth listener (`OXIDB_PG_PORT`, off by default; needs `OXIDB_SQL=1`) speaks the **PostgreSQL v3 frontend/backend protocol**, so `psql` and `psycopg` connect unmodified — verified against real psql 18 and psycopg 3.3. **Zero OxiWire changes**: it reaches the same per-database engines via `sql_bridge::engine`, the same accounts via `auth`, and the same SCRAM verifiers via `scram` (PostgreSQL wraps SCRAM in a SASL envelope, but the messages inside it are the RFC 5802 ones `ScramState` already parses — the only fix needed was accepting the `y,,` GS2 header alongside `n,,`, and deriving `c=` from it instead of hardcoding `biws`). Modules: `wire` (codec), `auth` (handshake), `session` (state + the one call into the engine), `catalog` (statements that never reach it), `types` (OIDs + value encoding), `errors` (SQLSTATEs). **A portal executes once, at `Describe` or `Execute` — whichever comes first** — because the engine reports a result's shape only by producing it, and answering `Describe(portal)` with `NoData` breaks psycopg (which reads column metadata from exactly there); the only visible difference from PostgreSQL is that an error surfaces one message earlier, still inside the same batch. `SET`/`RESET`/`SHOW`/`DISCARD`/`version()`/`current_database()` are intercepted (the engine's parser rejects `SET`, and every client sends one before it will talk); `\dt` and `\l` are answered from the engine's catalog, and **every other `pg_catalog` query is refused with `0A000` naming what is unsupported** — an empty result would be believed (found for real: answering psql's `\d <table>` probe with the table list made psql fail on a column it expected). Errors map to the SQLSTATEs clients recover on (`23505`/`42P01`/`42703`/`23502`/`42601`/`0A000`/`55P03`/`42501`), and the failed-transaction state is emulated (`'E'` until `ROLLBACK`; `COMMIT` answers `ROLLBACK`) because psycopg's `with conn.transaction():` recovery depends on it. Engine ints are **`int8`, never `int4`** (i64 would truncate). `Role::Read` may only SELECT/SHOW, same gate as the native port. **Doğrulanmış istemciler (gerçek sürücülerle, tahminle değil): psql 18, psycopg 3.3, Npgsql 8.0 (default modda — `NoTypeLoading` flag'i GEREKMİYOR), pgjdbc 42.7** (`DatabaseMetaData` dahil: getTables/getColumns/getPrimaryKeys — composite PK'nın her parçası — /getIndexInfo/getImportedKeys/getTypeInfo/getSchemas, hepsi motorun kendi kataloğundan: `list_tables`/`table_def`/`list_indexes`/`Table::foreign_keys`). Bunu açan iki iş: (a) **karışık batch** — bir simple-query mesajı hem intercept edilen hem motora giden statement taşıyabilir (Npgsql tam olarak `SELECT version();` + type-catalog sorgusunu TEK mesajda yolluyor; eskiden tüm batch motora gidip `version()`'da patlıyordu). `split_statements` tırnak/`''` escape/dollar-quote/`--`/`/* */` farkında, ardışık motor statement'ları tek çağrıda kalıyor. (b) **type catalog cevaplanıyor** — içeriği STATİK (bu sunucunun ürettiği tip listesi, gerçek PG OID'leriyle → sürücünün mevcut handler'ı aynen çalışıyor); composite-field ve enum sorguları **boş** dönüyor, ki bu DOĞRU (composite tip ve enum yok). Tablo-başına introspection hâlâ reddediliyor (statik değil). `pg_type.oid` kolonu `oid` (26), `typtype` `char` (18) olarak declare edilmeli — sürücü `int8`/`text` kabul etmiyor. **Catalog SATIRLARI da cevaplanıyor (0.41.4, `pg/pgcatalog.rs`) — DBeaver 25.3 native PostgreSQL sürücüsüyle bağlanıp gezinebiliyor.** DBeaver soru sormaz, kataloğun kendisini ister: `SELECT c.oid,c.* FROM pg_catalog.pg_class c` + `WHERE 1<>1` shape probe'ları. Bu yüzden PostgreSQL'in **gerçek kolon setleri** (sırasıyla, gerçek tip OID'leriyle) tutuluyor ve OxiDB'nin şemasından dolduruluyor: pg_class/pg_type/pg_namespace/pg_attribute/pg_constraint/pg_index/pg_database/pg_roles/pg_settings. **Kural: kolon setleri PostgreSQL'in, DEĞERLER OxiDB'yi anlatır** — karşılığı olmayan (tablespace, ACL, freeze horizon) NULL/0, olmayan katalog (pg_proc/pg_extension/pg_trigger) **kolonlarıyla + SIFIR satır** döner ("yok" doğru cevap, uydurma satır değil). Bunları çalıştırmak değil, ŞEKLİ cevaplamak: gerçekten çalıştırmak `~`, `::regclass`, `format_type()`, `pg_get_expr()`, set-returning fonksiyon ister. **DBeaver'da 3 gerçek bug çıktı (hepsi kodu okuyarak değil, ÇALIŞTIRARAK):** (1) dispatch *bahsedilen* tabloya bakıyordu → `pg_class LEFT JOIN pg_description` sorgusu pg_description olarak cevaplandı (boş tablo listesi) → artık **FROM hedefine** bakıyor; (2) `relkind` filtresi yok sayılıyordu → index'ler tablo olarak listelendi; (3) `\d` reddi çok genişti. **Çıktı BUFFER'lı** (`Conn.w()` artık `&mut Vec<u8>`, flush protokolün söylediği yerde): bir sonuç kümesi satır BAŞINA bir `DataRow` mesajıdır, doğrudan sokete yazınca 1000 satır = 1000 syscall (+`TCP_NODELAY` ile ~1000 paket). Benchmark bunu buldu: 1000-satır okuma 526→1796 ops/s (**3.4x**), OxiWire'a karşı 0.43x'ten 1.51x'e döndü → [wire benchmark](docs/wire-benchmark.md), `examples/wire_bench.rs` (aynı motor, aynı process, iki tel; her iki istemci de elle yazılmış ve minimal — kütüphane değil TEL ölçülüyor). **Eşzamanlılık (`--mode conc`)**: her iki dinleyici de standalone'da thread-per-connection (`OXIDB_POOL_SIZE` sadece cluster'da) — nokta okuma 16 bağlantıda ~3.6x'te tavan yapıyor (motor tek mutex), 100-satır okuma 4 bağlantıda ~8.3k'da BULUŞUYOR (yük altında tel önemini yitiriyor). **INSERT 1→32 bağlantıda DÜMDÜZ ~266/s, p50 4ms→91ms (tam doğrusal kuyruk) — SQL motorunda GROUP COMMIT YOK**: `Wal::append` kayıt başına fsync ediyor ve engine mutex'i tutulurken çağrılıyor, yani eşzamanlı commit'ler batch'lenmiyor sıraya giriyor (doküman motorunda group commit VAR, SQL motorunda yok — benchmark bu boşluğu ölçülebilir yaptı). ### Second engine — SQL (`oxidb-sql/`, ADR-0010)
A standalone relational SQL engine (its own crate) can be mounted alongside the document engine in the same server. It owns **entirely separate files** and shares no state — a collection name and a SQL table name never collide. Off by default.
- `OXIDB_SQL` (set to `1`/`true`/`yes`/`on` to enable; default off — zero cost when unused)
- `OXIDB_SQL_DATA` (SQL engine data dir; default `${OXIDB_DATA}/sql`)
- `OXIDB_SQL_DISK_FIRST` (rows served from the mmap'd last-checkpoint `.rdat` snapshot, only post-checkpoint changes in RAM; default off = all rows resident)
- `OXIDB_SQL_CHECKPOINT_BYTES` (auto-checkpoint the SQL WAL past this size; default 64 MiB, `0` = manual only)

Wire routing (`handler.rs`): a request with `engine: "sql"` — or the reserved `sql` command — is served by the SQL engine; a missing/`"doc"` engine keeps the document path byte-for-byte (full backward compatibility). Request shape: `{ "engine": "sql", "cmd": "sql", "sql": "SELECT ...", "params": [ ... ] }` (`params` binds `?`/`$N`). RBAC gates `sql` at the `ReadWrite` role. SQL supports DDL, DML, single-table + INNER/LEFT/RIGHT/FULL-join SELECT with GROUP BY/HAVING aggregates, secondary indexes, parameterized queries, and per-engine transactions (`BEGIN`/`COMMIT`/`ROLLBACK`). **Concurrent writers vs. a buffered transaction (0.40.2, was a silent lost write):** a transaction reserves its row ids and `AUTO_INCREMENT` values *from the engine* as it buffers each write (`SqlEngine::reserve_row_ids` / `next_auto_block`) instead of peeking the counter and allocating locally — the old peek handed the same id to any concurrent writer (another transaction **or a plain autocommit INSERT**) and the commit then overwrote their row, no error anywhere. Reservation makes rollback leave a gap, as sequences do everywhere. Because distinct ids alone would turn that lost row into two rows sharing one key, `commit_batch_checked` re-validates every PK/UNIQUE constraint against committed state under the commit lock (`BatchSim` simulates the ops in order, so a key the batch itself frees stays reusable) and refuses the commit if a key was taken meanwhile. The replication apply path (`commit_batch`) deliberately does **not** re-check — the cluster already agreed, and a node that second-guesses diverges — so the re-check is single-node; `tests/t_concurrent_writers.rs` (10 tests, all proven red first). **Cluster:** SQL writes ARE Raft-replicated — `sql_is_write` (`async_server.rs`) classifies a statement by parsing it (`oxidb_sql::is_read_only`), and a write replicates as `OxiDbRequest::Sql` (`Scoped` per database); SELECT-only SQL, and SQL that fails to parse, runs node-locally. **Not sharded:** oxipool shards by `collection` + a shard key, which a `sql` request has none of, so SQL is never scattered across shards — it routes to one backend (a replica when read-only, else the master). Stored procedures come in two languages (ADR-0014): SQL-text bodies (`CREATE PROCEDURE ... AS BEGIN dml; END` — zero-toolchain, re-parsed per CALL) and compiled **Cobra** bytecode (`CREATE PROCEDURE ... LANGUAGE COBRA AS '<base64 .cobrac>'`) executed by the `oxidb-cobra/` VM crate: the file defines `def run(db, ...params)`, `db.query`/`db.execute` join the CALL's transaction, print → notices, 100M-instruction fuel cap, determinism validated at CREATE (async/import/IO rejected) so CALL replicates safely.

**Persistence & crash-atomic checkpoints (`storage.rs`, `wal.rs`, `catalog.rs`, `manifest.rs`).** Each checkpoint writes a whole new **generation** into its own `gen.<N>/` subdirectory (`catalog.json` + one `<table>.rdat` row snapshot each), fsyncs it, then promotes it by renaming a tiny `MANIFEST` file (`{generation, wal_seq}`) into place — **the single atomic commit point** (`manifest.rs`). A crash anywhere before that rename leaves the previous `MANIFEST`, and thus the previous intact generation, in force; a half-written generation is ignored at open and swept. Because catalog and snapshots switch together, their arities can never disagree after a crash (the failure mode the old flat overwrite-in-place layout had). The WAL stays a **single file** (`wal/live.wal`, CRC'd, seq-numbered): the manifest records the highest seq folded into the snapshots, and recovery replays only records past that watermark (`Wal::open_since`), so a not-yet-truncated WAL never double-applies a checkpointed (non-idempotent) ALTER; truncation is best-effort. **Group commit (`CommitGate` in `lib.rs`):** a write appends + applies under the engine lock, releases it, and fsyncs *outside* it through a WAL descriptor duplicated once at open; one writer is elected leader and everyone whose record was on disk when its flush began is covered by it, so the engine lock is never held across an fsync. Acknowledgement is unchanged (a statement returns only after a flush covering its own seq); what is newly observable is the apply→flush window, the same one PostgreSQL and the document engine accept. A checkpoint publishes durability without flushing (`mark_durable`) — it already fsynced the snapshot those records were folded into, and must, since it may have just truncated the WAL they would flush. The gain starts at ~4 concurrent writers (a flush may only claim what was on disk when it *started*, so 1-2 writers never accumulate a group): the wire benchmark went from flat ~266 writes/s at every concurrency to ~1.2k/s at 16 connections. The watermark is `Wal::last_seq()` — publishing `next_seq` instead silently skipped every second fsync, caught only because single-connection throughput doubled where batching cannot help; pinned by `commit_gate_tests` (the gate may never claim a seq the WAL has not written) and `tests/t_group_commit.rs`. **Değişmeyen tablo YENİDEN YAZILMIYOR (0.41.27):** bir checkpoint, dayandığı generation'dan beri dokunulmamış her tablonun dosyalarını yeni generation'a **hard-link** ediyor (`link_generation_files`) — eski generation'ı geri kazanmak sadece bir dizin girdisini düşürür, inode yeni link üzerinden yaşar; MANIFEST rename'i hâlâ TEK commit noktası. Öncesinde checkpoint maliyeti ne kadar az değiştiğine bakmaksızın TÜM veritabanıydı (~1s / 1.2M satır) ve açılış tepesini sınırlamak için sık fold etmeyi karşılanamaz kılan buydu. Yeniden kullanım kasten **muhafazakâr**: tablo ancak satır deposu *tam olarak* base snapshot'ıysa (`RowStore::is_base_only` — dirty flag DEĞİL, yeni bir yazma yolunun set etmeyi unutabileceği bir bayrak yerine deponun kendisinden türetiliyor) VE yeni generation'ın ihtiyaç duyduğu her dosya eskisinde ZATEN varsa uygun. İkinci koşul gereksiz değil: son checkpoint'ten sonra yaratılan bir index'in dosyası yoktur, "var olanı linkle" demek dosyası olmayan bir index'i BEYAN eden generation commit etmek olurdu — hiçbir sorguya yanlış cevap vermez, index sessizce index olmaktan çıkar (`usable()` false → tarama). `checkpoint_reuse_tests` (5) her durumu pinliyor; index olanı kontrol kaldırılınca KIRMIZI olduğu kanıtlandı. Aynı işte **tablo başına tek satır yürüyüşü** (`storage::SnapshotWriter` + `RowStore::visit_physical`): snapshot yazıcısı, PK, UNIQUE ve secondary index builder'ları artık aynı geçişten besleniyor (eskiden tablo tüketici başına bir kez, yani disk-first'te satır başına bir decode BAŞINA tüketici okunuyordu). **Sequences live in a separate `sequences.json`** (direct-saved on every `NEXT VALUE FOR` — far more often than a checkpoint, and arity-independent), never inside the generationed catalog. Legacy flat-layout databases (root `catalog.json` + `<table>.rdat`, no `MANIFEST`) open as generation 0 and migrate to `gen.1/` at their first checkpoint. `OXIDB_SQL_DISK_FIRST` mmaps the committed generation's `.rdat` as the read base. **Engine-aware backup/restore**: `SqlEngine::backup(out)` is **low-lock** — it holds the engine lock only for two O(1) phases (pin a committed generation + read the WAL length; then unpin) and runs the slow `.tar.gz` compression with the lock released, so concurrent queries/writes are not blocked. A pinned generation is safe from GC and freezes WAL truncation, so the archive (a synthesized `MANIFEST` → the pinned `gen.<N>/` + a stable WAL prefix + `sequences.json`) is crash-consistent as of the pin instant even while writes and auto-checkpoints continue. `SqlEngine::restore(archive, target)` extracts into an empty dir. `Tsdb` (`oxidb-tsdb`) has the same **low-lock** `backup`/`restore`, split into `backup_begin` (pin a generation under the write lock) / `backup_write` (compress, no lock) / `backup_end` (unpin) — the per-generation `blocks.<N>.tsb`/`wal.<N>.log` files are pinned against a checkpoint's GC, so writes and auto-checkpoints continue during the archive; `tsdb_bridge.rs` orchestrates the three phases. Both are admin-only over the wire (`{engine:"sql"|"tsdb", cmd:"backup", path}` / `{cmd:"restore", archive, target}`, `sql_bridge.rs`/`tsdb_bridge.rs`) — separate from the document engine's `backup()`/PITR, which snapshots only the document data dir.

**Query performance vs PostgreSQL (`docs/query-benchmark.md`, `examples/query_bench.rs`).** İlk kez gerçek PostgreSQL'e karşı SORGU hızı ölçüldü (wire benchmark'ı OxiDB'nin KENDİ motoru üzerinde iki TEL'i karşılaştırıyordu, PG'nin planner/executor'ı hiç işin içinde değildi). OxiDB PG telini konuştuğu için **tek elle yazılmış istemci iki sunucuyu da sürüyor** — sürücü/dil farkı yok. Aynı 1.2M satırlık veri, simple query, her hücre decode ediliyor, PG stok + `ANALYZE`. **Nokta erişimi BERABERE** (PK 0.97x, composite PK 0.97x, secondary index eq 1.08x, range+ORDER BY+LIMIT 1.10x — hepsi ±%10). **Tarayan iş için `streamed_aggregate` (executor.rs) eklendi — aggregate'ler artık tarama SIRASINDA fold ediliyor**, genel yol gibi tüm satırları `Chunk`'a materyalize edip sonra grup indexlemek yerine (400k satırda İKİ geçiş + 400k'lık vektör, tek satır üretmek için): **full-scan aggregate 0.48x → 1.02x (PARİTE)**, GROUP BY 0.42x → **1.10x** (PG'yi GEÇTİ), secondary index eq 1.08x → 1.13x. **İki tuzak:** (a) ilk sürüm index probe'unu ATLIYORDU → `count(*) WHERE customer_id=?` 25µs lookup'tan 4ms full scan'e düştü (0.01x, benchmark anında yakaladı); artık index sonucu ÜZERİNDE fold ediyor. (b) DECIMAL'i `f64`'ten fold etmek YANLIŞ CEVAP olurdu (genel yol tam toplar) → SUM/AVG sadece tipi BİLİNEN ve tam foldlanabilir tiplerde (Int/Double/Timestamp) stream ediliyor. **Streaming index lookup (`Store::index_visit_eq`)** düşük seçicilikli taramayı **0.29x → 0.50x** yaptı: (a) `index_lookup_eq` eşleşen HER satırı önce bir `Vec<(u64, Vec<Value>)>`'e topluyordu (20k satır, sırf `count(*)` için), artık satırlar akıp gidiyor; (b) her aday satır İKİ KEZ materyalize ediliyordu — index key'ini doğrulamak için fiziksel, sonuç için mantıksal; artık `RowStore::to_logical` ile bir kez (DROP COLUMN yoksa fiziksel satır ZATEN mantıksal olandır). **Üçüncü maliyet: `RowStore::raw` KOŞULSUZ klonluyordu** — resident modda bellekte DURAN bir `Vec`'ten her aday kopyalanıyordu. `physical_ref`/`logical_ref` (Cow) artık ödünç alıyor; sadece disk-first base materyalize etmek ZORUNDA (satırlar mmap'te kodlu). **0.50x → 0.76x.** Kalan fark satır erişimi değil, satır başına predicate değerlendirmesi. **GROUP BY 0.42x → 1.10x:** `eval_scalar` OWNED `Value` döndürüyor, yani text kolonuyla gruplamak SATIR BAŞINA heap allocation + string kopyası yapıyordu (zaten var olan grubu bulmak için 400k allocation). Key düz bir kolonsa artık satırdan doğrudan karşılaştırılıyor, gerçekten YENİ grup çıkana kadar hiçbir şey ayrılmıyor. Bu hızlı yol SINIRLI: 32 gruptan sonra map yoluna geçer (yüksek kardinalite quadratic olmasın). 32 gruptan sonra **hash index** devreye giriyor (aynı yerinde karşılaştırmayla): 400k satırda 173k grup **153ms → 93ms** (PG 72ms). **İki yol da GEREKLİ, sınırı ölçüm belirledi:** hash'i koşulsuz kullanmak beş-gruplu durumu YAVAŞLATTI (1.10x → 0.95x) çünkü text key'i hash'lemek her baytı okur, karşılaştırma ise genelde ilkinde durur. **Key kolonları eşitliği net olan tiplerle sınırlı** (Int/Text/Bool/Timestamp): `total_order` sayısalları TİPLER ARASI karşılaştırır (`Int(1)` == `Double(1.0)`) ve NaN'ı her sayıya eşit sayar — hiçbir hash bunu üretemez, düz `==` de aynı fikirde değil; iki yol farklı gruplamasın diye float/decimal key'ler sıralı yolda kalıyor. **Join 0.56x → 0.87x (`semi_join_scan`)**: hash join sağ tabloyu KOMPLE materyalize edip çoğunu atıyordu (400k satırdan 40k eşleşiyor). Artık sağ satır, key'i solda YOKSA kurulmadan atlanıyor. **Yapı işin tamamıydı — iki ÖLÇÜLMÜŞ başarısızlık onu buldu:** (1) `INL_MAX_LEFT`'i 8192'den yükseltip 19823 satırla probe etmek DAHA KÖTÜ oldu (0.56x → 0.29x) — yani mevcut sabit ölçümle DOĞRULANDI; (2) bariz `BTreeSet<IndexKey>` üyelik testi daha da kötü (0.22x): satır başına ~14 `Value` karşılaştırması, kaçındığı satır kurulumundan pahalı. **Doğrudan adreslenen bitmap** (integer key aralığı üzerinde tek shift + tek mask) nihayet satır kurmaktan ucuz. Sadece integer key + bitmap'e değecek kadar yoğun aralıkta devreye giriyor; değilse eski yol. **Disk-first tarama hızını AYRICA düşürüyor** (aggregate 0.38x, GROUP BY 0.55x, join 0.29x) çünkü satırlar mmap'ten decode ediliyor — üstelik eskiden satır BAŞINA yeni bir `Vec` de ayrılıyordu: bir tabloyu gezen ITERATOR sahipli satır döndürmek ZORUNDA (kendi scratch'ine referans `next`'ten uzun yaşayamaz). `RowStore::visit_rows` push tarzı yürüyüş, tamponu kendi tutuyor → 1M satırlık tarama 1M yerine 1 allocation (GROUP BY 0.35x → 0.55x). **Sonra (0.41.29) SORGUNUN OKUDUĞU KOLONLAR KADAR decode:** bir tarama tüm satırı decode ediyordu; `sum(total)` `orders`'ın 5 kolonundan 1'ini okuyor. Executor okuyacağı kolon kümesini geçiyor (`Store::scan_visit_cols`), decoder gerisini ATLIYOR (uzunluğu oku, ilerle) ve pozisyonları korumak için `Value::Null` placeholder bırakıyor — böylece hiçbir çağıran değişmiyor, index remap yok. **GÜVENLİK yapısal:** küme `collect_needed`'dan geliyor, o da projection+filter+join+GROUP BY+HAVING+ORDER BY'ı geziyor, yani okunan her kolonun ÜST kümesi; DROP COLUMN varsa (fiziksel≠mantıksal pozisyon) masking REDDEDİLİYOR. **Sonuç: full-scan aggregate 0.37x→0.59x, join 0.27x→0.46x** (en kötü durum 3.7x yavaştan 2.2x'e). GROUP BY (0.53→0.51) ve düşük-seçicilik (0.46→0.45) DEĞİŞMEDİ ve sebebi kesin: GROUP BY tek TEXT kolonunu okuyup 3 int atlıyor, düşük-seçicilik index'ten servis ediliyor. `t_masked_scan.rs` differential (18 sorgu iki modda aynı sonuç, maskeyi sabote edince KIRMIZI) + `skip_cell`/`decode_cell` genişlik eşitliği her varyantta pinli. **Kalan maliyet ÖLÇÜLDÜ, çıkarsanmadı** (`examples/decode_bench.rs` — sorgu farklarından çıkarma İKİ KEZ yanlış sonuç verdi, çünkü bir hücreyi onu okuyan predicate terimiyle karıştırıyor): 400k satırda **sayısal hücre ~2 ns, TEXT hücre ~20 ns**; bunun 13.2 ns'i `Box<str>` alloc+copy+free, 3.4 ns'i UTF-8 doğrulama (`black_box` şart — ilk ölçüm 0.5 ns dedi, allocation DCE edilmişti). Yani geniş bir hücre-başı verimsizlik YOK; kalan şey değişken uzunluklu hücreyi materyalize etmek. **ÖDÜNÇ ALAN HÜCRE (`ValueRef<'a>`, 0.41.29) EKLENDİ:** mmap'e işaret eden `&str`; `Value`'ya lifetime EKLENMEDİ (katalog+WAL+serde'ye yayılırdı, tek kod yolu için). Kullanıldığı yer: hücrenin SAKLANMAKTAN çok KARŞILAŞTIRILDIĞI durum — group key. Text kolonuyla gruplarken 400k satırda kolon 400k kez kopyalanıyordu, zaten var olan grubu bulmak için; artık GRUP BAŞINA bir kez. **GROUP BY 0.51x → 0.63x** (p50 23.0→18.6 ms ≈ 11 ns/satır; allocation'ın 16 ns'inden azı, farkı ödünç satırın kendi defter tutması yiyor). Diğer workload'lar DEĞİŞMEDİ — text group key'leri yok, beklenen sonuç. **Üçü emüle edilmeden REDDEDİLİYOR** (cevap değişebilirdi): **resident tablolar** (hücreler zaten `Value`, ödünç almak sadece iki kez dönüştürüp karşılaştırır; ayrıca paritedeki modu ellemiyoruz — VE differential testi anlamlı kılan bu: iki mod da ödünç alırken bozuk bir ödünç İKİ TARAFI birden bozuyor, karşılaştırma yeşil kalıyordu), **`DECIMAL` kolonu** (owned `Value`'dan ödünç alınamaz → NULL okunurdu), **düşürülmüş kolon** (fiziksel≠mantıksal pozisyon). Gruplama mantığı TEK implementasyon: key hücreleri `KeyCells` trait'i üzerinden okunuyor, kaynak başına bir impl — ikinci bir kopya bu motorda zaten iki yolun FARKLI gruplamasına yol açmıştı (`==` vs `total_order`, `Int(1)`/`Double(1.0)`). `borrowed_key_tests` (eşitlik+HASH+materyalize) + `t_masked_scan::borrowed_grouping` (10 sorgu, ÜÇ sabotajın üçünde de KIRMIZI). **Yan bulgu — GERÇEK BUG düzeltildi:** `HAVING count(*) > 3` ORDER BY YOKKEN patlıyordu ("aggregate function used outside an aggregated query") çünkü ORDER BY olmaması tam da streaming aggregate yoluna sokuyor, o da HAVING'i BİTMİŞ grup satırına karşı değerlendiriyor ve orada `count(*)` hâlâ bir aggregate düğümü; artık aggregate içeren HAVING'de streaming yol ÇEKİLİYOR (genel yol doğru cevaplıyor, ORDER BY'lı yazımı hep öyle yapıyordu). PG bu sorguyu cevaplıyor, OxiDB cevaplamıyordu. **PREDICATE DEĞERLENDİRMESİ (0.41.30) — kalan boşluğun TAMAMI buymuş.** Terim SAYISINI değiştirip kolonu sabit tutan merdiven testi (decode aynı, sadece eval değişiyor): filtresiz `sum(total)` OxiDB 8.5 ms / PG 7.0 ms (**1.2x, neredeyse parite**), ama her ek AND terimi OxiDB'de **+5.1 ms**, PG'de **+0.35 ms** → satır başına terim başına **12.8 ns vs ~1 ns, 14x**. İki `f64` karşılaştırmak ~1 ns olduğuna göre 12 ns'in tamamı `eval_scalar`'ın HER SATIRDA yeniden karar vermesi: iki operandı önce borrowed string dene, sonra borrowed value dene, sonra operatörü dispatch et — hiç değişmeyen bir ifade için 400k kez. `SimpleFilter` bu kararları BİR KEZ veriyor: `kolon <cmp> literal` konjonksiyonu → `(index, op, value)` listesi; başka şekiller REDDEDİLİP genel yola bırakılıyor. **Terim başına 12.8 → 2.7 ns.** full-scan aggregate 0.60→**0.71x**, GROUP BY 0.63→**0.75x**, join 0.46→**0.49x**, 5-terimli predicate 0.26→**0.62x**. **Bu, geri alınan ifade derleyicisi DEĞİL** (`4398402e`→`e7d0da69`): o, işi bytecode dispatch döngüsüne TAŞIYORDU (Rust'ta computed goto yok, inline match'ten pahalı); bu işi KALDIRIYOR. **Differential test ilk koşuda GERÇEK bug yakaladı:** `c0 > 0 AND c1 < 'm'`, c0 NULL iken — ben NULL'da kısa devre yapıp "satır yok" diyordum, oysa SQL'in üç değerli AND'i sadece KESİN FALSE'ta kısa devre yapar, yani genel yol ikinci terime geçip HATA veriyor. Yani sessizce, patlaması gereken sorguya cevap üretiyordum. Artık unknown ile false ayrı izleniyor ve test sadece boolean'ı değil HATA ERİŞİLEBİLİRLİĞİNİ de karşılaştırıyor (1176 değer/operatör çifti). **JOIN AKIŞLI HÂLE GETİRİLDİ (0.41.31) — join+filter 0.49x → 0.79x (20.4→12.8 ms).** Faz ölçümü suçluyu kesin gösterdi: genel yolda probe+emit İKİ modda da 1.1 ms — fark tamamen MATERYALİZASYON (sol taraf chunk'ı 7.0 vs 1.6 ms, sağ semi-join taraması 10.7 vs 4.6; disk-first'te her materyalize satır = decode). PG probe tarafını HİÇ materyalize etmez: küçük filtreli tarafı hash'ler, büyüğü STREAM eder. `streamed_join_aggregate` = o şekil: tek INNER equi-join + aggregate (residual ON yok, ORDER BY/LIMIT/DISTINCT yok, her WHERE konjonktı TEK tarafa bağlanıyor) → sağ taraf KÜÇÜK kurulur (eşitliğini bir index karşılıyorsa index ÜZERİNDEN — 200k tarama yerine 20k fetch), sol taraf STREAM edilir, her eşleşme bulunduğu anda fold. **İki bekçi:** (1) SEÇİCİ eşitlik genel yolun sahası (index probe → küçük driver → INL, µs) — seçicilik sorgudan okunamaz, CAP'Lİ INDEX YÜRÜYÜŞÜYLE sınırlanıyor: `INL_MAX_LEFT`'i aşan eşleşme (veya index yok) = genel yol da tarayacaktı; (2) INNER simetrik → yön ÖLÇÜMLE: eşitlik-filtreli taraf index tarafı olur, yoksa küçük tablo. **Differential test İKİ KEZ boş çıktı** (bugün DÖRDÜNCÜ kez aynı ders): index tarafının anahtarı unique iken zincirler hep 1 uzunluğunda → zincir yürüyüşünü kıran sabotaj GÖRÜNMEZ; ve INL_MAX_LEFT'ten küçük fixture her eşitlik sorgusunu test edilen koda GİRMEDEN decline ediyor. Şimdiki fixture: index tarafında duplicate key + cap'i aşan eşitlik; ÜÇ ayrı sabotaj (zincir/scratch/residual-recheck) üçü de KIRMIZI. **Yan bulgu (önceden var, AYRI iş):** `JOIN ... WHERE c.id=42` genel yolda ~13 ms — `choose_driver` o tarafa swap etmiyor, sol taraf komple taranıyor; akışlı yol bunu DOĞRU şekilde decline ediyor (INL'in işi). **INDEX-FETCH DE MASKELENDİ (0.41.31 devamı):** düşük-seçicilik workload'ı (`country='TR' AND created>… AND id>…`) index'ten servis ediliyor, tarama DEĞİL — o yüzden scan-side masking hiç dokunmamıştı; ~20k adayın HER BİRİ 5 kolon tam materyalize ediliyordu (2'si kimsenin okumadığı text: email, name). `index_visit_eq_cols` / `index_visit_eq_masked`: scan yolunun `want` kümesi index fetch'ine taşındı; mask index'in KENDİ kolonlarını da içerir (base-is-a-hint kontratı her adayı canlı satıra karşı doğrulamayı GEREKTİRİR — doğrulama o kolonları okur); DROP COLUMN'lı tablo tam fetch'e düşer. **Düşük-seçicilik 0.52→0.65x (3.17→2.54 ms).** Join'in sağ-taraf index build'i de aynı maskeden geçiyor. Sabotaj (mask'ten caller kolonlarını düşür) differential'da KIRMIZI. **Kalan fark fetch değil aday-başına mekanik:** resident (map'ten fetch, decode yok) aynı sorguda 0.77x → fetch-side işle en fazla oraya ulaşılır; PG'nin avantajı bitmap heap scan (adaylar sıralı, sayfalar sıralı ziyaret) = FARKLI yürütme şekli. **⚠️ Ölçüm dersi (bugün 5.): bench oturumları arası ±5-8 makine kayması var — join 12.8→13.5 'regresyon' çıktı, tek değişkenli A/B (maskeyi geri al, aynı oturum) maskeli tarafın HIZLI olduğunu gösterdi; oturumlar arası sayı karşılaştırma, aynı oturumda A/B yap.** Bugünün toplamı: en kötü durum 3.7x yavaştan ~1.5x'e (düşük-seçicilik 0.65x), join 0.27→0.79x, aggregate 0.37→0.72x, GROUP BY 0.53→0.78x. **Tavan DEĞİŞMEDİ:** hiç text okumayan, HİÇ allocate etmeyen bir tarama hâlâ 0.65x — yani disk-first'i resident'tan ayıran allocation değil, decode'un KENDİSİ. Resident decode etmiyor (satırlar zaten `Vec<Value>`), o yüzden pariteye ulaşıyor ve disk-first allocation kaldırarak ona YETİŞEMEZ — nokta sorguları etkilenmiyor; yani memory benchmark'ının disk-first rakamlarıyla bunun resident rakamları İKİ FARKLI takas, deployment birini seçer. Yükleme de yavaş: 21 s vs 5.5 s. Ölçülmedi: eşzamanlılık, daha büyük veri, ayarlanmış PG, plan seçimi (PG'nin tarama avantajının bir kısmı daha İYİ PLAN seçmek olabilir — çalıştırmayı hızlandırmaktan farklı bir problem).

**Resident-memory design (`lib.rs`, benchmarked in `docs/pg-memory-benchmark.md`).** The SQL engine holds keys in RAM where PostgreSQL holds a capped page cache, which made an index-heavy 1M-row database cost 423 MB warm (disk-first) against PostgreSQL's 105 MB. Nine measured changes took that to **36 MB** of process memory, with the post-load figure from 611 to 68 MB, and (like PostgreSQL) exercising every index no longer moves it. **⚠️ Do not quote 36-vs-106 as a memory win**: `phys_footprint` excludes clean file-backed pages, so moving indexes into mmap'd files partly moved memory into a column the metric does not count. Measured properly (`bench/pg-memory/fair.sh` + `cached.rs`, `mincore(2)` over each data directory): **total physical OxiDB 203 MB (35 anonymous + 168 page cache) vs PostgreSQL 297 MB (108 + 189)** — a third less, mostly because the data directory is a third the size. **ÇOK KİRACILI ŞEKİL — OxiBase'in gerçek dağıtımı (`bench/pg-memory/tenants.sh`):** OxiBase'de proje = veritabanı ve hepsi TEK process'i paylaşır; Supabase'de proje = ayrı Postgres INSTANCE'ı, yani sabit maliyetler (postmaster + 8 arka plan process + `shared_buffers`) kiracı BAŞINA ödenir. 10 kiracı (her biri 5k müşteri / 20k sipariş / 40k satır, 4 index), PG `shared_buffers=32MB` ile: **OxiDB 201 MB tek process, PostgreSQL 960 MB on instance — 4.8x az**; kiracı başına 20 MB vs 96 MB, MARJİNAL ~16 MB vs 96 MB (PG'nin 96'sı her instance'ta AYNI çıktı). 50 kiracıda ~0.8 GB vs ~4.8 GB'a projekte olur. **Tek büyük veritabanında OxiDB 3x hafif DEĞİL; çok sayıda küçüğünde gerçekten öyle.** ⚠️ Bu test bir boşluk buldu: **`OXIDB_DOC=0` bugün TEK VERİTABANI demek** — kiracı provision'ı doküman manager'ından geçiyor, o da dokümanlar kapalıyken in-memory olduğu için SQL registry'nin aradığı disk dizinini hiç yaratmıyor; SQL-only çok kiracılı host henüz mümkün değil (benchmark OxiBase gibi dokümanlar AÇIK koşuyor).

**Bellek baskısı testi (`bench/pg-memory/pressure.sh`, cgroup v2 `--memory`) tahmini ÇÜRÜTTÜ:** evictable oranı düşük bir tabana çevrilmiyor — **OxiDB'nin tabanı ~96 MB, ayarlanmış PostgreSQL'inki ~64 MB** (stok PG ~112 MB, yani OxiDB varsayılanı yener, ayarlanmışı yenemez). Sebep cgroup muhasebesinde görünüyor: warm OxiDB `anon 72 MB, file 0 MB` — anonim kalan kısım hâlâ satırla ölçekleniyor (`.rdat` satır-offset index'i 24 B/satır = 27 MB) + BOŞ veritabanında bile 37 MB taban. **Daha kötü bulgu: fold edilmemiş WAL kuyruğuyla AÇILIŞ 415 MB tepe yapıyor** (steady state 94 MB) — checkpoint her index/PK/UNIQUE'i yazmadan önce bellekte sıralı map olarak materyalize ediyor, yani 128 MB'da rahat KOŞAN bir sunucu bulk load sonrası 128 MB'da YENİDEN BAŞLAYAMIYOR. **DÜZELTİLDİ: 415 → 365 → 328 → (0.41.27) steady state'in 1.7 katı.** Açılış tepesi **ÖLÇÜLDÜ, çıkarsanmadı** (`oxidb-sql/examples/open_mem.rs`, sayan global allocator): tepe *canlı* byte 128.7 MB ≈ process tepesi 116 MiB, yani **allocator retention DEĞİL** — bu doküman öyle diyordu ve YANLIŞTI (process metriği canlı ile serbest-ama-tutulan'ı ayırt edemez, sonuç iki yapısal düzeltmenin ödemediğinden ELEME ile çıkarılmıştı). Tepe TAMAMEN WAL replay'i: fold edilmiş WAL ile aynı açılış 42 MB. Tepe bekleyen iş cinsinden DÜZ BİR DOĞRU (~55 MB + bekleyen satır işlemi başına ~370 B), yani fold aralığı tepenin KENDİSİ. Eski takas: 25k'da fold = 71 MB ama 42.6 s (200k = 129 MB / 8.0 s), çünkü fold maliyeti veritabanının tamamıydı. Değişmeyen tabloların dosyaları yeniden kullanılınca fold değişene oranlı hâle geldi → varsayılan 50k: **63 MB / 6.1 s** — hem yarısı kadar tepe HEM de yerini aldığı ayardan hızlı. Bonus: builder'lar artık aynı anda canlı olduğu için `SPILL_ENTRIES` 131_072 → 32_768 (%10 zamana 22 MB; altında tepe düşmüyor). **Fold aralığı SABİT DEĞİL, satır sayısıyla ÖLÇEKLENİYOR** (`auto_fold_ops` = `max(50_000, rows/24)`; `OXIDB_SQL_REPLAY_FOLD_OPS` ezer, `0`=hiç fold etme). Sebebi 9.6M satırda (`gen.py --scale 8`) ölçüldü: takasın İKİ tarafı da satır başına (geçici ~370 B/bekleyen işlem, steady ~33 B/satır), yani SABİT aralık her ölçekte farklı ORAN demek ve birini yanlış yapar — 1.2M'de 50k doğru (3.2x marjı 1.67x'e indiriyor, 2.6 s'e), ama 9.6M'de 300 MB steady'den 46 MB kırpmak için 9 SANİYE fazla harcıyor (13.0 s / 387 MB vs oransal aralıkta 4.0 s / 489 MB). Oransal aralık ORANI sabitliyor: her ölçekte yeniden başlatma ≈ koşmanın 1.65 katı. Bu, bu işin AZ ÖNCE yanlış koyduğu bir varsayılandı; 1.2M'de ölçüp genellemek yetmedi. **Uçtan uca cgroup ölçümü (`bench/pg-memory/openpeak.sh` — yeni, sayı artık ad hoc değil yeniden koşulabilir; VARSAYILAN ayarlarla yükle, SIGKILL, yeniden aç, `memory.peak` oku): tepe 333 → 180 MB, açılış sonrası oturma 258 → 108 MB** (cgroup sayıları allocator'ınkinden büyük çünkü açılışın faultladığı page cache de yükleniyor; 333 geçen seansın ad hoc rakamını BİREBİR doğruladı). **⚠️ Tepeyi fazla satma:** sert limit altında çekirdek tepenin page-cache kısmını geri alır, bağlayıcı olan anonim kısım — bulk-load edilmiş veritabanını açabildiği en küçük limit **192 → 160 MB**, yani 1.9x'lik tepe kazancının aksine BİR basamak (128 MB'da iki build de OOM). İkisi de gerçek, farklı soruları cevaplıyor. **10M+ SATIRDA OOM RİSKİ VAR ama açılış tepesi DEĞİL:** steady state satır başına **32.8 B ve sabit terim YOK** (1.2M→37.5 MB, 9.6M→300 MB, fit orijinden geçiyor) — neredeyse tamamı `.rdat` satır-offset index'i (`Vec<(u64,u64,u32)>` = 24 B/satır). 10M ≈ 310 MB, 50M ≈ 1.5 GB, 100M ≈ 3.1 GB, hepsi ANONİM (evictable değil). Açılış GEÇİCİSİ ise sınırlı kalıyor (WAL kuyruğu `checkpoint_bytes` ile sınırlı, tabloyla büyümüyor) — 9.6M'de 56 MB kuyruk steady'nin 189 MB üstünde, 1.2M'dekiyle aynı aralık. Yani "disk-first" adına rağmen 100M satırda veri diskte, ona giden index RAM'de. **ÇÖZÜLDÜ — SEYREK satır index'i (`storage.rs`, `BLOCK_RECORDS=32`):** kayıtlar sabit başlıklı ve artan row-id sırasında olduğu için dosya ZATEN kendi index'i; 32 kayıtta bir girdi + hedefe 16-baytlık başlıkları yürüyerek ulaşılıyor. **Dosya formatı DEĞİŞMEDİ** — sadece açılışta kurulan şey değişti. **Tuzak:** tarama yolu kayıtlara KONUMSAL ve SIRAYLA erişiyor; seyrek index'ten "i. kayıt" istemek her satırda bloğu yeniden yürümek olurdu (tarama blok boyutunda quadratic). Bu yüzden sıralı okuyucular `SnapshotCursor` kullanıyor (kendi byte offset'ini taşıyor, sabit zamanda ilerliyor); sadece row-id ile arama yürüyor. **Sonuç: 32.8 B/satır → 0.69 B/satır (47x).** 1.2M: steady 37.5→**0.8 MB**, tepe 62.5→37.1; 9.6M: steady 300→**6.3 MB**, tepe 489→137. Okuma bedeli ~%2 (tarama 132→135 ms, PK nokta 7.2→7.3 µs), açılış süresi AYNI. 100M satır ≈ 69 MB (3.1 GB yerine). Disk-first artık satır başına HİÇBİR yapı tutmuyor: satırlar, secondary index'ler, PK, UNIQUE ve satır index'i hepsi dosya. **Blok boyutu ölçümle seçildi ama en büyüğü ALINMADI:** 9.6M'de yürüyüş neredeyse düz (16→7.1 µs, 128→7.4 µs) ve bellek 8x düşüyor, yani büyük blok bedava GÖRÜNÜYOR — ama o koşuda dosya page cache'te; yürüyüş payload'ları atladığı için 128-kayıtlık blok ~14 KB kaplar = bir satırı okumak için SOĞUKTA 4 sayfa (32'de 1 sayfa). Her boyut zaten GB'ı MB yapıyor, kalan MB'ı benchmark'ın ölçemediği page fault'la satın almaya değmez. **Değişen davranış:** yoğun index açılışta kendini savunma amaçlı SIRALIYORDU; seyrek olan satırları tutmadığı için sıralayamaz → artan row-id artık ZORUNLU invariant, ihlal eden dosya (veya tekrarlanan id) `Corrupt` ile açılmıyor; her yazıcı zaten artan sırada üretiyor. `sparse_index_tests` (8) pinliyor — satırlar BOŞLUKLU id'lerle üretiliyor (1,3,5…), çünkü bitişik id'ler "kayıt kalmadı" ile "geçti" arasındaki farkı gizler; ayrıca bir test index'in satır başına DEĞİL blok başına girdi tuttuğunu assert ediyor (yoksa yoğun bir implementasyon diğer 7'sini de geçerdi). (i) `IndexBuilder` bir **external sort**: çiftler sınırlı tampona birikir, sıralanıp run dosyasına spill edilir, sonra k-yollu merge doğrudan çıktıya; dosyanın üç bölümü ayrı temp dosyalara yazılıp birleştirilir, yani bitmiş index'in kopyası da tutulmaz. (ii) WAL replay artık kayıtları **tüketiyor** (`for rec in records`), eskiden ödünç alıp tüm parse edilmiş kuyruğu overlay'in yanında canlı tutuyordu. **Kalan ~230 MB overlay'in kendisi**: WAL kuyruğunu replay etmek bekleyen her satırı checkpoint fold edene kadar materyalize ediyor. Bunu sınırlamak replay SIRASINDA checkpoint gerektirir — ama `checkpoint_locked` canlı WAL'i truncate edip watermark'a `wal.last_seq()` yazar, yani replay ortasında çağırmak HENÜZ UYGULANMAMIŞ kayıtları "fold edildi" ilan edip silerdi. Güvenli hâli watermark'ın son UYGULANAN seq'i izlemesini ister — YAPILMADI: (a) **sorted inline posting lists** (`RowIds` = `SmallVec<[u64;1]>`) instead of a `BTreeSet<u64>` per index key — a key matching one row was allocating a whole 11-slot leaf node, ~150 B, to say so; (b) **`KeyTuple` = `SmallVec<[IndexKey;1]>`** instead of `Vec<IndexKey>`, killing one heap allocation per key in every index and PK map; (c) **`PkMap`** stores a single-column integer primary key as a bare `i64` (`103 → 34 bytes/row`), widening itself to the general `BTreeMap<KeyTuple,u64>` if a value that does not fit ever arrives; (d) **the replayed WAL tail is folded at open** in disk-first mode (`checkpoint_bytes/8` threshold) — records past the watermark replay into the RAM overlay and only a checkpoint moves them into the mmap, so a restart used to inherit the previous process's pending WAL as resident memory (a 55 MB tail cost 60 MB); (e) **secondary indexes are `populated: false` at open and built on first use** — rebuilding them eagerly cost 318 MB for three indexes on 1M rows before answering anything; writes skip an unpopulated index (it is built from current rows when wanted, pinned by `lazy_index_tests`), while `CREATE INDEX` still builds eagerly; (f) **the statement cache skips text over `STMT_CACHE_MAX_TEXT` (4 KiB)** — a bulk load filled all 512 slots with parsed 500-row `INSERT`s whose text is unique by construction, so the hit rate was zero and ~250 MB of key+AST stayed resident for the process's life (`stmt_cache_tests`). (g) **disk-backed secondary indexes** (`index_file.rs`, `.sidx`, disk-first only): a **sorted entry table** mmap'd in place — the document engine's `.mcidx` shape, not a B-tree, because every writer rewrites the file whole at checkpoint time (no splits, no free-space map, no page concurrency); lookup is a binary search over a fixed-stride table (keys reuse `encode_row`, which is not order-preserving, so ~20 decodes per probe). **The base is a HINT, not the truth**: it describes rows as of the last checkpoint, so instead of tombstones every candidate is *verified* against the live **physical** row (a deleted row is gone from the store; an updated row no longer matches the key) — one comparison on a row the caller was fetching anyway, and a stale base becomes self-correcting rather than wrong. Writes since the checkpoint go to `map` as an overlay; a checkpoint rewrites the `.sidx` and drops the overlay. **Indexes must be registered BEFORE the WAL replay at open** — registering after left the base current only to the checkpoint and the overlay empty, so every row written since was invisible to an indexed lookup (`disk_index_tests::rows_in_the_replayed_wal_tail_are_found`). Result: **318 MB resident → 41 MB on disk, and exercising every index no longer moves memory at all** (311 → 163 MB, flat like PostgreSQL); (h) **the PRIMARY KEY is disk-backed the same way** (`$pk.sidx` — `$` is illegal in an identifier so it cannot collide with a user index): the open path stops seeding `pk_map` per row when the file exists, `pk_owner_of` consults overlay-then-base and **verifies every hit against the live physical row** (a deleted row's key is reusable, a re-keyed row frees its old key — both pinned, because a stale hit here would be a phantom duplicate-key error and a missed hit a corrupt table), and `rebuild_meta` drops the base after an `ALTER` shifts positions. **163 → 58 MB**; (i) **column-level `UNIQUE` too** (`$uq<pos>.sidx` — keyed by physical *position*, not name, so a `RENAME COLUMN` cannot point at a stale file): NULLs are exempt under SQL so they are never written (a written NULL would make the second one a duplicate — pinned), same overlay/base/verify shape. **58 → 36 MB.** **The design came from the PostgreSQL source**, not from tuning: buffers are page-granular with a partitioned hash + clock sweep (`storage/buffer/README`), `_bt_check_unique` descends the on-disk tree and binary-searches a *locked leaf page* rather than any key map (`nbtree/nbtinsert.c`), and an index entry is an 8-byte `IndexTupleData` header + MAXALIGN'd key + 4-byte line pointer ≈ **20 bytes on disk** (`access/itup.h`). Disk-first mode now holds **no per-row structure in memory at all** — rows, secondary indexes and primary keys are all mapped files, and what stays resident is bounded by the checkpoint interval rather than by row count. **No key set of any kind is resident**; what is left is the `.rdat` row-offset index, the catalog and the post-checkpoint overlays. Resident mode is unchanged by design.

**Doküman motoru belleği (AYRI mekanizma — `OXIDB_DISK_FIRST`, default AÇIK; SQL'inki `OXIDB_SQL_DISK_FIRST`, default KAPALI; farklı depolama, farklı kod).** OxiBase dokümanları/storage/realtime'ı bu motordan servis ettiği için ayrıca ölçüldü: 1M doküman → boş 8 MB, yükleme sonrası 84 MB, **restart sonrası 52 MB**, tam tarama+filtre sonrası **92 MB**, diskte 141 MB. **Zaten SINIRLI** — 5 kat veri 1.7 kat bellek: her iki doküman cache'i de koleksiyonla ölçeklenen entry sayısıyla değil **sabit 128 MiB bütçeyle** boyutlanıyor (`doc_cache.rs`, `doc_bytes_cache.rs`), yani tarama onları doldurur ve DURUR — PostgreSQL'in `shared_buffers`'ıyla aynı şekil. Veriyle ölçeklenmeye devam eden: doküman başına offset index (SQL'deki `.rdat` satır-offset index'inin karşılığı).

**Instant (metadata-only) `ALTER TABLE ADD/DROP COLUMN` (`rows.rs`, ADR-0013 Phase D).** Both are **O(1)** — no row rewrite, no checkpoint — answering the "add/drop a column on a 500M-row live table with zero downtime" problem. The catalog stores the **physical** schema; `table_def` returns a **logical** view so the executor (whose scope is positional, `cols[i]↔cells[i]`) is untouched and never sees a dropped column. ADD appends a slot (old rows read back padded with the new column's default); DROP tombstones a column in place via a `Column.dropped` flag (Postgres `attisdropped`-style — the physical cell stays, projected out on read). `RowStore` projects physical→logical on read and exposes raw physical rows for index/snapshot work; writes expand logical→physical (`TableState::prepare_write`/`to_physical`, dropped slots = NULL placeholder); transactions read logical but log physical, translating a shifted UNIQUE position via `table_layout`. Durability rides on the WAL record alone (checkpoint skipped). A later checkpoint **compacts**: `RowStore::compact()` rewrites rows to the live columns and the tombstones are dropped from the catalog, reclaiming the space — the deferred O(n) rewrite folded into a checkpoint that rewrites every row anyway. `RENAME COLUMN` still rewrites/checkpoints eagerly. **`ALTER COLUMN <c> TYPE <ty>`** (PG `[SET DATA] TYPE`, MySQL `MODIFY COLUMN`) casts existing cells eagerly via the executor's CAST semantics (`RowStore::rewrite_slot`): a dry-run over all rows first — any uncastable value or over-length `VARCHAR(n)` aborts before the WAL append — then WAL + in-place rewrite + index rebuild + eager checkpoint; narrow (pre-ADD) rows are covered by casting the column default the fill template regenerates from. PRIMARY KEY / AUTO_INCREMENT / UNIQUE / FK-bound columns are rejected (a cast can collide previously-distinct key values).

### Third engine — TSDB (`oxidb-tsdb/`)
A standalone time-series engine (InfluxDB-style), mounted like SQL. Off by default. Storage differentiator: each series (measurement × tag-set × field) is a **Gorilla-compressed** columnar stream (delta-of-delta timestamps + XOR floats; ~0.3 bytes/point on regular data), partitioned into sealed blocks so retention drops whole expired blocks.
- `OXIDB_TSDB` (`1`/`true`/`yes`/`on` to enable; default off — zero cost when unused). Per-database, like SQL.
- `OXIDB_TSDB_DATA` (default `${OXIDB_DATA}/tsdb` for the default db; named dbs at `${OXIDB_DATA}/<name>/tsdb`).

Persistence (`persist.rs`): a **versioned block snapshot + per-generation WAL**, with a `MANIFEST` as the atomic commit point (`blocks.<N>.tsb`, `wal.<N>.log`, `MANIFEST`). Every point is WAL-appended; a checkpoint seals active buffers, writes a fresh `blocks.<N+1>.tsb` snapshot (+fsync), atomically replaces the MANIFEST (temp+rename), then rotates the WAL. Recovery reads the MANIFEST's generation → snapshot + its WAL, so a crash on either side of the rename never double-counts; retention is durable (dropped blocks just aren't in the next snapshot). Auto-checkpoint past 8 MiB of WAL.

Fields are typed (float/**integer**/**boolean**/**string**); numeric values are stored as `f64` (ints exact to 2^53, bools 0/1), text in a separate `(ts, string)` path; the type is remembered per series and reported in query results. Numeric aggregations: mean/sum/min/max/count/first/last/**distinct** plus **`rate`** (per-second change, for counters) and **`percentile`** (`agg:"percentile"`+`p`, or shorthand `p95`; linear interpolation). Text-field aggregations: first/last/count/distinct.

**Continuous-aggregate rollups**: `add_rollup(measurement, interval, aggs)` materializes completed time buckets of every numeric series of a measurement into a derived measurement `<m>@<label>` with fields `<field>_<agg>` (e.g. `cpu@1m` `usage_mean`). Incremental via a persisted per-series watermark (crash-safe, no double-count on restart); the rule set persists in `rollups.json`. `refresh_rollups(now)` processes only fully-closed buckets. Roll from raw (1s→1m, 1s→1h); chaining is a caller concern.

Wire routing (`tsdb_bridge.rs`): `engine: "tsdb"` (or reserved `tsdb` command), `cmd: "tsdb"` with an `op`: `write` (points: measurement/tags/fields/ts — JSON bool→boolean, integer→integer, else float), **`write_lp`** (InfluxDB line protocol in an `lp` string; ms timestamps, `now()` when absent — `line_protocol.rs`), `query` (measurement + field + tag filters + `[start,end)` + optional `GROUP BY time(interval)` downsample + `group_by` tags + `agg`), `stats`, `retention` (cutoff), `checkpoint`, `rollup_add`/`rollup_refresh`/`rollups`. RBAC gates `tsdb` at `ReadWrite`; Read role is query-only. Node-local.
