# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OxiDB is a fast, embeddable document database engine written in Rust. It supports both SQL and JSON-based queries. It can run as an embedded library, a standalone TCP server, or be accessed via client libraries (Python, Go, Julia, .NET, Swift/iOS via C FFI).

## Build Commands

```bash
cargo build --release                    # Build core library
cargo build --release -p oxidb-server    # Build TCP server
cargo build --release -p oxidb-client-ffi # Build C FFI shared library (.dylib/.so/.dll)
cargo build --workspace --features ocr   # Build with OCR support
```

## Testing

```bash
cargo test                               # All tests (workspace)
cargo test -p oxidb                      # Core library tests only
cargo test -p oxidb-server               # Server tests only
cargo test <test_name>                   # Single test by name
cargo test -- --nocapture                # With stdout output
```

Unit tests are inline (`#[cfg(test)]` modules in source files). Integration tests for the server are in `oxidb-server/tests/` (ACID and security tests).

## Workspace Structure

Cargo workspace with three crates:
- **Root (`oxidb`)** — core database library
- **`oxidb-server/`** — TCP server with SCRAM-SHA-256 auth, RBAC, TLS, audit logging
- **`oxidb-client-ffi/`** — C-compatible FFI (`cdylib`) for language bindings

Client libraries: `python/`, `go/`, `julia/`, `dotnet/`, `swift/`, `oxibase-dart/` (Dart/Flutter, see below)

## Architecture

### Core Engine (`src/engine.rs`)
`OxiDb` owns a `RwLock<HashMap<name, Arc<RwLock<Collection>>>>`. Per-collection locking enables concurrent reads. Collections are auto-created on first insert.

### Multiple Databases (`src/database_manager.rs`, ADR-0012)
`DatabaseManager` hosts many isolated `OxiDb` instances, one per subdirectory of `OXIDB_DATA`: default database `oxidb` (alias `postgres`), server-global `_auth`/`_audit` at the top level, flat legacy layouts auto-migrated into `oxidb/` on open (never overwriting). Wire: optional `db` field per request, `use_db` sets the session default, plus `create_database`/`drop_database`/`list_databases` — and the SQL-text equivalents `CREATE/DROP DATABASE`, `SHOW DATABASES`, `USE` (both surfaces parse into one `DbIntent` in `oxidb-server/src/db_admin.rs`; create/drop are Admin-only). RBAC supports per-database roles (`db_roles`, `grant_db_role`/`revoke_db_role`). The SQL engine is per-database too: default db at `OXIDB_SQL_DATA` (`${OXIDB_DATA}/sql`), others at `${OXIDB_DATA}/<name>/sql` (`sql_bridge` registry). Cluster mode replicates database DDL and scopes writes via `OxiDbRequest::Scoped`; TTL/alert threads run per database; REST takes `?db=<name>`, WS a per-message `"db"` field; transactions are bound to the database they began on. OxiMem keyspace and S3 buckets are intentionally global.

### Collection (`src/collection.rs`)
Each collection owns:
- **Storage** (`storage.rs`) — append-only file with `[status:u8][length:u32 LE][payload]` records; soft-delete flips status byte in-place
- **WAL** (`wal.rs`) — write-ahead log with CRC32 checksums; entries tagged with transaction IDs; 3-fsync protocol (WAL → data → checkpoint)
- **In-memory document cache** — `HashMap<DocumentId, Arc<Value>>` (JSON deserialized once, then refcounted)
- **Field indexes** — `BTreeMap<IndexValue, BTreeSet<DocumentId>>` per indexed field
- **Composite indexes** — multi-field B-tree for prefix scans
- **Version map** — per-document version counters for OCC

### Query Engine (`src/query.rs`, `src/pipeline.rs`)
Query AST with field conditions and logical operators ($and, $or, $nor). Operators: $eq, $ne, $gt/$gte/$lt/$lte, $in, $nin, $exists, $regex, $elemMatch, $not, $all, $size, $type, $mod. Top-level $expr for cross-field comparisons. Key optimizations:
- Index-backed sort: BTreeMap iteration is O(limit) instead of O(n log n)
- Index-only count: returns set size without touching documents
- Early termination: `update_one`/`delete_one` stop after first match

Aggregation pipeline: $match, $group, $sort, $skip, $limit, $project, $count, $unwind, $addFields, $lookup, $facet, $setWindowFields (window functions — document `{documents: [lo,hi]}` AND value/time `{range: [lo,hi], unit?}` frames), $dateHistogram (time-bucketed group + empty-bucket fill), $ohlcv (tick→candle OHLCV with symbol partitioning and LOCF gap fill), $densify (gap-generating docs on a numeric/date axis; fixed units only), $fill (locf / linear / constant null-filling per partition).

### Updates (`src/update.rs`)
Field operators ($set, $unset, $inc, $mul, $min, $max, $rename, $currentDate) and array operators ($push, $pull, $addToSet, $pop). Supports dot-notation for nested fields.

### Indexes (`src/index.rs`, `src/value.rs`)
`IndexValue` enforces cross-type ordering: Null < Bool < Num < DateTime < String. Dates are auto-detected from ISO 8601/RFC 3339/YYYY-MM-DD strings and stored as epoch ms.

### Transactions (`src/transaction.rs`, `src/tx_log.rs`)
OCC with 3-phase commit: prepare → validate versions → commit. Writes are buffered until commit. Deadlock-free via sorted collection locking (BTreeSet). Recovery uses transaction log + WAL replay on startup.

Isolation: backward-validating OCC over item read-sets — committed transactions are serializable w.r.t. the items they read/wrote; phantoms and torn reads for non-tx observers are admitted for plain `find`/`count`. The exact guarantee, anomaly scorecard, and application rules live in `docs/isolation.md`, pinned by `tests/isolation_characterization.rs`.

### Read snapshots — MVCC-lite (`src/snapshot.rs`, ADR-0017)
Read-path-only snapshot visibility; the write path (OCC, `find_for_update`, group commit) is untouched. `aggregate` is snapshot-consistent by default: optimistic latest-state run, proven valid when no write raced it (`SnapGate::changed_since`), else an always-correct resolve-and-recheck fallback — a concurrent aggregation can never see half a transfer. Explicit API `begin_snapshot`/`snapshot_find`/`snapshot_count`/`snapshot_aggregate`/`end_snapshot` (wire: `snapshot_begin`…`snapshot_end`, Read-role tier; the snapshot id is a token, not session state). Mechanics: a snapshot begins under `commit_lock.write()`; every writer records displaced prior bytes into the gate under its `commit_lock.read()` scope (storage layer, `btree_storage.rs`) — that RwLock is the visibility boundary. No snapshot open (the default) costs one relaxed atomic load per write; the version map exists only while a snapshot is open and prunes to the oldest live one. `OXIDB_SNAPSHOT_MAX_SECS` (default 300) hard-expires snapshots — dead-snapshot reads fail with `SnapshotExpired`, writers never wait. Pinned by `tests/snapshot_reads.rs` (torn-sum test proven red pre-feature).

### Full-Text Search (`src/fts.rs`)
Background worker thread receives indexing jobs via `sync_channel(256)`. Supports HTML, XML, JSON, PDF, DOCX, XLSX, images (OCR with `ocr` feature). TF-IDF ranking. Persisted as `_fts/index.json`.

### Blob Storage (`src/blob.rs`)
S3-style bucket interface. Objects stored as `_blobs/<bucket>/<id>.data` + `<id>.meta`. ETags are the first 16 bytes of the payload's SHA-256, hex-encoded (not S3's MD5). A full S3-compatible HTTP API (`OXIDB_S3_PORT`) covers Put/Get/Head/Delete/Copy, ListObjectsV2 (prefix/delimiter/continuation), multipart upload, Range + If-[None-]Match, object tagging, `Expiration/Days` lifecycle, SSE-S3/SSE-C, and SigV4 auth (headers + presigned URLs) — so `aws-cli`, `boto3` and the MinIO SDKs work unmodified. No versioning/ACL/S3-Select; path-style addressing only.

### Encryption (`src/crypto.rs`)
Transparent AES-GCM encryption at the storage layer. Optional—enabled by passing an encryption key to the engine.

### Point-In-Time Recovery (`src/pitr.rs`, `src/archive.rs`)
Opt-in via `OXIDB_PITR`. `ArchiveSequencer` (`pitr.rs`) hands every durable WAL write a global, monotonic, wall-clock-stamped GSN (persisted in leases via `_gsn`); WAL records carry it in the **v2** record format (`wal.rs`). The WAL rotates: `Wal::seal()` atomically renames the live `.wal` to a numbered sealed segment under the WAL lock. A background archiver (`archive.rs`, spawned by the engine) copies sealed segments into `_archive/segments/*.seg` (verbatim bytes + trailer) with a self-healing `manifest.json`. `backup()` embeds a `base.meta` GSN watermark. `OxiDb::restore_to_point` extracts a base backup then `archive::replay_into` advances it to a `Gsn`/`Timestamp`/`Latest` target with transactionally-consistent cuts. Off = zero cost.

### Server Protocol (`oxidb-server/`)
Length-prefixed JSON over TCP (max 16 MiB). Auth via SCRAM-SHA-256. RBAC roles: Admin, ReadWrite, Read. Configurable via env vars:
- `OXIDB_ADDR` (default `127.0.0.1:4444`)
- `OXIDB_DATA` (default `./oxidb_data`)
- `OXIDB_DISK_FIRST` (default ON since 0.38-line: document bodies live in an mmap'd `.bdat` with only a ~24 B/doc offset index resident; `0` restores the always-resident `.btree` mode. Existing collections keep their created format — `.bopts`/on-disk format is authoritative over the env). Since 0.38.10 the `.bdat` is **uncompressed by default** (per-record zstd cost scans/aggregations 4-8x); `OXIDB_DISK_COMPRESSED=1` opts back into zstd. Composite indexes are disk-backed too (`.mcidx`, 0.38.9), and full-collection `$group` aggregations covered by a composite index are answered without reading documents (0.38.3-7).
- `OXIDB_POOL_SIZE` (default 4 worker threads)
- `OXIDB_IDLE_TIMEOUT` (default 30s, 0 = never)
- `OXIDB_AUDIT` (default off; set to `true`/`1` to enable audit log)
- `OXIDB_AUDIT_MAX_BYTES` (optional; rotates audit log when live file reaches this many bytes)
- `OXIDB_AUDIT_MAX_AGE_SECS` (optional; rotates after this many elapsed seconds since file became active)
- `OXIDB_AUDIT_CALENDAR` (optional; `hourly` / `daily` / `none` — UTC calendar boundary)
- `OXIDB_AUDIT_COMPRESS` (optional; `true`/`1`/`yes`/`on` to gzip rotated audit files; default off)
- `OXIDB_SLOW_QUERY_MS` (optional; record wire commands slower than this many ms into `_profile` with a TTL index; default off)
- `OXIDB_PROFILE_TTL_SECS` (optional; retention of `_profile` records, default 86400)

Diagnostics: `{"cmd": "explain", "inner": {...find/count/aggregate...}}` returns the query plan (strategy, index used, examined/returned, post-filter operators) plus real run timing. Prometheus exposition at `GET /metrics` on the REST listener.

**Dart/Flutter client (`oxibase-dart/`, package `oxibase` 0.1.0).** Mobile apps talk to a project the way the browser does: `OxibaseClient(url, key, ref, authUrl)` → `.from(table)` (PostgREST grammar → documents or a SQL table, server-dispatched), `.series(measurement)` (tsdb profile), `.sql(text, params)`, `.textSearch`/`.createTextIndex`, `.storage.from(bucket)` incl. `.search()` over file contents, `.subscribe()` realtime (one shared socket; the auth frame carries `db`; reset on identity change but **not** on rotation, or every hourly refresh would drop every subscription), and `.auth` (password, magic link, OAuth URL for a deep link, Google ID token, `sessionFromRedirect` for the fragment). Two deps, both already in a Flutter tree: `http`, `web_socket_channel`. **The JS client's auth bugs are designed out**: refresh is single-flight, a request whose token rotated mid-flight retries instead of re-refreshing (`_tokenGeneration`), and every rotation is emitted on `onAuthStateChange` so a stored session stays current — `setSession` deliberately does not emit, or a persist-listener loops. `OxibaseException` keeps the server's distinctions: `isRateLimited` (429 + `retryAfter`) separate from `isDenied` (401/403), `isConflict` (409) for a unique-index duplicate. 17 tests: URL building (incl. `eq."42"` quoting, and `is.null` *not* quoted — a real bug the test caught), single-flight refresh, rotation reporting, the spent-token regression, and an opt-in live suite (`OXIBASE_URL`/`OXIBASE_KEY`) covering documents, ranked search and storage search. MIT, like the other clients; `dart analyze` and `pub publish --dry-run` clean, **not published to pub.dev**.

**Full-text search over REST (0.39.27).** The engine's BM25 index (`src/fts.rs`, k1=1.2/b=0.75, Lucene defaults) was wire-only, so no OxiBase project could use it: `POST /api/{col}/text_search` (`{query, limit≤500, highlight}` → documents with `_score`, and `_highlights` `<mark>` snippets when asked) and `POST /api/{col}/text_index` (`{fields}`) close that. **Gating differs from `aggregate` on purpose**: a text search returns whole documents, so a row-level read rule *can* be honoured — matches are filtered like `find` does rather than the request being refused (a filtered search may return fewer than `limit`; the alternative leaks how many matches the caller may not see). `read:false` is refused outright. Searching is a read (`rest_permitted` allows it for Read/Authenticated alongside `aggregate`); **building the index is not**, so it needs ReadWrite/service_role — otherwise a published browser key could index anything. Unindexed collection = explicit error, not an empty result, so a client can fall back. `oxibase-js` 0.3.0: `.textSearch(col, q, {limit, highlight})` / `.createTextIndex(col, fields)`. **Disk-first text indexes did not survive a restart (0.39.28)** — found the moment the surface was used for real: `btree_collection::create_text_index` never called `save_index_metadata` (its `collection.rs` sibling always did, and `list_indexes` already reported the index), and the open path had no `"text"` arm, so every deploy silently dropped every project's index and searches answered "no text index". Only the *definition* is persisted; postings are rebuilt by one document scan at open, paid only by collections that asked for full-text search. Pinned by `tests/fts-rest.e2e.mjs` (19 assertions: ranking, highlights, both refusals, row-level filtering, service-key bypass, and surviving a restart via `OXIDB_RESTART_CMD`). **Blob/bucket FTS over REST too (0.39.29):** `POST /api/storage/_search` (`{bucket, query, limit≤200, highlight}` → `{bucket, key, score}` + `highlights`) searches the text extracted from uploaded files (HTML/XML/JSON/PDF/DOCX/XLSX, OCR'd images with the feature) — indexed automatically on every `put_object`, so nothing is built first. **The bucket is required**: a bucket's read rule is per bucket, so a cross-bucket search could report keys out of a `read:false` bucket; per-bucket makes the check exactly `read_allowed`, the one a download already passes. Matched ahead of the storage delegate because `POST /api/storage/{x}` already means "create bucket x", so `_search` is not a usable bucket name on this surface. `oxibase-js` 0.4.0: `.storage.from(bucket).search(query, {limit, highlight})`. Pinned by `tests/fts-storage.e2e.mjs` (13 assertions: ranking, bucket-scoped hits, missing bucket/query 400s, `<mark>` snippets, `read:false` refusing the *search*, service-key bypass, and surviving a restart).

**PostgREST-compatible auto-REST (`oxidb-server/src/rest/postgrest.rs`, ADR-0019).** A wire-compatible PostgREST surface over the document engine at `/rest/v1/{table}` (a table = a collection), so `@supabase/postgrest-js` and PostgREST clients talk to OxiDB unmodified. Pure **URL-grammar → query-AST translation** — no new engine state; compiles to the existing `find_with_options`/`insert_many`/`update`/`delete`. Grammar: filters `col=eq.42`/`gt`/`gte`/`lt`/`lte`/`neq`, `not.` negation (inverse ops `$ne`/`$nin`, else `$not`), `in.(a,b)`, `is.null`/`is.true`/`is.false`, `like`/`ilike` (→ anchored `$regex`; SQL-native `%`/`_` wildcards **and** PostgREST's `*` alias — the real `postgrest-js` emits `%`), `match`/`imatch` (raw regex), `or=(…)`/`and=(…)` (nestable), `select=name,price` (+`alias:col`), **resource embedding** `select=*,related(cols)` (nested docs via `$lookup`-style stitch — belongs-to inferred from a parent `<singular(target)>_id` field → single object, else has-many `<singular(parent)>_id` on the child → array; explicit `related!fk(...)` names the FK; nested embeds rejected), `order=price.desc,name`, `limit`/`offset`; full CRUD (`POST`/`PATCH`/`DELETE`), `Prefer: return=representation` echoes rows, `Content-Range` on reads. `cs`/`cd` array containment (`tags=cs.{a,b}` → `$all`/`$in`, the Postgres array literal `postgrest-js` `.contains()` emits — quote-aware, so `{"a,b"}` is one element and `{"2024"}` stays a string). Schemaless value coercion (null/bool/int/float/string; `eq."42"` forces string). Guardrails: `OXIDB_PGRST_MAX_ROWS` (default 1000) hard-caps a read; `?db=<name>` targeting inherited (ADR-0012). **Read-side gates (0.39.21, from an anon-key audit):** `POST /api/{col}/aggregate` now consults `read_access` — a pipeline reads the collection, and `$group` cannot be filtered after the fact, so a collection with a row-level read rule is **refused** to untrusted keys rather than answered from rows they may not see (before this, `$group` over a `doc.owner`-scoped collection returned every owner's values to the public key). `_`-prefixed **system collections are closed to untrusted keys** in both `check_access` and `read_access` — skipping the rules there was meant for the server's own bookkeeping, but let any anon key read the request log/slow-query profile and create unlimited `_`-named collections, which are also exempt from the project's collection quota. `GET /api/rules/{col}` is admin-only (the policy is not for the key it constrains). **Read policy now spans every engine (0.39.22):** the rules store is keyed by *name*, so a rule on a SQL table, a time-series measurement or a storage bucket governs reads of it exactly as a collection's does — `read:false` or `auth != null` makes it private. No rule still means readable (as for documents); what changed is that these could not be closed **at all** before. Only the document engine can honour a *row-level* rule, so a `doc.`-referencing rule on the other engines is a refusal rather than a silent no-op. `/api/sql` is gated per **referenced table** (`oxidb_sql::referenced_tables` walks FROM/JOIN, derived tables, CTEs and set operations), so a join, subquery or UNION cannot reach around the rule of any table it touches; an unparseable statement is refused for untrusted callers rather than passed through. **Safety reuses the existing gates**: `rest_permitted` (Read role → GET only) then `rules::check_access` per request (the RLS analog — `read:false` → `403`). **Rate limits in a rule (0.39.24):** a rule may carry `"rate": {"create": "10/min", "delete": "30/hour"}` (units sec/min/hour/day), enforced **per identity** (`auth.username`) per operation per collection — so one account flooding a collection cannot throttle everyone else, which the per-project `max_requests_per_min` would. Checked *after* the expression, so a write the rule refuses never consumes budget; a refused write answers **429 with `Retry-After`** (PostgREST surface) rather than 403, because "no" and "not yet" are different answers. service_role bypasses, as it bypasses rules. Fixed window, in-process (two nodes each allow the limit — the usual trade for not putting a write on every request's hot path); specs are validated at save time so an unparseable limit is an error rather than a rule that silently never applies. **Rule namespaces:** `doc.<field>` is the stored row and `newDoc.<field>` the incoming one; on **create** `doc.` binds to the row being created (there is no stored one), which is what makes `create: auth.username == doc.owner` — "you may only create rows you own" — expressible at all. Before 0.39.19 it denied every insert, and `newDoc.` was rejected by the validator despite the evaluator reading it, so ownership on create could not be written in any form. Native `/api/...` surface untouched. **Phase 2b — SQL engine under the same grammar** (`oxidb-server/src/rest/postgrest_sql.rs`): when `OXIDB_SQL=1` and `{table}` names a SQL table (`sql_bridge::sql_table_exists`), `/rest/v1/{table}` is served by the SQL engine — the same URL grammar → **parameterized SQL** (values always bound `?`, identifiers validated `^[A-Za-z_]\w*$` as the name-injection guard), CRUD → `INSERT`/`UPDATE`/`DELETE`, `{columns,rows}` reshaped to array-of-objects. A collection and a SQL table never collide, so dispatch is unambiguous; SQL-off keeps the document path byte-for-byte. SQL authz is RBAC-only (no per-row rules, like `/api/sql`) — which is exactly why **a write to a SQL table through `/rest/v1` requires a ReadWrite/service_role key** (0.39.20): the gate lets Read/Authenticated writes through so the *document* rules can adjudicate them, and a table has no rules to adjudicate with, so before this a published anon key could insert into and delete from any table. Same fix and reasoning as the tsdb profile. **SQL resource embedding** (Phase 2c) infers the relationship from **catalog foreign keys** (`sql_bridge::sql_foreign_keys`): FK current→target = belongs-to (object), FK target→current = has-many (array), `related!fk(...)` names the column; each embed is one batched `SELECT … WHERE fk IN (…)` stitched in Rust (not a JOIN — exact join columns from the declared FK, no naming-convention guessing). **SQL write-representation**: `Prefer: return=representation` appends `RETURNING *` to the INSERT/UPDATE/DELETE and echoes the affected rows (projected by `?select=`), else minimal (`201 []`/`200 []`/`204`). **TSDB under the same grammar** (`oxidb-server/src/rest/postgrest_tsdb.rs`, Phase 2d): selected by PostgREST's **schema profile** — `Accept-Profile: tsdb` / `Content-Profile: tsdb` (what `postgrest-js` `.schema('tsdb')` emits) routes `/rest/v1/{measurement}` to the time-series engine (profile-routing, not existence-routing, since a measurement only exists after its first write). Read: `select=<field>` (the field), `tag=eq.value` (tag equality), `ts=gte./lt.` (time range `[start,end)`), extension params `agg`/`interval`/`group_by`/`p`; the series result is flattened to `{ts, value, <tags…>}` rows, with `order=ts.*`/`limit` post-flatten. Write: flat `{ts, host:"x", usage:0.5}` → ts/time=timestamp, string→tag, number/bool→field (or nested `{ts,tags,fields}`). PATCH/DELETE → `405` (append-only; use retention). RBAC-only, `OXIDB_TSDB=1` — and because "RBAC-only" means there are no per-row rules to fall back on, **writes under the tsdb profile require a ReadWrite/service_role key**: the browser-safe anon key may read series but never append to them (0.39.17; before that it could, which let a published anon key poison a project's series). **Nested embeds** (`authors(name,books(title,chapters(name)))`) work on both the document and SQL engines — a child's `select` recurses through the same projection path (`project_top`/`project_sql`) at `depth+1`, bounded by `MAX_EMBED_DEPTH` (5). The whole surface (**all three engines**, incl. 2-level nesting) is verified against the real unmodified `@supabase/postgrest-js` client (`tests/postgrest-js-test/`, 26 assertions). ADR-0019's mapped grammar is functionally complete.

**OxiBase control plane (`oxidb-server/src/platform/`, ADR-0020).** A multi-tenant provisioning layer — the Supabase-platform analog on top of the `/rest/v1` data plane. Off unless `OXIDB_PLATFORM=1` **and** `OXIDB_PLATFORM_SECRET` (the platform master secret that signs developer sessions). Route family `/platform/v1/*`: `signup`/`login` (developer accounts, stored in a `_oxibase` system database opened directly outside `DatabaseManager`), `POST/GET/DELETE projects` (a project = one isolated tenant database via `DatabaseManager::create_database`). Each project gets its **own** `jwt_secret`, generated at creation and stored **AES-GCM encrypted** in `_oxibase.projects` (`crypto::EncryptionKey::from_bytes`). **Two-secret boundary (ADR-0021):** `OXIDB_PLATFORM_SECRET` signs developer sessions (control-plane only); `OXIDB_SEAL_KEY` seals/unseals per-project secrets — the data-plane hook `project_secret` unseals with the seal key **alone**, never the session-signing master (falls back to master when `OXIDB_SEAL_KEY` unset, single-binary skeleton). Two API keys per project, minted as JWTs signed with that project secret at a fixed `iat` (deterministic/stable): `anon_key` (role `read`, browser-safe) and `service_role_key` (role `admin`, server-only, bypasses rules). **The one data-plane change:** the REST listener resolves the JWT verification secret **per target database** — a `?db=<ref>` request to an OxiBase project verifies with that project's secret (`platform::project_secret`), everything else with the global `OXIDB_JWT_SECRET`. Isolation modes recorded per project: `shared` (many logical databases in one process, the default and OxiDB's density advantage) vs `dedicated` (a process per tenant, future). Addressing v1 is `<host>/rest/v1?db=<ref>` (works today); per-project subdomains are a v2 behind a wildcard cert. **Hardening:** `POST /platform/v1/projects/{ref}/keys/rotate` re-mints both keys under a fresh project secret so a leaked key dies immediately (keys carry a stored `key_iat` = creation-or-rotation time, kept deterministic); per-project secrets are cached (`secret_cache`) and invalidated on rotate/delete so a revoked secret can never keep verifying; signup is guarded by an 8-char minimum password, a per-actor rate limit (forwarded client IP via `X-Forwarded-For`/`CF-Connecting-IP`, `OXIDB_PLATFORM_SIGNUP_RATE`/min), an optional invite code (`OXIDB_PLATFORM_SIGNUP_CODE` — private signup), and a global account ceiling (`OXIDB_PLATFORM_MAX_ACCOUNTS`); login has a per-email brute-force lockout (5 fails → 5-min 429); projects-per-account is capped (`OXIDB_PLATFORM_MAX_PROJECTS`, default 100). Deployment specifics (hosts/secrets) stay in env, never committed. **Separate-service migration (ADR-0021, landed):** the generic HTTP types + parsing + a thread-pooled `serve` listener + a blocking JSON client are a standalone dependency-free **`oxidb-http`** crate (server's `s3::http` re-exports it). The control plane is now its own lean binary — the **`oxibase`** crate (deps: `oxidb-http` for its listener, `oxidb-client` for the wire, small crypto — **no engine**): it serves `/platform/v1/*` and reaches the data plane over OxiDB's **native OxiWire protocol** (a new standalone **`oxidb-client`** crate: length-prefixed JSON over TCP + client-side SCRAM-SHA-256 + a self-healing connection **`Pool`** with typed errors — `Connect` retryable / `Io` not / `Wire` healthy — so a stale pooled connection re-dials safely; zero engine deps) as an admin client — tenant databases via `create_database`, its own accounts/projects stored in an `oxibase` metadata database. Config: `OXIBASE_UPSTREAM` (`host:port`), optional `OXIBASE_UPSTREAM_USER/_PASSWORD` (SCRAM); the shared secret between the planes is now just `OXIDB_SEAL_KEY` (+SCRAM creds) — no shared JWT. `upstream.rs` isolates the transport, so the earlier REST version was a one-file swap. The data plane keeps **only** the `tenant_auth::project_secret` hook (`oxidb-server/src/tenant_auth.rs`, ~140 lines: reads that shared `oxibase` db locally, unseals with `OXIDB_SEAL_KEY`, short TTL cache since the control plane is out-of-process) and no longer serves `/platform/v1`. Config: `OXIBASE_ADDR`, `OXIBASE_UPSTREAM_URL`, shared `OXIDB_JWT_SECRET` (oxibase's admin token) + `OXIDB_SEAL_KEY`, control-plane-only `OXIDB_PLATFORM_SECRET`. Proven two-process end-to-end (signup → provision → service_role/anon keys work against the data plane's `/rest/v1`). ADR-0021 migration complete. **End-user social sign-in (`oxibase/src/oauth.rs`)**: per-project Google/GitHub OAuth for an app's *own* users — the developer stores the provider's client id + **sealed** secret on the project row (`oauth.{google,github}`, owner-only `GET/PATCH /platform/v1/projects/{ref}/auth/providers`), and users sign in through the authorization-code redirect (`/auth/authorize/{provider}` → provider → `/auth/callback/{provider}`) or, for Google, a browser ID token (`POST /auth/oauth/google`, no secret needed). The session is handed back on a **pre-registered** `redirect_urls` entry in the URL *fragment* (tokens never reach a server log); the allow-list is mandatory and its `*` can only extend a path, never widen a host. State is a stateless HMAC blob (10-min TTL) bound to project+provider, so the callback is CSRF-safe with no server-side session table. Accounts link by **verified** email only (GitHub's primary-verified address, Google's `email_verified`), so password-then-Google lands in one account. `GET /auth/settings` is the public discovery endpoint. **Magic links** (passwordless): `POST /auth/magiclink {email, redirect_to}` mails a 15-minute single-use link, `GET /auth/magiclink/verify?token=` burns it and redirects to the app with a session — the destination is validated and stored *when the mail is sent*, so a tampered link cannot move the session, and re-checked on click so a revoked URL stops working. The click doubles as signup + address verification. `mail.rs` gained a dev/test transport (`OXIBASE_MAIL_SINK` writes messages to a file instead of SMTP) so the whole email surface is testable without a mail server. **Session rotation (0.39.26)**: access tokens are short-lived (`OXIDB_PLATFORM_ACCESS_TTL`, default 1h) and `POST /auth/refresh` **rotates** the refresh token — it revokes the presented one, which is what makes a replayed token detectable. Two consequences were breaking real apps. (a) A client must persist *every* rotation, not just what sign-in returned; `oxibase-js` had no way to say a rotation happened, so an app storing the session in `localStorage` kept the token spent by the first refresh and every reload past the first hour 401'd forever with no recovery but re-login. The SDK now has `auth.onAuthStateChange(cb)` (`signedIn`/`tokenRefreshed`/`signedOut`) — `setSession` deliberately does *not* fire it, so a persist-on-event listener cannot loop. (b) Concurrent requests each 401ing on the same expired access token all POSTed the same refresh token, so one rotated and the rest were told "invalid" — a page whose feed fires 8 queries lost 7 of them. Fixed on both ends: the SDK coalesces refreshes into one in-flight promise and retries (rather than re-refreshes) a request whose token was rotated while it was in flight (a `tokenGen` counter), and the server honours a *just-consumed* token for `REFRESH_GRACE_SECS` (10) — a race is forgiven, a later replay is not. Consumed rows carry `used_at` and are swept, scoped to the user, on their next issued session; every revocation path (password reset/change, user delete) still deletes all of a user's rows, so grace never outlives a revoke. Pinned by `oxibase/test/auth.e2e.mjs` (rotation/grace/replay) and `oxibase-js/test/refresh.mjs` (offline, stub server: coalescing + the stale-persisted-token regression). **Per-project request rate limiting (0.39.16)**: the same model-B split as the size quotas — the value lives on the project row (`max_requests_per_min`, `PATCH /projects/{ref}/limits`, env default `OXIDB_PROJECT_MAX_RPM`), enforcement is in the data plane at the one point a request is attributed to a tenant (`rest/mod.rs`, right after the tenant db resolves), so every surface on that listener (REST, `/api`, storage, SQL) is covered by one check and refused before any work happens: `429` + `Retry-After`. Fixed one-minute window per project in `tenant_auth::rate_limit_hit` (one lock, one counter; refusals do not extend the window; stale windows swept past 4096 tracked projects). **0 = unlimited is the default** — throttling is opt-in, never a surprise an upgrade delivers under load. Remaining OxiBase work is additive: the web dashboard is a static React+TS+Vite SPA (`oxibase-dashboard/`, matching the OxiDB Studio stack; served outside Rust) — v1 has auth + project management (list/create/keys/rotate/delete), with a table/SQL editor over `/rest/v1` next, (B) JWKS/asymmetric verification for multi-node, and anon-with-rules.

**PostgreSQL wire protocol (`oxidb-server/src/pg/`, ADR-0023).** A tenth listener (`OXIDB_PG_PORT`, off by default; needs `OXIDB_SQL=1`) speaks the **PostgreSQL v3 frontend/backend protocol**, so `psql` and `psycopg` connect unmodified — verified against real psql 18 and psycopg 3.3. **Zero OxiWire changes**: it reaches the same per-database engines via `sql_bridge::engine`, the same accounts via `auth`, and the same SCRAM verifiers via `scram` (PostgreSQL wraps SCRAM in a SASL envelope, but the messages inside it are the RFC 5802 ones `ScramState` already parses — the only fix needed was accepting the `y,,` GS2 header alongside `n,,`, and deriving `c=` from it instead of hardcoding `biws`). Modules: `wire` (codec), `auth` (handshake), `session` (state + the one call into the engine), `catalog` (statements that never reach it), `types` (OIDs + value encoding), `errors` (SQLSTATEs). **A portal executes once, at `Describe` or `Execute` — whichever comes first** — because the engine reports a result's shape only by producing it, and answering `Describe(portal)` with `NoData` breaks psycopg (which reads column metadata from exactly there); the only visible difference from PostgreSQL is that an error surfaces one message earlier, still inside the same batch. `SET`/`RESET`/`SHOW`/`DISCARD`/`version()`/`current_database()` are intercepted (the engine's parser rejects `SET`, and every client sends one before it will talk); `\dt` and `\l` are answered from the engine's catalog, and **every other `pg_catalog` query is refused with `0A000` naming what is unsupported** — an empty result would be believed (found for real: answering psql's `\d <table>` probe with the table list made psql fail on a column it expected). Errors map to the SQLSTATEs clients recover on (`23505`/`42P01`/`42703`/`23502`/`42601`/`0A000`/`55P03`/`42501`), and the failed-transaction state is emulated (`'E'` until `ROLLBACK`; `COMMIT` answers `ROLLBACK`) because psycopg's `with conn.transaction():` recovery depends on it. Engine ints are **`int8`, never `int4`** (i64 would truncate). `Role::Read` may only SELECT/SHOW, same gate as the native port. **Doğrulanmış istemciler (gerçek sürücülerle, tahminle değil): psql 18, psycopg 3.3, Npgsql 8.0 (default modda — `NoTypeLoading` flag'i GEREKMİYOR), pgjdbc 42.7** (`DatabaseMetaData` dahil: getTables/getColumns/getPrimaryKeys — composite PK'nın her parçası — /getIndexInfo/getImportedKeys/getTypeInfo/getSchemas, hepsi motorun kendi kataloğundan: `list_tables`/`table_def`/`list_indexes`/`Table::foreign_keys`). Bunu açan iki iş: (a) **karışık batch** — bir simple-query mesajı hem intercept edilen hem motora giden statement taşıyabilir (Npgsql tam olarak `SELECT version();` + type-catalog sorgusunu TEK mesajda yolluyor; eskiden tüm batch motora gidip `version()`'da patlıyordu). `split_statements` tırnak/`''` escape/dollar-quote/`--`/`/* */` farkında, ardışık motor statement'ları tek çağrıda kalıyor. (b) **type catalog cevaplanıyor** — içeriği STATİK (bu sunucunun ürettiği tip listesi, gerçek PG OID'leriyle → sürücünün mevcut handler'ı aynen çalışıyor); composite-field ve enum sorguları **boş** dönüyor, ki bu DOĞRU (composite tip ve enum yok). Tablo-başına introspection hâlâ reddediliyor (statik değil). `pg_type.oid` kolonu `oid` (26), `typtype` `char` (18) olarak declare edilmeli — sürücü `int8`/`text` kabul etmiyor. **Eşleştirme KURALI: sorgunun okuduğu tabloya değil, o çağrıya ÖZGÜ alias'a bak** (`self_referencing_col_name`, `index_qualifier`, `elemtypoid`, `fkcolumn_name`). Geniş eşleştirme geliştirme sırasında `getIndexInfo`'ya **tablo listesini** index kolon adları altında döndürdü — çağıran bunu doğrudan ayırt edemez; `tests/pg_wire.rs` "hiçbir catalog sorgusu başkasının şeklinde cevaplanmaz" özelliğini pinliyor. Kalan eksikler: rastgele catalog sorguları (psql `\d <table>`, pg_dump, BI araçları), `COPY`, `LISTEN`/`NOTIFY`, `DECLARE CURSOR`, cancellation, gerçek şema — hepsi adıyla reddediliyor. **TLS doğrulandı** (`sslmode=require` → TLSv1.3). One small engine addition: `SqlEngine::command_kinds` (`CommandKind`), because `CommandComplete` must name the verb (`INSERT 0 3`) and `QueryResult` says what happened, not which verb asked. Tests: `tests/pg_wire.rs` (27, byte-level, incl. a real SCRAM login with mutual auth) + `tests/pg_e2e.rs` (5, real psycopg).

### Second engine — SQL (`oxidb-sql/`, ADR-0010)
A standalone relational SQL engine (its own crate) can be mounted alongside the document engine in the same server. It owns **entirely separate files** and shares no state — a collection name and a SQL table name never collide. Off by default.
- `OXIDB_SQL` (set to `1`/`true`/`yes`/`on` to enable; default off — zero cost when unused)
- `OXIDB_SQL_DATA` (SQL engine data dir; default `${OXIDB_DATA}/sql`)
- `OXIDB_SQL_DISK_FIRST` (rows served from the mmap'd last-checkpoint `.rdat` snapshot, only post-checkpoint changes in RAM; default off = all rows resident)
- `OXIDB_SQL_CHECKPOINT_BYTES` (auto-checkpoint the SQL WAL past this size; default 64 MiB, `0` = manual only)

Wire routing (`handler.rs`): a request with `engine: "sql"` — or the reserved `sql` command — is served by the SQL engine; a missing/`"doc"` engine keeps the document path byte-for-byte (full backward compatibility). Request shape: `{ "engine": "sql", "cmd": "sql", "sql": "SELECT ...", "params": [ ... ] }` (`params` binds `?`/`$N`). RBAC gates `sql` at the `ReadWrite` role. SQL supports DDL, DML, single-table + INNER/LEFT/RIGHT/FULL-join SELECT with GROUP BY/HAVING aggregates, secondary indexes, parameterized queries, and per-engine transactions (`BEGIN`/`COMMIT`/`ROLLBACK`). **Concurrent writers vs. a buffered transaction (0.40.2, was a silent lost write):** a transaction reserves its row ids and `AUTO_INCREMENT` values *from the engine* as it buffers each write (`SqlEngine::reserve_row_ids` / `next_auto_block`) instead of peeking the counter and allocating locally — the old peek handed the same id to any concurrent writer (another transaction **or a plain autocommit INSERT**) and the commit then overwrote their row, no error anywhere. Reservation makes rollback leave a gap, as sequences do everywhere. Because distinct ids alone would turn that lost row into two rows sharing one key, `commit_batch_checked` re-validates every PK/UNIQUE constraint against committed state under the commit lock (`BatchSim` simulates the ops in order, so a key the batch itself frees stays reusable) and refuses the commit if a key was taken meanwhile. The replication apply path (`commit_batch`) deliberately does **not** re-check — the cluster already agreed, and a node that second-guesses diverges — so the re-check is single-node; `tests/t_concurrent_writers.rs` (10 tests, all proven red first). **Cluster:** SQL writes ARE Raft-replicated — `sql_is_write` (`async_server.rs`) classifies a statement by parsing it (`oxidb_sql::is_read_only`), and a write replicates as `OxiDbRequest::Sql` (`Scoped` per database); SELECT-only SQL, and SQL that fails to parse, runs node-locally. **Not sharded:** oxipool shards by `collection` + a shard key, which a `sql` request has none of, so SQL is never scattered across shards — it routes to one backend (a replica when read-only, else the master). Stored procedures come in two languages (ADR-0014): SQL-text bodies (`CREATE PROCEDURE ... AS BEGIN dml; END` — zero-toolchain, re-parsed per CALL) and compiled **Cobra** bytecode (`CREATE PROCEDURE ... LANGUAGE COBRA AS '<base64 .cobrac>'`) executed by the `oxidb-cobra/` VM crate: the file defines `def run(db, ...params)`, `db.query`/`db.execute` join the CALL's transaction, print → notices, 100M-instruction fuel cap, determinism validated at CREATE (async/import/IO rejected) so CALL replicates safely.

**Persistence & crash-atomic checkpoints (`storage.rs`, `wal.rs`, `catalog.rs`, `manifest.rs`).** Each checkpoint writes a whole new **generation** into its own `gen.<N>/` subdirectory (`catalog.json` + one `<table>.rdat` row snapshot each), fsyncs it, then promotes it by renaming a tiny `MANIFEST` file (`{generation, wal_seq}`) into place — **the single atomic commit point** (`manifest.rs`). A crash anywhere before that rename leaves the previous `MANIFEST`, and thus the previous intact generation, in force; a half-written generation is ignored at open and swept. Because catalog and snapshots switch together, their arities can never disagree after a crash (the failure mode the old flat overwrite-in-place layout had). The WAL stays a **single file** (`wal/live.wal`, CRC'd, seq-numbered): the manifest records the highest seq folded into the snapshots, and recovery replays only records past that watermark (`Wal::open_since`), so a not-yet-truncated WAL never double-applies a checkpointed (non-idempotent) ALTER; truncation is best-effort. **Sequences live in a separate `sequences.json`** (direct-saved on every `NEXT VALUE FOR` — far more often than a checkpoint, and arity-independent), never inside the generationed catalog. Legacy flat-layout databases (root `catalog.json` + `<table>.rdat`, no `MANIFEST`) open as generation 0 and migrate to `gen.1/` at their first checkpoint. `OXIDB_SQL_DISK_FIRST` mmaps the committed generation's `.rdat` as the read base. **Engine-aware backup/restore**: `SqlEngine::backup(out)` is **low-lock** — it holds the engine lock only for two O(1) phases (pin a committed generation + read the WAL length; then unpin) and runs the slow `.tar.gz` compression with the lock released, so concurrent queries/writes are not blocked. A pinned generation is safe from GC and freezes WAL truncation, so the archive (a synthesized `MANIFEST` → the pinned `gen.<N>/` + a stable WAL prefix + `sequences.json`) is crash-consistent as of the pin instant even while writes and auto-checkpoints continue. `SqlEngine::restore(archive, target)` extracts into an empty dir. `Tsdb` (`oxidb-tsdb`) has the same **low-lock** `backup`/`restore`, split into `backup_begin` (pin a generation under the write lock) / `backup_write` (compress, no lock) / `backup_end` (unpin) — the per-generation `blocks.<N>.tsb`/`wal.<N>.log` files are pinned against a checkpoint's GC, so writes and auto-checkpoints continue during the archive; `tsdb_bridge.rs` orchestrates the three phases. Both are admin-only over the wire (`{engine:"sql"|"tsdb", cmd:"backup", path}` / `{cmd:"restore", archive, target}`, `sql_bridge.rs`/`tsdb_bridge.rs`) — separate from the document engine's `backup()`/PITR, which snapshots only the document data dir.

**Instant (metadata-only) `ALTER TABLE ADD/DROP COLUMN` (`rows.rs`, ADR-0013 Phase D).** Both are **O(1)** — no row rewrite, no checkpoint — answering the "add/drop a column on a 500M-row live table with zero downtime" problem. The catalog stores the **physical** schema; `table_def` returns a **logical** view so the executor (whose scope is positional, `cols[i]↔cells[i]`) is untouched and never sees a dropped column. ADD appends a slot (old rows read back padded with the new column's default); DROP tombstones a column in place via a `Column.dropped` flag (Postgres `attisdropped`-style — the physical cell stays, projected out on read). `RowStore` projects physical→logical on read and exposes raw physical rows for index/snapshot work; writes expand logical→physical (`TableState::prepare_write`/`to_physical`, dropped slots = NULL placeholder); transactions read logical but log physical, translating a shifted UNIQUE position via `table_layout`. Durability rides on the WAL record alone (checkpoint skipped). A later checkpoint **compacts**: `RowStore::compact()` rewrites rows to the live columns and the tombstones are dropped from the catalog, reclaiming the space — the deferred O(n) rewrite folded into a checkpoint that rewrites every row anyway. `RENAME COLUMN` still rewrites/checkpoints eagerly. **`ALTER COLUMN <c> TYPE <ty>`** (PG `[SET DATA] TYPE`, MySQL `MODIFY COLUMN`) casts existing cells eagerly via the executor's CAST semantics (`RowStore::rewrite_slot`): a dry-run over all rows first — any uncastable value or over-length `VARCHAR(n)` aborts before the WAL append — then WAL + in-place rewrite + index rebuild + eager checkpoint; narrow (pre-ADD) rows are covered by casting the column default the fill template regenerates from. PRIMARY KEY / AUTO_INCREMENT / UNIQUE / FK-bound columns are rejected (a cast can collide previously-distinct key values).

SQL analytics surface additions: `DISTINCT ON` (argmax), `mode() WITHIN GROUP` (ordered-set aggregate), `WITH`/CTE incl. **`WITH RECURSIVE`** (non-recursive CTEs parse-time desugared to derived tables, column-alias lists `c(a, b)` supported; a self-referencing CTE must be `anchor UNION [ALL] step` and is materialized by fixpoint iteration in the executor — step re-runs with the CTE bound to the previous iteration's rows as a VALUES-derived table, UNION dedups against everything seen so cycles terminate, guards at 1M iterations / 10M rows; `src/executor.rs` `materialize_recursive_ctes`, wired at `resolve_query`), `LEAST`/`GREATEST`, set operations `UNION`/`EXCEPT`/`INTERSECT` (each with `ALL` bag semantics; standard precedence — INTERSECT binds tighter), FROM-less `SELECT` (`SELECT 1` — one implicit zero-column row; WHERE/aggregates/set-op arms all work), aggregate `DISTINCT` (`COUNT/SUM/AVG(DISTINCT x)`), `CROSS JOIN` (desugars to INNER ON TRUE), and **LATERAL joins** (`[LEFT] JOIN LATERAL (SELECT ...) x ON ...` — left-referencing derived tables re-executed per left row via the correlated-subquery machinery; RIGHT/FULL LATERAL rejected). Date/time: `NOW()`/`CURRENT_TIMESTAMP`, `EXTRACT(part FROM ts)` + `date_part('part', ts)`, `date_trunc('part', ts)` (UTC calendar math, ISO weeks, PG DOW numbering), `INTERVAL` literals folded to ms integers (fixed units only — month/year rejected), timestamp ± ms(/double) arithmetic, `ts - ts` → ms. Scalars: `FLOOR`/`CEILING` (exact for DECIMAL), `POWER`, `SQRT`, `%`/`MOD`, `POSITION`/`STRPOS`, `LPAD`/`RPAD`. Also: `add_months(ts, n)` (calendar-correct, day clamps — serves EF `AddMonths`/`AddYears`), `UPDATE/DELETE ... AS alias` (EF `ExecuteUpdate`/`ExecuteDelete`), and correlated references that sit inside derived tables (EF's LIMIT'd collection projections) — `extract_outer_body` descends into FROM/JOIN subqueries. The EF Core provider translates `DateTime` members (incl. `DayOfWeek`)/`AddX` methods, `Math.*`, `IndexOf`/`PadLeft/Right`/`Contains(char)`, renders EF's CROSS/OUTER APPLY as `[LEFT] JOIN LATERAL`, has **full migrations support** (`Database.Migrate()` with a real `__EFMigrationsHistory`, Add/Drop/Rename column, Create/Drop index — ALTER-class DDL runs with `suppressTransaction` since the engine forbids it in transactions; `OxiDb:AutoIncrement` column annotation via `OxiDbAnnotationProvider`) and **design-time scaffolding** (`dotnet ef dbcontext scaffold` — `OxiDbDesignTime.cs`: `IDatabaseModelFactory` over SHOW TABLES/DESCRIBE/SHOW INDEXES). EF test suites: `tests/efcore-oxidb-test` (e2e), `tests/efcore-migrations-test`, `tests/efcore-scaffold-test`, `tests/efcore-conformance-test` (51-query LINQ matrix), and **`tests/efcore-spec-tests` — the official EF Core relational specification tests** (`OxiDbTestStore`/factory over the wire; all 12 Northwind suites incl. Include/Navigations/KeylessEntities/DbFunctions, **3832/3832 green**; known limits are explicit overrides in the test classes, SQLite-parity where applicable). Engine additions driven by the spec run: `VALUES` table constructor (+`AS alias(c1,…)` column renames — EF's local-`Contains` shape), full float math (`sin cos tan asin acos atan atan2 exp ln log10 log(base,x) degrees radians sign trunc`), `regexp_like` (Rust regex), **ASCII case-insensitive LIKE** (SQLite-style), **`COLLATE "NOCASE"/"BINARY"`** (NOCASE = case fold), 2-arg TRIM/LTRIM/RTRIM (char-set), `text + text` concat, `^`/`&`/`|` (int bitwise, bool logical), **composite PRIMARY KEY** (`CONSTRAINT pk PRIMARY KEY (a, b)` — the key map is a tuple map (`Vec<IndexKey> -> row_id`) so simple and composite keys take one code path; every member column carries the `primary_key` flag and is implicitly NOT NULL, and `Table::pk_cols()` derives the key from those flags in column order, so old catalogs/WAL records need no migration and a table created before 0.40.1 keeps its old unenforced semantics; enforced on INSERT/multi-row INSERT/UPDATE and inside transactions (`transaction.rs` `UniqueMap` probes the engine's map via `pk_owner`), seeded on both the resident and disk-first open paths, and served by the full-key `index_lookup_eq` fast path — a partial key falls back to a scan. A single-column FK cannot reference a composite-PK parent (refused, not mis-enforced); table-level composite UNIQUE is still parsed-and-ignored. `tests/t_composite_pk.rs`), **single-column FOREIGN KEY enforcement** (child INSERT/UPDATE must find the referenced parent row — NULL FK references nothing; parent DELETE honours `ON DELETE` NO ACTION/RESTRICT/CASCADE/SET NULL; changing a referenced parent key is RESTRICTed; composite (multi-column) FKs and `ON UPDATE` cascade/set-null are parsed-and-ignored — `oxidb-sql/src/executor.rs` `check_fk_children`/`enforce_fk_on_delete`, `tests/t_foreign_keys.rs`), `UPDATE/DELETE ... AS alias`, correlated subqueries **inside aggregate arguments and grouped queries** (group-key correlation), `EXISTS` over aggregated subqueries (derived-table wrap), **multi-level correlation** (outer refs through any depth of nested subqueries/derived tables/VALUES; scope chains shadow correctly; deferred materialization for synthetic-param subqueries), bool literals must be TRUE/FALSE (provider `OxiDbBoolTypeMapping` — `1`/`0` is not a boolean to the engine). `OxiDb.Data` treats `DateTimeKind.Unspecified` as UTC (epoch-ms store). Index usage: PRIMARY KEY point lookups and in-transaction reads consult indexes; **index-nested-loop join** (small outer ⋈ indexed base table) prunes the scan.

### Third engine — TSDB (`oxidb-tsdb/`)
A standalone time-series engine (InfluxDB-style), mounted like SQL. Off by default. Storage differentiator: each series (measurement × tag-set × field) is a **Gorilla-compressed** columnar stream (delta-of-delta timestamps + XOR floats; ~0.3 bytes/point on regular data), partitioned into sealed blocks so retention drops whole expired blocks.
- `OXIDB_TSDB` (`1`/`true`/`yes`/`on` to enable; default off — zero cost when unused). Per-database, like SQL.
- `OXIDB_TSDB_DATA` (default `${OXIDB_DATA}/tsdb` for the default db; named dbs at `${OXIDB_DATA}/<name>/tsdb`).

Persistence (`persist.rs`): a **versioned block snapshot + per-generation WAL**, with a `MANIFEST` as the atomic commit point (`blocks.<N>.tsb`, `wal.<N>.log`, `MANIFEST`). Every point is WAL-appended; a checkpoint seals active buffers, writes a fresh `blocks.<N+1>.tsb` snapshot (+fsync), atomically replaces the MANIFEST (temp+rename), then rotates the WAL. Recovery reads the MANIFEST's generation → snapshot + its WAL, so a crash on either side of the rename never double-counts; retention is durable (dropped blocks just aren't in the next snapshot). Auto-checkpoint past 8 MiB of WAL.

Fields are typed (float/**integer**/**boolean**/**string**); numeric values are stored as `f64` (ints exact to 2^53, bools 0/1), text in a separate `(ts, string)` path; the type is remembered per series and reported in query results. Numeric aggregations: mean/sum/min/max/count/first/last/**distinct** plus **`rate`** (per-second change, for counters) and **`percentile`** (`agg:"percentile"`+`p`, or shorthand `p95`; linear interpolation). Text-field aggregations: first/last/count/distinct.

**Continuous-aggregate rollups**: `add_rollup(measurement, interval, aggs)` materializes completed time buckets of every numeric series of a measurement into a derived measurement `<m>@<label>` with fields `<field>_<agg>` (e.g. `cpu@1m` `usage_mean`). Incremental via a persisted per-series watermark (crash-safe, no double-count on restart); the rule set persists in `rollups.json`. `refresh_rollups(now)` processes only fully-closed buckets. Roll from raw (1s→1m, 1s→1h); chaining is a caller concern.

Wire routing (`tsdb_bridge.rs`): `engine: "tsdb"` (or reserved `tsdb` command), `cmd: "tsdb"` with an `op`: `write` (points: measurement/tags/fields/ts — JSON bool→boolean, integer→integer, else float), **`write_lp`** (InfluxDB line protocol in an `lp` string; ms timestamps, `now()` when absent — `line_protocol.rs`), `query` (measurement + field + tag filters + `[start,end)` + optional `GROUP BY time(interval)` downsample + `group_by` tags + `agg`), `stats`, `retention` (cutoff), `checkpoint`, `rollup_add`/`rollup_refresh`/`rollups`. RBAC gates `tsdb` at `ReadWrite`; Read role is query-only. Node-local.
