# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OxiDB is a fast, embeddable document database engine written in Rust. It supports both SQL and JSON-based queries. It can run as an embedded library, a standalone TCP server, or be accessed via client libraries (Python, Go, Julia, .NET, Swift/iOS via C FFI).

## Build Commands

```bash
cargo build --release                    # Build core library
cargo build --release -p oxidb-server    # Build TCP server
cargo build --release -p oxidb-client-ffi # Build C FFI shared library (.dylib/.so/.dll)
cargo build --workspace --features ocr   # Build with OCR support
```

## Testing

```bash
cargo test                               # All tests (workspace)
cargo test -p oxidb                      # Core library tests only
cargo test -p oxidb-server               # Server tests only
cargo test <test_name>                   # Single test by name
cargo test -- --nocapture                # With stdout output
```

Unit tests are inline (`#[cfg(test)]` modules in source files). Integration tests for the server are in `oxidb-server/tests/` (ACID and security tests).

## Architecture

### Core Engine (`src/engine.rs`)
`OxiDb` owns a `RwLock<HashMap<name, Arc<RwLock<Collection>>>>`. Per-collection locking enables concurrent reads. Collections are auto-created on first insert.

### Multiple Databases (`src/database_manager.rs`, ADR-0012)
`DatabaseManager` hosts many isolated `OxiDb` instances, one per subdirectory of `OXIDB_DATA`: default database `oxidb` (alias `postgres`), server-global `_auth`/`_audit` at the top level, flat legacy layouts auto-migrated into `oxidb/` on open (never overwriting). Wire: optional `db` field per request, `use_db` sets the session default, plus `create_database`/`drop_database`/`list_databases` — and the SQL-text equivalents `CREATE/DROP DATABASE`, `SHOW DATABASES`, `USE` (both surfaces parse into one `DbIntent` in `oxidb-server/src/db_admin.rs`; create/drop are Admin-only). RBAC supports per-database roles (`db_roles`, `grant_db_role`/`revoke_db_role`). The SQL engine is per-database too: default db at `OXIDB_SQL_DATA` (`${OXIDB_DATA}/sql`), others at `${OXIDB_DATA}/<name>/sql` (`sql_bridge` registry). Cluster mode replicates database DDL and scopes writes via `OxiDbRequest::Scoped`; TTL/alert threads run per database; REST takes `?db=<name>`, WS a per-message `"db"` field; transactions are bound to the database they began on. OxiMem keyspace and S3 buckets are intentionally global.

### Collection (`src/collection.rs`)
Each collection owns:
- **Storage** (`storage.rs`) — append-only file with `[status:u8][length:u32 LE][payload]` records; soft-delete flips status byte in-place
- **WAL** (`wal.rs`) — write-ahead log with CRC32 checksums; entries tagged with transaction IDs; 3-fsync protocol (WAL → data → checkpoint)
- **In-memory document cache** — `HashMap<DocumentId, Arc<Value>>` (JSON deserialized once, then refcounted)
- **Field indexes** — `BTreeMap<IndexValue, BTreeSet<DocumentId>>` per indexed field
- **Composite indexes** — multi-field B-tree for prefix scans
- **Version map** — per-document version counters for OCC

### Query Engine (`src/query.rs`, `src/pipeline.rs`)
Query AST with field conditions and logical operators ($and, $or, $nor). Operators: $eq, $ne, $gt/$gte/$lt/$lte, $in, $nin, $exists, $regex, $elemMatch, $not, $all, $size, $type, $mod. Top-level $expr for cross-field comparisons. Key optimizations:
- Index-backed sort: BTreeMap iteration is O(limit) instead of O(n log n)
- Index-only count: returns set size without touching documents
- Early termination: `update_one`/`delete_one` stop after first match

Aggregation pipeline: $match, $group, $sort, $skip, $limit, $project, $count, $unwind, $addFields, $lookup, $facet, $setWindowFields (window functions — document `{documents: [lo,hi]}` AND value/time `{range: [lo,hi], unit?}` frames), $dateHistogram (time-bucketed group + empty-bucket fill), $ohlcv (tick→candle OHLCV with symbol partitioning and LOCF gap fill), $densify (gap-generating docs on a numeric/date axis; fixed units only), $fill (locf / linear / constant null-filling per partition).

### Updates (`src/update.rs`)
Field operators ($set, $unset, $inc, $mul, $min, $max, $rename, $currentDate) and array operators ($push, $pull, $addToSet, $pop). Supports dot-notation for nested fields.

### Indexes (`src/index.rs`, `src/value.rs`)
`IndexValue` enforces cross-type ordering: Null < Bool < Num < DateTime < String. Dates are auto-detected from ISO 8601/RFC 3339/YYYY-MM-DD strings and stored as epoch ms.

### Transactions (`src/transaction.rs`, `src/tx_log.rs`)
OCC with 3-phase commit: prepare → validate versions → commit. Writes are buffered until commit. Deadlock-free via sorted collection locking (BTreeSet). Recovery uses transaction log + WAL replay on startup.

Isolation: backward-validating OCC over item read-sets — committed transactions are serializable w.r.t. the items they read/wrote; phantoms and torn reads for non-tx observers are admitted for plain `find`/`count`. The exact guarantee, anomaly scorecard, and application rules live in `docs/isolation.md`, pinned by `tests/isolation_characterization.rs`.

### Read snapshots — MVCC-lite (`src/snapshot.rs`, ADR-0017)
Read-path-only snapshot visibility; the write path (OCC, `find_for_update`, group commit) is untouched. `aggregate` is snapshot-consistent by default: optimistic latest-state run, proven valid when no write raced it (`SnapGate::changed_since`), else an always-correct resolve-and-recheck fallback — a concurrent aggregation can never see half a transfer. Explicit API `begin_snapshot`/`snapshot_find`/`snapshot_count`/`snapshot_aggregate`/`end_snapshot` (wire: `snapshot_begin`…`snapshot_end`, Read-role tier; the snapshot id is a token, not session state). Mechanics: a snapshot begins under `commit_lock.write()`; every writer records displaced prior bytes into the gate under its `commit_lock.read()` scope (storage layer, `btree_storage.rs`) — that RwLock is the visibility boundary. No snapshot open (the default) costs one relaxed atomic load per write; the version map exists only while a snapshot is open and prunes to the oldest live one. `OXIDB_SNAPSHOT_MAX_SECS` (default 300) hard-expires snapshots — dead-snapshot reads fail with `SnapshotExpired`, writers never wait. Pinned by `tests/snapshot_reads.rs` (torn-sum test proven red pre-feature).

### Full-Text Search (`src/fts.rs`)
Background worker thread receives indexing jobs via `sync_channel(256)`. Supports HTML, XML, JSON, PDF, DOCX, XLSX, images (OCR with `ocr` feature). BM25 ranking. Persisted as `_fts/index.json` (blob index; collection indexes rebuild from a scan at open). **FTS memory (0.42.13, from a production OOM — measured at 1M docs by `examples/fts_mem_bench.rs`, counting allocator):** the collection inverted index is fully RAM-resident and was **1 GB per 1M documents against 38 MB for the documents themselves** (disk-first), ~8x the raw text; a search's transient was unbounded by `limit` — term-at-a-time BM25 accumulates a score entry per doc matching *any* query term before truncation, measured 25 MB per common-term query (500k matches) and 51 MB for two common terms, **multiplied by concurrent searches**. Two fixes: (a) `doc_terms` (per-doc distinct-term list, kept for O(doc-terms) removal) now **interns `Arc<str>` shared with the postings keys** instead of owning a `String` copy per (doc × term) — that copy alone was 558 MB/55% of the index (measured by a temporary no-insert build); interning recovered 230 MB (1015→785 MB — the rest of the 558 is the per-doc `Vec` + map overhead, which only deriving terms at removal would reclaim, deferred); also fixed: `clear()` never dropped `doc_terms` (compaction-rebuild leak). (b) **distinct-doc scoring cap** (`OXIDB_FTS_SCORE_CAP`, default 200k, `0`=unbounded): query terms are processed **rarest-first** and, at the cap, already-admitted docs keep accumulating while new ones are refused — so what the cap cuts is the tail of the least informative posting list, never a rare-term match (the ordering is pinned by an adversarial fixture that indexes the rare doc *last*, red when the sort is removed). Not a term-skip on purpose: a query made only of common terms must still answer. Search transient 25.5/51 → **7.3 MB flat**, and it no longer grows with the corpus; both engines' searches (`CollectionTextIndex` + blob `FtsIndex`) capped. **(c) The collection text index is disk-backed in disk-first mode (`.mtidx`, `src/mmap_text_index.rs`)** — it was the one index type with no disk form. The `.mfidx` model applied to postings: an immutable mmap'd base (header + doc table `id→dl` + postings blob + term table + string blob; postings *before* the term table so a persist streams term-by-term with nothing document-proportional buffered), a RAM overlay (the existing resident structure — `CollectionTextIndex` keeps the single scoring implementation) for docs written since the last persist, and a **dead-doc set** because the removal unit is the document, not the (term,id) pair: the base is never edited, search skips dead ids (Lucene's deleted-docs bitmap), the next persist folds them away. Persist is skip-clean (idle tick free), streams a merge-join (base terms are file-sorted, overlay vocabulary sorted once), publishes via temp+rename, and **replaces** the overlay maps rather than `.clear()`ing them — clear keeps bucket capacity, and the empty skeletons alone measured ~180 MB after a 1M-doc fold. Builds and the crash-recovery rebuild fold every 200k docs, bounding the build peak. Open mmaps the file — **no more full-scan rebuild at every start**; a missing/torn/`needs_reindex` open falls back to rebuild+persist (the `.mfidx` shape), and in-RAM mode is unchanged. Search tie-breaks equal scores by doc id (was map iteration order — nondeterministic, broke pagination, and made the disk/resident differential test fail legitimately). Known approximation, documented: a term's df counts dead base docs until the next persist (Lucene's docFreq does the same until a merge). **Result at 1M docs: resident index 785 MB → 0** (37.8 MB total = the documents alone), build peak 882→265 MB, open scan gone; common-term search 24→35 ms (per-posting `dl` binary search on the doc table — a sorted-merge would make it sequential, future work). Pinned by `mmap_text_index` unit tests (roundtrip, torn-file refusal, incomplete-write refusal), a resident-vs-disk **differential** (same ops, persists interleaved; identical membership mid-window, identical scores after persist), reopen-without-rebuild + mutations-across-the-base, skip-clean, and `tests/fts_disk_index.rs` end-to-end through the engine (restart survival, update/delete voiding base postings, drop removing the file). **(d) The blob/bucket search index is disk-backed too (`_fts/index.mtidx`, `OXTB` variant in `mmap_text_index.rs`)** — same base+overlay+dead model with two domain differences: docs are named `(bucket, key)` so the doc table indexes a names blob and postings reference doc **ordinals** (u32 — 8 B/entry, and the search's score map is ordinal-keyed, never a String per scored posting); each doc carries `text_bytes`, and the `(bucket, key)`-sorted doc table makes `bucket_text_size` (tenant FTS quota) a binary-searched contiguous range walk instead of a full-map scan. `positions` (4 B per token *occurrence*, resident, read by nothing) is gone from the format entirely. **`index.json` is dead**: a legacy file is loaded once at open, backfilled (`total_term_count`), folded to `.mtidx` and removed — old files with `positions` still parse (serde ignores unknown fields), pinned by a hand-written-legacy-JSON migration test; the old persist serialized the WHOLE index into one JSON buffer per flush tick. `flush()`/batched semantics unchanged (the engine's flusher thread now folds the overlay instead). Persist streams the same merge-join with an ordinal remap table (4 B × base docs, the one transient). Pinned by `blob_disk_mode_folds_and_reopens` (fold → bucket-filtered search → mutate across base → quota stable across a fold → reopen). **(e) The last three FTS memory levers, closed (0.42.13):** `FtsJob` no longer carries the object's bytes — a 256-deep queue per worker pinned queue-depth × blob-size during an upload burst; the worker re-reads from the (now `Arc`'d) blob store, bounded by workers × one blob, and an object deleted between queueing and processing skips cleanly while an overwritten one indexes the newer bytes (idempotent — the newer put's own job re-indexes; pinned by `tests/fts_blob_worker.rs`, incl. a put-then-immediate-delete that must not wedge the worker). Extraction is capped at one choke point (`OXIDB_FTS_MAX_EXTRACT_BYTES`, default 4 MiB, `0`=off): zip-based formats (DOCX/XLSX) stop *pulling* at the cap via `Read::take` so a decompression bomb is never inflated (pinned by a test that zips megabytes of repeated text and asserts the output honours the cap), plain formats truncate at a char boundary; PDF is truncated after `pdf_extract` returns — its internal memory is not boundable from outside, the honest limit of the cap. Highlighting scans a bounded prefix (`OXIDB_FTS_MAX_HIGHLIGHT_BYTES`, default 256 KiB): a match past the window yields no snippet, the result row is unaffected — megabyte fields no longer cost result × field size per highlighted search.

### Blob Storage (`src/blob.rs`)
S3-style bucket interface. Objects stored as `_blobs/<bucket>/<id>.data` + `<id>.meta`. ETags are the first 16 bytes of the payload's SHA-256, hex-encoded (not S3's MD5). A full S3-compatible HTTP API (`OXIDB_S3_PORT`) covers Put/Get/Head/Delete/Copy, ListObjectsV2 (prefix/delimiter/continuation), multipart upload, Range + If-[None-]Match, object tagging, `Expiration/Days` lifecycle, SSE-S3/SSE-C, and SigV4 auth (headers + presigned URLs) — so `aws-cli`, `boto3` and the MinIO SDKs work unmodified. No versioning/ACL/S3-Select; path-style addressing only.

### Encryption (`src/crypto.rs`)
Transparent AES-GCM encryption at the storage layer. Optional—enabled by passing an encryption key to the engine.

### Point-In-Time Recovery (`src/pitr.rs`, `src/archive.rs`)
Opt-in via `OXIDB_PITR`. `ArchiveSequencer` (`pitr.rs`) hands every durable WAL write a global, monotonic, wall-clock-stamped GSN (persisted in leases via `_gsn`); WAL records carry it in the **v2** record format (`wal.rs`). The WAL rotates: `Wal::seal()` atomically renames the live `.wal` to a numbered sealed segment under the WAL lock. A background archiver (`archive.rs`, spawned by the engine) copies sealed segments into `_archive/segments/*.seg` (verbatim bytes + trailer) with a self-healing `manifest.json`. `backup()` embeds a `base.meta` GSN watermark. `OxiDb::restore_to_point` extracts a base backup then `archive::replay_into` advances it to a `Gsn`/`Timestamp`/`Latest` target with transactionally-consistent cuts. Off = zero cost.

### Server Protocol (`oxidb-server/`)
Length-prefixed JSON over TCP (max 16 MiB). Auth via SCRAM-SHA-256. RBAC roles: Admin, ReadWrite, Read. Configurable via env vars:
- `OXIDB_ADDR` (default `127.0.0.1:4444`)
- `OXIDB_DATA` (default `./oxidb_data`)
- `OXIDB_DISK_FIRST` (default ON since 0.38-line: document bodies live in an mmap'd `.bdat` with only a ~24 B/doc offset index resident; `0` restores the always-resident `.btree` mode. Existing collections keep their created format — `.bopts`/on-disk format is authoritative over the env). Since 0.38.10 the `.bdat` is **uncompressed by default** (per-record zstd cost scans/aggregations 4-8x); `OXIDB_DISK_COMPRESSED=1` opts back into zstd. Composite indexes are disk-backed too (`.mcidx`, 0.38.9), and full-collection `$group` aggregations covered by a composite index are answered without reading documents (0.38.3-7).
- `OXIDB_DOC` (default **ON** — the only engine switch that is; `0`/`false`/`no`/`off` runs the server **without the document engine**: no document data dir, no TTL/alert/scheduler threads, document commands refused by name (`ping` still answers). Idle server 9.8 MB RSS / 8 threads vs 14.2 MB / 23. Refuses to start with neither `OXIDB_SQL=1` nor `OXIDB_TSDB=1` (nothing to serve), with any document-backed listener configured (REST/WS/S3/MQTT/AMQP/GELF/MsgPack/OxiMem — named individually with the reason), or in cluster mode. `OXIDB_ADDR` and `OXIDB_PG_PORT` both work without it. `doc_engine.rs`, `tests/doc_disabled.rs`)
- `OXIDB_POOL_SIZE` (default 4 worker threads)
- `OXIDB_IDLE_TIMEOUT` (default 0 = never; set seconds to drop idle connections — was 30s until 0.42.12)
- `OXIDB_TX_MAX_IDLE_SECS` (default 300, `0` = never): idle-expiry for interactive transactions, **one knob for both engines**. Document engine: a transaction whose owner goes quiet past this is rolled back by the *engine* — buffered state dropped, `find_for_update` locks released; later touches (including commit) answer `TransactionExpired`, not `TransactionNotFound`; checked lazily on every tx op, swept on each `begin_transaction` and by the TTL thread; `OxiDb::set_tx_max_idle_ms` is the programmatic override; pinned by `tests/tx_timeout.rs`. SQL engine: a *parked* session transaction (ADR-0013 Phase B — it sits in `session_txns` between calls, so parked = idle by definition; the clock resets at every park) expires the same way — buffered writes discarded, `SELECT ... FOR UPDATE` row locks released, `SqlError::TxnExpired` (PG wire: SQLSTATE `25P03`, PostgreSQL's `idle_in_transaction_session_timeout`); on resume failure the engine clears the session's tx id so the recovery `ROLLBACK` doesn't loop on the same error; swept on every session execute plus a 10 s server thread (`sql_bridge::spawn_txn_sweeper`) for the zero-traffic case; `SqlEngine::set_txn_max_idle_ms`; pinned by `oxidb-sql/tests/t_txn_idle_expiry.rs`. Backstop for the client that vanishes while its connection stays open (keep-alives, `OXIDB_IDLE_TIMEOUT=0`) or an embedded caller leaking a tx id — disconnects still roll back immediately in the session layer.
- `OXIDB_READY_FILE` (optional; written **atomically once every standalone listener is bound** — lines `name=value` with the **actual** bound addresses, so `OXIDB_ADDR=127.0.0.1:0` and `OXIDB_PG_PORT=auto` (kernel-assigned) are discoverable without probing. postmaster.pid's job in PostgreSQL. This is how test harnesses spawn servers race-free: the old pick-a-free-port-then-release scheme collided across the 9 test binaries that each boot real servers in parallel, and a connect-poll cannot tell "my server is up" from "another test's server owns that stolen port" — which produced both observed `pg_wire` flakes: 20 s "port never opened" against a dead child, and mid-test "connection reset by peer" when the *other* test's Guard killed the server both were talking to. **Every server-spawning test file is converted** — pg_wire/pg_e2e (10/10 stable, uniform ~2 s), mqtt_wire/mqtt_qos2/mqtt_durable_crash/mqtt_persistent_session, amqp_e2e, s3_wire/s3_etag, oximem_tx_wire, sql_backup_stress, p99_soak; `auto` exists for `OXIDB_PG_PORT`/`OXIDB_MQTT_PORT`/`OXIDB_AMQP_PORT`/`OXIDB_S3_PORT`/`OXIDB_OXIMEM_PORT` and the ready file reports each (`pg=`/`mqtt=`/`amqp=`/`s3=`/`oximem=` + `addr=`). No `free_port`/`test_port` remains anywhere in `oxidb-server/tests/`; crash-restart tests delete the previous ready file before respawning and re-read the new port. The full suite went from failing roughly every other run (a different file each time — the last was `oximem_tx_wire`, which self-identified during this conversion) to 3/3 clean.)
- `OXIDB_AUDIT` (default off; set to `true`/`1` to enable audit log)
- `OXIDB_AUDIT_MAX_BYTES` (optional; rotates audit log when live file reaches this many bytes)
- `OXIDB_AUDIT_MAX_AGE_SECS` (optional; rotates after this many elapsed seconds since file became active)
- `OXIDB_AUDIT_CALENDAR` (optional; `hourly` / `daily` / `none` — UTC calendar boundary)
- `OXIDB_AUDIT_COMPRESS` (optional; `true`/`1`/`yes`/`on` to gzip rotated audit files; default off)
- `OXIDB_SLOW_QUERY_MS` (optional; record wire commands slower than this many ms into `_profile` with a TTL index; default off)
- `OXIDB_PROFILE_TTL_SECS` (optional; retention of `_profile` records, default 86400)

Diagnostics: `{"cmd": "explain", "inner": {...find/count/aggregate...}}` returns the query plan (strategy, index used, examined/returned, post-filter operators) plus real run timing. Prometheus exposition at `GET /metrics` on the REST listener.

**Dart/Flutter client (`clients/oxibase-dart/`, package `oxibase` 0.1.0).** Mobile apps talk to a project the way the browser does: `OxibaseClient(url, key, ref, authUrl)` → `.from(table)` (PostgREST grammar → documents or a SQL table, server-dispatched), `.series(measurement)` (tsdb profile), `.sql(text, params)`, `.textSearch`/`.createTextIndex`, `.storage.from(bucket)` incl. `.search()` over file contents, `.subscribe()` realtime (one shared socket; the auth frame carries `db`; reset on identity change but **not** on rotation, or every hourly refresh would drop every subscription), and `.auth` (password, magic link, OAuth URL for a deep link, Google ID token, `sessionFromRedirect` for the fragment). Two deps, both already in a Flutter tree: `http`, `web_socket_channel`. **The JS client's auth bugs are designed out**: refresh is single-flight, a request whose token rotated mid-flight retries instead of re-refreshing (`_tokenGeneration`), and every rotation is emitted on `onAuthStateChange` so a stored session stays current — `setSession` deliberately does not emit, or a persist-listener loops. `OxibaseException` keeps the server's distinctions: `isRateLimited` (429 + `retryAfter`) separate from `isDenied` (401/403), `isConflict` (409) for a unique-index duplicate. 17 tests: URL building (incl. `eq."42"` quoting, and `is.null` *not* quoted — a real bug the test caught), single-flight refresh, rotation reporting, the spent-token regression, and an opt-in live suite (`OXIBASE_URL`/`OXIBASE_KEY`) covering documents, ranked search and storage search. MIT, like the other clients; `dart analyze` and `pub publish --dry-run` clean, **not published to pub.dev**.

**Full-text search over REST (0.39.27).** The engine's BM25 index (`src/fts.rs`, k1=1.2/b=0.75, Lucene defaults) was wire-only, so no OxiBase project could use it: `POST /api/{col}/text_search` (`{query, limit≤500, highlight}` → documents with `_score`, and `_highlights` `<mark>` snippets when asked) and `POST /api/{col}/text_index` (`{fields}`) close that. **Gating differs from `aggregate` on purpose**: a text search returns whole documents, so a row-level read rule *can* be honoured — matches are filtered like `find` does rather than the request being refused (a filtered search may return fewer than `limit`; the alternative leaks how many matches the caller may not see). `read:false` is refused outright. Searching is a read (`rest_permitted` allows it for Read/Authenticated alongside `aggregate`); **building the index is not**, so it needs ReadWrite/service_role — otherwise a published browser key could index anything. Unindexed collection = explicit error, not an empty result, so a client can fall back. `oxibase-js` 0.3.0: `.textSearch(col, q, {limit, highlight})` / `.createTextIndex(col, fields)`. **Disk-first text indexes did not survive a restart (0.39.28)** — found the moment the surface was used for real: `btree_collection::create_text_index` never called `save_index_metadata` (its `collection.rs` sibling always did, and `list_indexes` already reported the index), and the open path had no `"text"` arm, so every deploy silently dropped every project's index and searches answered "no text index". Only the *definition* is persisted; postings are rebuilt by one document scan at open, paid only by collections that asked for full-text search. Pinned by `tests/fts-rest.e2e.mjs` (19 assertions: ranking, highlights, both refusals, row-level filtering, service-key bypass, and surviving a restart via `OXIDB_RESTART_CMD`). **Blob/bucket FTS over REST too (0.39.29):** `POST /api/storage/_search` (`{bucket, query, limit≤200, highlight}` → `{bucket, key, score}` + `highlights`) searches the text extracted from uploaded files (HTML/XML/JSON/PDF/DOCX/XLSX, OCR'd images with the feature) — indexed automatically on every `put_object`, so nothing is built first. **The bucket is required**: a bucket's read rule is per bucket, so a cross-bucket search could report keys out of a `read:false` bucket; per-bucket makes the check exactly `read_allowed`, the one a download already passes. Matched ahead of the storage delegate because `POST /api/storage/{x}` already means "create bucket x", so `_search` is not a usable bucket name on this surface. `oxibase-js` 0.4.0: `.storage.from(bucket).search(query, {limit, highlight})`. Pinned by `tests/fts-storage.e2e.mjs` (13 assertions: ranking, bucket-scoped hits, missing bucket/query 400s, `<mark>` snippets, `read:false` refusing the *search*, service-key bypass, and surviving a restart).

**PostgREST-compatible auto-REST (`oxidb-server/src/rest/postgrest.rs`, ADR-0019).** A wire-compatible PostgREST surface over the document engine at `/rest/v1/{table}` (a table = a collection), so `@supabase/postgrest-js` and PostgREST clients talk to OxiDB unmodified. Pure **URL-grammar → query-AST translation** — no new engine state; compiles to the existing `find_with_options`/`insert_many`/`update`/`delete`. Grammar: filters `col=eq.42`/`gt`/`gte`/`lt`/`lte`/`neq`, `not.` negation (inverse ops `$ne`/`$nin`, else `$not`), `in.(a,b)`, `is.null`/`is.true`/`is.false`, `like`/`ilike` (→ anchored `$regex`; SQL-native `%`/`_` wildcards **and** PostgREST's `*` alias — the real `postgrest-js` emits `%`), `match`/`imatch` (raw regex), `or=(…)`/`and=(…)` (nestable), `select=name,price` (+`alias:col`), **resource embedding** `select=*,related(cols)` (nested docs via `$lookup`-style stitch — belongs-to inferred from a parent `<singular(target)>_id` field → single object, else has-many `<singular(parent)>_id` on the child → array; explicit `related!fk(...)` names the FK; nested embeds rejected), `order=price.desc,name`, `limit`/`offset`; full CRUD (`POST`/`PATCH`/`DELETE`), `Prefer: return=representation` echoes rows, `Content-Range` on reads. `cs`/`cd` array containment (`tags=cs.{a,b}` → `$all`/`$in`, the Postgres array literal `postgrest-js` `.contains()` emits — quote-aware, so `{"a,b"}` is one element and `{"2024"}` stays a string). Schemaless value coercion (null/bool/int/float/string; `eq."42"` forces string). Guardrails: `OXIDB_PGRST_MAX_ROWS` (default 1000) hard-caps a read; `?db=<name>` targeting inherited (ADR-0012). **Read-side gates (0.39.21, from an anon-key audit):** `POST /api/{col}/aggregate` now consults `read_access` — a pipeline reads the collection, and `$group` cannot be filtered after the fact, so a collection with a row-level read rule is **refused** to untrusted keys rather than answered from rows they may not see (before this, `$group` over a `doc.owner`-scoped collection returned every owner's values to the public key). `_`-prefixed **system collections are closed to untrusted keys** in both `check_access` and `read_access` — skipping the rules there was meant for the server's own bookkeeping, but let any anon key read the request log/slow-query profile and create unlimited `_`-named collections, which are also exempt from the project's collection quota. `GET /api/rules/{col}` is admin-only (the policy is not for the key it constrains). **Read policy now spans every engine (0.39.22):** the rules store is keyed by *name*, so a rule on a SQL table, a time-series measurement or a storage bucket governs reads of it exactly as a collection's does — `read:false` or `auth != null` makes it private. No rule still means readable (as for documents); what changed is that these could not be closed **at all** before. Only the document engine can honour a *row-level* rule, so a `doc.`-referencing rule on the other engines is a refusal rather than a silent no-op. `/api/sql` is gated per **referenced table** (`oxidb_sql::referenced_tables` walks FROM/JOIN, derived tables, CTEs and set operations), so a join, subquery or UNION cannot reach around the rule of any table it touches; an unparseable statement is refused for untrusted callers rather than passed through. **Safety reuses the existing gates**: `rest_permitted` (Read role → GET only) then `rules::check_access` per request (the RLS analog — `read:false` → `403`). **Rate limits in a rule (0.39.24):** a rule may carry `"rate": {"create": "10/min", "delete": "30/hour"}` (units sec/min/hour/day), enforced **per identity** (`auth.username`) per operation per collection — so one account flooding a collection cannot throttle everyone else, which the per-project `max_requests_per_min` would. Checked *after* the expression, so a write the rule refuses never consumes budget; a refused write answers **429 with `Retry-After`** (PostgREST surface) rather than 403, because "no" and "not yet" are different answers. service_role bypasses, as it bypasses rules. Fixed window, in-process (two nodes each allow the limit — the usual trade for not putting a write on every request's hot path); specs are validated at save time so an unparseable limit is an error rather than a rule that silently never applies. **Rule namespaces:** `doc.<field>` is the stored row and `newDoc.<field>` the incoming one; on **create** `doc.` binds to the row being created (there is no stored one), which is what makes `create: auth.username == doc.owner` — "you may only create rows you own" — expressible at all. Before 0.39.19 it denied every insert, and `newDoc.` was rejected by the validator despite the evaluator reading it, so ownership on create could not be written in any form. Native `/api/...` surface untouched. **Phase 2b — SQL engine under the same grammar** (`oxidb-server/src/rest/postgrest_sql.rs`): when `OXIDB_SQL=1` and `{table}` names a SQL table (`sql_bridge::sql_table_exists`), `/rest/v1/{table}` is served by the SQL engine — the same URL grammar → **parameterized SQL** (values always bound `?`, identifiers validated `^[A-Za-z_]\w*$` as the name-injection guard), CRUD → `INSERT`/`UPDATE`/`DELETE`, `{columns,rows}` reshaped to array-of-objects. A collection and a SQL table never collide, so dispatch is unambiguous; SQL-off keeps the document path byte-for-byte. SQL authz is RBAC-only (no per-row rules, like `/api/sql`) — which is exactly why **a write to a SQL table through `/rest/v1` requires a ReadWrite/service_role key** (0.39.20): the gate lets Read/Authenticated writes through so the *document* rules can adjudicate them, and a table has no rules to adjudicate with, so before this a published anon key could insert into and delete from any table. Same fix and reasoning as the tsdb profile. **SQL resource embedding** (Phase 2c) infers the relationship from **catalog foreign keys** (`sql_bridge::sql_foreign_keys`): FK current→target = belongs-to (object), FK target→current = has-many (array), `related!fk(...)` names the column; each embed is one batched `SELECT … WHERE fk IN (…)` stitched in Rust (not a JOIN — exact join columns from the declared FK, no naming-convention guessing). **SQL write-representation**: `Prefer: return=representation` appends `RETURNING *` to the INSERT/UPDATE/DELETE and echoes the affected rows (projected by `?select=`), else minimal (`201 []`/`200 []`/`204`). **TSDB under the same grammar** (`oxidb-server/src/rest/postgrest_tsdb.rs`, Phase 2d): selected by PostgREST's **schema profile** — `Accept-Profile: tsdb` / `Content-Profile: tsdb` (what `postgrest-js` `.schema('tsdb')` emits) routes `/rest/v1/{measurement}` to the time-series engine (profile-routing, not existence-routing, since a measurement only exists after its first write). Read: `select=<field>` (the field), `tag=eq.value` (tag equality), `ts=gte./lt.` (time range `[start,end)`), extension params `agg`/`interval`/`group_by`/`p`; the series result is flattened to `{ts, value, <tags…>}` rows, with `order=ts.*`/`limit` post-flatten. Write: flat `{ts, host:"x", usage:0.5}` → ts/time=timestamp, string→tag, number/bool→field (or nested `{ts,tags,fields}`). PATCH/DELETE → `405` (append-only; use retention). RBAC-only, `OXIDB_TSDB=1` — and because "RBAC-only" means there are no per-row rules to fall back on, **writes under the tsdb profile require a ReadWrite/service_role key**: the browser-safe anon key may read series but never append to them (0.39.17; before that it could, which let a published anon key poison a project's series). **Nested embeds** (`authors(name,books(title,chapters(name)))`) work on both the document and SQL engines — a child's `select` recurses through the same projection path (`project_top`/`project_sql`) at `depth+1`, bounded by `MAX_EMBED_DEPTH` (5). The whole surface (**all three engines**, incl. 2-level nesting) is verified against the real unmodified `@supabase/postgrest-js` client (`tests/postgrest-js-test/`, 26 assertions). ADR-0019's mapped grammar is functionally complete.

**OxiBase control plane (`oxidb-server/src/platform/`, ADR-0020).** A multi-tenant provisioning layer — the Supabase-platform analog on top of the `/rest/v1` data plane. Off unless `OXIDB_PLATFORM=1` **and** `OXIDB_PLATFORM_SECRET` (the platform master secret that signs developer sessions). Route family `/platform/v1/*`: `signup`/`login` (developer accounts, stored in a `_oxibase` system database opened directly outside `DatabaseManager`), `POST/GET/DELETE projects` (a project = one isolated tenant database via `DatabaseManager::create_database`). Each project gets its **own** `jwt_secret`, generated at creation and stored **AES-GCM encrypted** in `_oxibase.projects` (`crypto::EncryptionKey::from_bytes`). **Two-secret boundary (ADR-0021):** `OXIDB_PLATFORM_SECRET` signs developer sessions (control-plane only); `OXIDB_SEAL_KEY` seals/unseals per-project secrets — the data-plane hook `project_secret` unseals with the seal key **alone**, never the session-signing master (falls back to master when `OXIDB_SEAL_KEY` unset, single-binary skeleton). Two API keys per project, minted as JWTs signed with that project secret at a fixed `iat` (deterministic/stable): `anon_key` (role `read`, browser-safe) and `service_role_key` (role `admin`, server-only, bypasses rules). **The one data-plane change:** the REST listener resolves the JWT verification secret **per target database** — a `?db=<ref>` request to an OxiBase project verifies with that project's secret (`platform::project_secret`), everything else with the global `OXIDB_JWT_SECRET`. Isolation modes recorded per project: `shared` (many logical databases in one process, the default and OxiDB's density advantage) vs `dedicated` (a process per tenant, future). Addressing v1 is `<host>/rest/v1?db=<ref>` (works today); per-project subdomains are a v2 behind a wildcard cert. **Hardening:** `POST /platform/v1/projects/{ref}/keys/rotate` re-mints both keys under a fresh project secret so a leaked key dies immediately (keys carry a stored `key_iat` = creation-or-rotation time, kept deterministic); per-project secrets are cached (`secret_cache`) and invalidated on rotate/delete so a revoked secret can never keep verifying; signup is guarded by an 8-char minimum password, a per-actor rate limit (forwarded client IP via `X-Forwarded-For`/`CF-Connecting-IP`, `OXIDB_PLATFORM_SIGNUP_RATE`/min), an optional invite code (`OXIDB_PLATFORM_SIGNUP_CODE` — private signup), and a global account ceiling (`OXIDB_PLATFORM_MAX_ACCOUNTS`); login has a per-email brute-force lockout (5 fails → 5-min 429); projects-per-account is capped (`OXIDB_PLATFORM_MAX_PROJECTS`, default 100). Deployment specifics (hosts/secrets) stay in env, never committed. **Separate-service migration (ADR-0021, landed):** the generic HTTP types + parsing + a thread-pooled `serve` listener + a blocking JSON client are a standalone dependency-free **`oxidb-http`** crate (server's `s3::http` re-exports it). The control plane is now its own lean binary — the **`oxibase`** crate (deps: `oxidb-http` for its listener, `oxidb-client` for the wire, small crypto — **no engine**): it serves `/platform/v1/*` and reaches the data plane over OxiDB's **native OxiWire protocol** (a new standalone **`oxidb-client`** crate: length-prefixed JSON over TCP + client-side SCRAM-SHA-256 + a self-healing connection **`Pool`** with typed errors — `Connect` retryable / `Io` not / `Wire` healthy — so a stale pooled connection re-dials safely; zero engine deps) as an admin client — tenant databases via `create_database`, its own accounts/projects stored in an `oxibase` metadata database. Config: `OXIBASE_UPSTREAM` (`host:port`), optional `OXIBASE_UPSTREAM_USER/_PASSWORD` (SCRAM); the shared secret between the planes is now just `OXIDB_SEAL_KEY` (+SCRAM creds) — no shared JWT. `upstream.rs` isolates the transport, so the earlier REST version was a one-file swap. The data plane keeps **only** the `tenant_auth::project_secret` hook (`oxidb-server/src/tenant_auth.rs`, ~140 lines: reads that shared `oxibase` db locally, unseals with `OXIDB_SEAL_KEY`, short TTL cache since the control plane is out-of-process) and no longer serves `/platform/v1`. Config: `OXIBASE_ADDR`, `OXIBASE_UPSTREAM_URL`, shared `OXIDB_JWT_SECRET` (oxibase's admin token) + `OXIDB_SEAL_KEY`, control-plane-only `OXIDB_PLATFORM_SECRET`. Proven two-process end-to-end (signup → provision → service_role/anon keys work against the data plane's `/rest/v1`). ADR-0021 migration complete. **End-user social sign-in (`oxibase/src/oauth.rs`)**: per-project Google/GitHub OAuth for an app's *own* users — the developer stores the provider's client id + **sealed** secret on the project row (`oauth.{google,github}`, owner-only `GET/PATCH /platform/v1/projects/{ref}/auth/providers`), and users sign in through the authorization-code redirect (`/auth/authorize/{provider}` → provider → `/auth/callback/{provider}`) or, for Google, a browser ID token (`POST /auth/oauth/google`, no secret needed). The session is handed back on a **pre-registered** `redirect_urls` entry in the URL *fragment* (tokens never reach a server log); the allow-list is mandatory and its `*` can only extend a path, never widen a host. State is a stateless HMAC blob (10-min TTL) bound to project+provider, so the callback is CSRF-safe with no server-side session table. Accounts link by **verified** email only (GitHub's primary-verified address, Google's `email_verified`), so password-then-Google lands in one account. `GET /auth/settings` is the public discovery endpoint. **Magic links** (passwordless): `POST /auth/magiclink {email, redirect_to}` mails a 15-minute single-use link, `GET /auth/magiclink/verify?token=` burns it and redirects to the app with a session — the destination is validated and stored *when the mail is sent*, so a tampered link cannot move the session, and re-checked on click so a revoked URL stops working. The click doubles as signup + address verification. `mail.rs` gained a dev/test transport (`OXIBASE_MAIL_SINK` writes messages to a file instead of SMTP) so the whole email surface is testable without a mail server. **Session rotation (0.39.26)**: access tokens are short-lived (`OXIDB_PLATFORM_ACCESS_TTL`, default 1h) and `POST /auth/refresh` **rotates** the refresh token — it revokes the presented one, which is what makes a replayed token detectable. Two consequences were breaking real apps. (a) A client must persist *every* rotation, not just what sign-in returned; `oxibase-js` had no way to say a rotation happened, so an app storing the session in `localStorage` kept the token spent by the first refresh and every reload past the first hour 401'd forever with no recovery but re-login. The SDK now has `auth.onAuthStateChange(cb)` (`signedIn`/`tokenRefreshed`/`signedOut`) — `setSession` deliberately does *not* fire it, so a persist-on-event listener cannot loop. (b) Concurrent requests each 401ing on the same expired access token all POSTed the same refresh token, so one rotated and the rest were told "invalid" — a page whose feed fires 8 queries lost 7 of them. Fixed on both ends: the SDK coalesces refreshes into one in-flight promise and retries (rather than re-refreshes) a request whose token was rotated while it was in flight (a `tokenGen` counter), and the server honours a *just-consumed* token for `REFRESH_GRACE_SECS` (10) — a race is forgiven, a later replay is not. Consumed rows carry `used_at` and are swept, scoped to the user, on their next issued session; every revocation path (password reset/change, user delete) still deletes all of a user's rows, so grace never outlives a revoke. Pinned by `oxibase/test/auth.e2e.mjs` (rotation/grace/replay) and `oxibase-js/test/refresh.mjs` (offline, stub server: coalescing + the stale-persisted-token regression). **Per-project request rate limiting (0.39.16)**: the same model-B split as the size quotas — the value lives on the project row (`max_requests_per_min`, `PATCH /projects/{ref}/limits`, env default `OXIDB_PROJECT_MAX_RPM`), enforcement is in the data plane at the one point a request is attributed to a tenant (`rest/mod.rs`, right after the tenant db resolves), so every surface on that listener (REST, `/api`, storage, SQL) is covered by one check and refused before any work happens: `429` + `Retry-After`. Fixed one-minute window per project in `tenant_auth::rate_limit_hit` (one lock, one counter; refusals do not extend the window; stale windows swept past 4096 tracked projects). **0 = unlimited is the default** — throttling is opt-in, never a surprise an upgrade delivers under load. Remaining OxiBase work is additive: the web dashboard is a static React+TS+Vite SPA (`apps/oxibase-dashboard/`, matching the OxiDB Studio stack; served outside Rust) — v1 has auth + project management (list/create/keys/rotate/delete), with a table/SQL editor over `/rest/v1` next, (B) JWKS/asymmetric verification for multi-node, and anon-with-rules.

**PostgreSQL wire protocol (`oxidb-server/src/pg/`, ADR-0023).** A tenth listener (`OXIDB_PG_PORT`, off by default; needs `OXIDB_SQL=1`) speaks the **PostgreSQL v3 frontend/backend protocol**, so `psql` and `psycopg` connect unmodified — verified against real psql 18 and psycopg 3.3. **Zero OxiWire changes**: it reaches the same per-database engines via `sql_bridge::engine`, the same accounts via `auth`, and the same SCRAM verifiers via `scram` (PostgreSQL wraps SCRAM in a SASL envelope, but the messages inside it are the RFC 5802 ones `ScramState` already parses — the only fix needed was accepting the `y,,` GS2 header alongside `n,,`, and deriving `c=` from it instead of hardcoding `biws`). Modules: `wire` (codec), `auth` (handshake), `session` (state + the one call into the engine), `catalog` (statements that never reach it), `types` (OIDs + value encoding), `errors` (SQLSTATEs). **A portal executes once, at `Describe` or `Execute` — whichever comes first** — because the engine reports a result's shape only by producing it, and answering `Describe(portal)` with `NoData` breaks psycopg (which reads column metadata from exactly there); the only visible difference from PostgreSQL is that an error surfaces one message earlier, still inside the same batch. `SET`/`RESET`/`SHOW`/`DISCARD`/`version()`/`current_database()` are intercepted (the engine's parser rejects `SET`, and every client sends one before it will talk); `\dt` and `\l` are answered from the engine's catalog, and **every other `pg_catalog` query is refused with `0A000` naming what is unsupported** — an empty result would be believed (found for real: answering psql's `\d <table>` probe with the table list made psql fail on a column it expected). Errors map to the SQLSTATEs clients recover on (`23505`/`42P01`/`42703`/`23502`/`42601`/`0A000`/`55P03`/`42501`), and the failed-transaction state is emulated (`'E'` until `ROLLBACK`; `COMMIT` answers `ROLLBACK`) because psycopg's `with conn.transaction():` recovery depends on it. Engine ints are **`int8`, never `int4`** (i64 would truncate). `Role::Read` may only SELECT/SHOW, same gate as the native port. **Doğrulanmış istemciler (gerçek sürücülerle, tahminle değil): psql 18, psycopg 3.3, Npgsql 8.0 (default modda — `NoTypeLoading` flag'i GEREKMİYOR), pgjdbc 42.7** (`DatabaseMetaData` dahil: getTables/getColumns/getPrimaryKeys — composite PK'nın her parçası — /getIndexInfo/getImportedKeys/getTypeInfo/getSchemas, hepsi motorun kendi kataloğundan: `list_tables`/`table_def`/`list_indexes`/`Table::foreign_keys`). Bunu açan iki iş: (a) **karışık batch** — bir simple-query mesajı hem intercept edilen hem motora giden statement taşıyabilir (Npgsql tam olarak `SELECT version();` + type-catalog sorgusunu TEK mesajda yolluyor; eskiden tüm batch motora gidip `version()`'da patlıyordu). `split_statements` tırnak/`''` escape/dollar-quote/`--`/`/* */` farkında, ardışık motor statement'ları tek çağrıda kalıyor. (b) **type catalog cevaplanıyor** — içeriği STATİK (bu sunucunun ürettiği tip listesi, gerçek PG OID'leriyle → sürücünün mevcut handler'ı aynen çalışıyor); composite-field ve enum sorguları **boş** dönüyor, ki bu DOĞRU (composite tip ve enum yok). Tablo-başına introspection hâlâ reddediliyor (statik değil). `pg_type.oid` kolonu `oid` (26), `typtype` `char` (18) olarak declare edilmeli — sürücü `int8`/`text` kabul etmiyor. **Catalog SATIRLARI da cevaplanıyor (0.41.4, `pg/pgcatalog.rs`) — DBeaver 25.3 native PostgreSQL sürücüsüyle bağlanıp gezinebiliyor.** DBeaver soru sormaz, kataloğun kendisini ister: `SELECT c.oid,c.* FROM pg_catalog.pg_class c` + `WHERE 1<>1` shape probe'ları. Bu yüzden PostgreSQL'in **gerçek kolon setleri** (sırasıyla, gerçek tip OID'leriyle) tutuluyor ve OxiDB'nin şemasından dolduruluyor: pg_class/pg_type/pg_namespace/pg_attribute/pg_constraint/pg_index/pg_database/pg_roles/pg_settings. **Kural: kolon setleri PostgreSQL'in, DEĞERLER OxiDB'yi anlatır** — karşılığı olmayan (tablespace, ACL, freeze horizon) NULL/0, olmayan katalog (pg_proc/pg_extension/pg_trigger) **kolonlarıyla + SIFIR satır** döner ("yok" doğru cevap, uydurma satır değil). Bunları çalıştırmak değil, ŞEKLİ cevaplamak: gerçekten çalıştırmak `~`, `::regclass`, `format_type()`, `pg_get_expr()`, set-returning fonksiyon ister. **DBeaver'da 3 gerçek bug çıktı (hepsi kodu okuyarak değil, ÇALIŞTIRARAK):** (1) dispatch *bahsedilen* tabloya bakıyordu → `pg_class LEFT JOIN pg_description` sorgusu pg_description olarak cevaplandı (boş tablo listesi) → artık **FROM hedefine** bakıyor; (2) `relkind` filtresi yok sayılıyordu → index'ler tablo olarak listelendi; (3) `\d` reddi çok genişti. **Çıktı BUFFER'lı** (`Conn.w()` artık `&mut Vec<u8>`, flush protokolün söylediği yerde): bir sonuç kümesi satır BAŞINA bir `DataRow` mesajıdır, doğrudan sokete yazınca 1000 satır = 1000 syscall (+`TCP_NODELAY` ile ~1000 paket). Benchmark bunu buldu: 1000-satır okuma 526→1796 ops/s (**3.4x**), OxiWire'a karşı 0.43x'ten 1.51x'e döndü → [wire benchmark](docs/wire-benchmark.md), `examples/wire_bench.rs` (aynı motor, aynı process, iki tel; her iki istemci de elle yazılmış ve minimal — kütüphane değil TEL ölçülüyor). **Eşzamanlılık (`--mode conc`)**: her iki dinleyici de standalone'da thread-per-connection (`OXIDB_POOL_SIZE` sadece cluster'da) — nokta okuma 16 bağlantıda ~3.6x'te tavan yapıyor (motor tek mutex), 100-satır okuma 4 bağlantıda ~8.3k'da BULUŞUYOR (yük altında tel önemini yitiriyor). **INSERT 1→32 bağlantıda DÜMDÜZ ~266/s, p50 4ms→91ms (tam doğrusal kuyruk) — SQL motorunda GROUP COMMIT YOK**: `Wal::append` kayıt başına fsync ediyor ve engine mutex'i tutulurken çağrılıyor, yani eşzamanlı commit'ler batch'lenmiyor sıraya giriyor (doküman motorunda group commit VAR, SQL motorunda yok — benchmark bu boşluğu ölçülebilir yaptı). INSERT iki telde de ~265/s ≈ 4ms (fsync-bound) — motorun baskın olduğu yerde iki telin BİREBİR aynı çıkması ölçümün doğruluğunun kanıtı. **Reddedilen catalog sorguları loglanıyor** (`[pg] refused catalog query:`) — operatörün bildirebileceği tek hata bu ve sorgu metni raporun kendisi. **Eşleştirme KURALI: sorgunun okuduğu tabloya değil, o çağrıya ÖZGÜ alias'a bak** (`self_referencing_col_name`, `index_qualifier`, `elemtypoid`, `fkcolumn_name`). Geniş eşleştirme geliştirme sırasında `getIndexInfo`'ya **tablo listesini** index kolon adları altında döndürdü — çağıran bunu doğrudan ayırt edemez; `tests/pg_wire.rs` "hiçbir catalog sorgusu başkasının şeklinde cevaplanmaz" özelliğini pinliyor. Kalan eksikler: rastgele catalog sorguları (psql `\d <table>`, pg_dump, BI araçları), `COPY`, `LISTEN`/`NOTIFY`, `DECLARE CURSOR`, cancellation, gerçek şema — hepsi adıyla reddediliyor. **TLS doğrulandı** (`sslmode=require` → TLSv1.3). One small engine addition: `SqlEngine::command_kinds` (`CommandKind`), because `CommandComplete` must name the verb (`INSERT 0 3`) and `QueryResult` says what happened, not which verb asked. Tests: `tests/pg_wire.rs` (27, byte-level, incl. a real SCRAM login with mutual auth) + `tests/pg_e2e.rs` (5, real psycopg).

### Second engine — SQL (`oxidb-sql/`, ADR-0010)
A standalone relational SQL engine (its own crate) can be mounted alongside the document engine in the same server. It owns **entirely separate files** and shares no state — a collection name and a SQL table name never collide. Off by default.
- `OXIDB_SQL` (set to `1`/`true`/`yes`/`on` to enable; default off — zero cost when unused)
- `OXIDB_SQL_DATA` (SQL engine data dir; default `${OXIDB_DATA}/sql`)
- `OXIDB_SQL_DISK_FIRST` (rows served from the mmap'd last-checkpoint `.rdat` snapshot, only post-checkpoint changes in RAM; **default ON since 0.41.33** — warm 1.2M satır 39 MB, nokta/index sorguları paritede, taramalar resident'a göre ~%30 yavaş; `0` = all rows resident. Aynı format, iki yönde de güvenli geçiş. `SqlOptions::default()` da true — TÜM mode-agnostik testler artık disk-first koşuyor, `default_mode_tests` pinli, resident'a özgü mekanizmalar (scan cache) resident'ı açıkça açıyor)
- `OXIDB_SQL_CHECKPOINT_BYTES` (auto-checkpoint the SQL WAL past this size; default 64 MiB, `0` = manual only)

Wire routing (`handler.rs`): a request with `engine: "sql"` — or the reserved `sql` command — is served by the SQL engine; a missing/`"doc"` engine keeps the document path byte-for-byte (full backward compatibility). Request shape: `{ "engine": "sql", "cmd": "sql", "sql": "SELECT ...", "params": [ ... ] }` (`params` binds `?`/`$N`). RBAC gates `sql` at the `ReadWrite` role. SQL supports DDL, DML, single-table + INNER/LEFT/RIGHT/FULL-join SELECT with GROUP BY/HAVING aggregates, secondary indexes, parameterized queries, and per-engine transactions (`BEGIN`/`COMMIT`/`ROLLBACK`). **Concurrent writers vs. a buffered transaction (0.40.2, was a silent lost write):** a transaction reserves its row ids and `AUTO_INCREMENT` values *from the engine* as it buffers each write (`SqlEngine::reserve_row_ids` / `next_auto_block`) instead of peeking the counter and allocating locally — the old peek handed the same id to any concurrent writer (another transaction **or a plain autocommit INSERT**) and the commit then overwrote their row, no error anywhere. Reservation makes rollback leave a gap, as sequences do everywhere. Because distinct ids alone would turn that lost row into two rows sharing one key, `commit_batch_checked` re-validates every PK/UNIQUE constraint against committed state under the commit lock (`BatchSim` simulates the ops in order, so a key the batch itself frees stays reusable) and refuses the commit if a key was taken meanwhile. The replication apply path (`commit_batch`) deliberately does **not** re-check — the cluster already agreed, and a node that second-guesses diverges — so the re-check is single-node; `tests/t_concurrent_writers.rs` (10 tests, all proven red first). **Cluster:** SQL writes ARE Raft-replicated — `sql_is_write` (`async_server.rs`) classifies a statement by parsing it (`oxidb_sql::is_read_only`), and a write replicates as `OxiDbRequest::Sql` (`Scoped` per database); SELECT-only SQL, and SQL that fails to parse, runs node-locally. **Not sharded:** oxipool shards by `collection` + a shard key, which a `sql` request has none of, so SQL is never scattered across shards — it routes to one backend (a replica when read-only, else the master). Stored procedures come in two languages (ADR-0014): SQL-text bodies (`CREATE PROCEDURE ... AS BEGIN dml; END` — zero-toolchain, re-parsed per CALL) and compiled **Cobra** bytecode (`CREATE PROCEDURE ... LANGUAGE COBRA AS '<base64 .cobrac>'`) executed by the `oxidb-cobra/` VM crate: the file defines `def run(db, ...params)`, `db.query`/`db.execute` join the CALL's transaction, print → notices, 100M-instruction fuel cap, determinism validated at CREATE (async/import/IO rejected) so CALL replicates safely.

**Persistence & crash-atomic checkpoints (`storage.rs`, `wal.rs`, `catalog.rs`, `manifest.rs`).** Each checkpoint writes a whole new **generation** into its own `gen.<N>/` subdirectory (`catalog.json` + one `<table>.rdat` row snapshot each), fsyncs it, then promotes it by renaming a tiny `MANIFEST` file (`{generation, wal_seq}`) into place — **the single atomic commit point** (`manifest.rs`). A crash anywhere before that rename leaves the previous `MANIFEST`, and thus the previous intact generation, in force; a half-written generation is ignored at open and swept. Because catalog and snapshots switch together, their arities can never disagree after a crash (the failure mode the old flat overwrite-in-place layout had). The WAL stays a **single file** (`wal/live.wal`, CRC'd, seq-numbered): the manifest records the highest seq folded into the snapshots, and recovery replays only records past that watermark (`Wal::open_since`), so a not-yet-truncated WAL never double-applies a checkpointed (non-idempotent) ALTER; truncation is best-effort. **Group commit (`CommitGate` in `lib.rs`):** a write appends + applies under the engine lock, releases it, and fsyncs *outside* it through a WAL descriptor duplicated once at open; one writer is elected leader and everyone whose record was on disk when its flush began is covered by it, so the engine lock is never held across an fsync. Acknowledgement is unchanged (a statement returns only after a flush covering its own seq); what is newly observable is the apply→flush window, the same one PostgreSQL and the document engine accept. A checkpoint publishes durability without flushing (`mark_durable`) — it already fsynced the snapshot those records were folded into, and must, since it may have just truncated the WAL they would flush. The gain starts at ~4 concurrent writers (a flush may only claim what was on disk when it *started*, so 1-2 writers never accumulate a group): the wire benchmark went from flat ~266 writes/s at every concurrency to ~1.2k/s at 16 connections. The watermark is `Wal::last_seq()` — publishing `next_seq` instead silently skipped every second fsync, caught only because single-connection throughput doubled where batching cannot help; pinned by `commit_gate_tests` (the gate may never claim a seq the WAL has not written) and `tests/t_group_commit.rs`. **Değişmeyen tablo YENİDEN YAZILMIYOR (0.41.27):** bir checkpoint, dayandığı generation'dan beri dokunulmamış her tablonun dosyalarını yeni generation'a **hard-link** ediyor (`link_generation_files`) — eski generation'ı geri kazanmak sadece bir dizin girdisini düşürür, inode yeni link üzerinden yaşar; MANIFEST rename'i hâlâ TEK commit noktası. Öncesinde checkpoint maliyeti ne kadar az değiştiğine bakmaksızın TÜM veritabanıydı (~1s / 1.2M satır) ve açılış tepesini sınırlamak için sık fold etmeyi karşılanamaz kılan buydu. Yeniden kullanım kasten **muhafazakâr**: tablo ancak satır deposu *tam olarak* base snapshot'ıysa (`RowStore::is_base_only` — dirty flag DEĞİL, yeni bir yazma yolunun set etmeyi unutabileceği bir bayrak yerine deponun kendisinden türetiliyor) VE yeni generation'ın ihtiyaç duyduğu her dosya eskisinde ZATEN varsa uygun. İkinci koşul gereksiz değil: son checkpoint'ten sonra yaratılan bir index'in dosyası yoktur, "var olanı linkle" demek dosyası olmayan bir index'i BEYAN eden generation commit etmek olurdu — hiçbir sorguya yanlış cevap vermez, index sessizce index olmaktan çıkar (`usable()` false → tarama). `checkpoint_reuse_tests` (5) her durumu pinliyor; index olanı kontrol kaldırılınca KIRMIZI olduğu kanıtlandı. Aynı işte **tablo başına tek satır yürüyüşü** (`storage::SnapshotWriter` + `RowStore::visit_physical`): snapshot yazıcısı, PK, UNIQUE ve secondary index builder'ları artık aynı geçişten besleniyor (eskiden tablo tüketici başına bir kez, yani disk-first'te satır başına bir decode BAŞINA tüketici okunuyordu). **Sequences live in a separate `sequences.json`** (direct-saved on every `NEXT VALUE FOR` — far more often than a checkpoint, and arity-independent), never inside the generationed catalog. Legacy flat-layout databases (root `catalog.json` + `<table>.rdat`, no `MANIFEST`) open as generation 0 and migrate to `gen.1/` at their first checkpoint. `OXIDB_SQL_DISK_FIRST` mmaps the committed generation's `.rdat` as the read base. **Engine-aware backup/restore**: `SqlEngine::backup(out)` is **low-lock** — it holds the engine lock only for two O(1) phases (pin a committed generation + read the WAL length; then unpin) and runs the slow `.tar.gz` compression with the lock released, so concurrent queries/writes are not blocked. A pinned generation is safe from GC and freezes WAL truncation, so the archive (a synthesized `MANIFEST` → the pinned `gen.<N>/` + a stable WAL prefix + `sequences.json`) is crash-consistent as of the pin instant even while writes and auto-checkpoints continue. `SqlEngine::restore(archive, target)` extracts into an empty dir. `Tsdb` (`oxidb-tsdb`) has the same **low-lock** `backup`/`restore`, split into `backup_begin` (pin a generation under the write lock) / `backup_write` (compress, no lock) / `backup_end` (unpin) — the per-generation `blocks.<N>.tsb`/`wal.<N>.log` files are pinned against a checkpoint's GC, so writes and auto-checkpoints continue during the archive; `tsdb_bridge.rs` orchestrates the three phases. Both are admin-only over the wire (`{engine:"sql"|"tsdb", cmd:"backup", path}` / `{cmd:"restore", archive, target}`, `sql_bridge.rs`/`tsdb_bridge.rs`) — separate from the document engine's `backup()`/PITR, which snapshots only the document data dir.

**Resident-memory design (`lib.rs`, benchmarked in `docs/pg-memory-benchmark.md`).** The SQL engine holds keys in RAM where PostgreSQL holds a capped page cache, which made an index-heavy 1M-row database cost 423 MB warm (disk-first) against PostgreSQL's 105 MB. Bu yüzden sıralı okuyucular `SnapshotCursor` kullanıyor (kendi byte offset'ini taşıyor, sabit zamanda ilerliyor); sadece row-id ile arama yürüyor. **Sonuç: 32.8 B/satır → 0.69 B/satır (47x).** 1.2M: steady 37.5→**0.8 MB**, tepe 62.5→37.1; 9.6M: steady 300→**6.3 MB**, tepe 489→137. Okuma bedeli ~%2 (tarama 132→135 ms, PK nokta 7.2→7.3 µs), açılış süresi AYNI. 100M satır ≈ 69 MB (3.1 GB yerine). Disk-first artık satır başına HİÇBİR yapı tutmuyor: satırlar, secondary index'ler, PK, UNIQUE ve satır index'i hepsi dosya. **Blok boyutu ölçümle seçildi ama en büyüğü ALINMADI:** 9.6M'de yürüyüş neredeyse düz (16→7.1 µs, 128→7.4 µs) ve bellek 8x düşüyor, yani büyük blok bedava GÖRÜNÜYOR — ama o koşuda dosya page cache'te; yürüyüş payload'ları atladığı için 128-kayıtlık blok ~14 KB kaplar = bir satırı okumak için SOĞUKTA 4 sayfa (32'de 1 sayfa). Her boyut zaten GB'ı MB yapıyor, kalan MB'ı benchmark'ın ölçemediği page fault'la satın almaya değmez. **Değişen davranış:** yoğun index açılışta kendini savunma amaçlı SIRALIYORDU; seyrek olan satırları tutmadığı için sıralayamaz → artan row-id artık ZORUNLU invariant, ihlal eden dosya (veya tekrarlanan id) `Corrupt` ile açılmıyor; her yazıcı zaten artan sırada üretiyor. `sparse_index_tests` (8) pinliyor — satırlar BOŞLUKLU id'lerle üretiliyor (1,3,5…), çünkü bitişik id'ler "kayıt kalmadı" ile "geçti" arasındaki farkı gizler; ayrıca bir test index'in satır başına DEĞİL blok başına girdi tuttuğunu assert ediyor (yoksa yoğun bir implementasyon diğer 7'sini de geçerdi). (i) `IndexBuilder` bir **external sort**: çiftler sınırlı tampona birikir, sıralanıp run dosyasına spill edilir, sonra k-yollu merge doğrudan çıktıya; dosyanın üç bölümü ayrı temp dosyalara yazılıp birleştirilir, yani bitmiş index'in kopyası da tutulmaz. (ii) WAL replay artık kayıtları **tüketiyor** (`for rec in records`), eskiden ödünç alıp tüm parse edilmiş kuyruğu overlay'in yanında canlı tutuyordu. **Kalan ~230 MB overlay'in kendisi**: WAL kuyruğunu replay etmek bekleyen her satırı checkpoint fold edene kadar materyalize ediyor. Bunu sınırlamak replay SIRASINDA checkpoint gerektirir — ama `checkpoint_locked` canlı WAL'i truncate edip watermark'a `wal.last_seq()` yazar, yani replay ortasında çağırmak HENÜZ UYGULANMAMIŞ kayıtları "fold edildi" ilan edip silerdi. Güvenli hâli watermark'ın son UYGULANAN seq'i izlemesini ister — YAPILMADI: (a) **sorted inline posting lists** (`RowIds` = `SmallVec<[u64;1]>`) instead of a `BTreeSet<u64>` per index key — a key matching one row was allocating a whole 11-slot leaf node, ~150 B, to say so; (b) **`KeyTuple` = `SmallVec<[IndexKey;1]>`** instead of `Vec<IndexKey>`, killing one heap allocation per key in every index and PK map; (c) **`PkMap`** stores a single-column integer primary key as a bare `i64` (`103 → 34 bytes/row`), widening itself to the general `BTreeMap<KeyTuple,u64>` if a value that does not fit ever arrives; (d) **the replayed WAL tail is folded at open** in disk-first mode (`checkpoint_bytes/8` threshold) — records past the watermark replay into the RAM overlay and only a checkpoint moves them into the mmap, so a restart used to inherit the previous process's pending WAL as resident memory (a 55 MB tail cost 60 MB); (e) **secondary indexes are `populated: false` at open and built on first use** — rebuilding them eagerly cost 318 MB for three indexes on 1M rows before answering anything; writes skip an unpopulated index (it is built from current rows when wanted, pinned by `lazy_index_tests`), while `CREATE INDEX` still builds eagerly; (f) **the statement cache skips text over `STMT_CACHE_MAX_TEXT` (4 KiB)** — a bulk load filled all 512 slots with parsed 500-row `INSERT`s whose text is unique by construction, so the hit rate was zero and ~250 MB of key+AST stayed resident for the process's life (`stmt_cache_tests`). (g) **disk-backed secondary indexes** (`index_file.rs`, `.sidx`, disk-first only): a **sorted entry table** mmap'd in place — the document engine's `.mcidx` shape, not a B-tree, because every writer rewrites the file whole at checkpoint time (no splits, no free-space map, no page concurrency); lookup is a binary search over a fixed-stride table (keys reuse `encode_row`, which is not order-preserving, so ~20 decodes per probe). **The base is a HINT, not the truth**: it describes rows as of the last checkpoint, so instead of tombstones every candidate is *verified* against the live **physical** row (a deleted row is gone from the store; an updated row no longer matches the key) — one comparison on a row the caller was fetching anyway, and a stale base becomes self-correcting rather than wrong. Writes since the checkpoint go to `map` as an overlay; a checkpoint rewrites the `.sidx` and drops the overlay. **Indexes must be registered BEFORE the WAL replay at open** — registering after left the base current only to the checkpoint and the overlay empty, so every row written since was invisible to an indexed lookup (`disk_index_tests::rows_in_the_replayed_wal_tail_are_found`). Result: **318 MB resident → 41 MB on disk, and exercising every index no longer moves memory at all** (311 → 163 MB, flat like PostgreSQL); (h) **the PRIMARY KEY is disk-backed the same way** (`$pk.sidx` — `$` is illegal in an identifier so it cannot collide with a user index): the open path stops seeding `pk_map` per row when the file exists, `pk_owner_of` consults overlay-then-base and **verifies every hit against the live physical row** (a deleted row's key is reusable, a re-keyed row frees its old key — both pinned, because a stale hit here would be a phantom duplicate-key error and a missed hit a corrupt table), and `rebuild_meta` drops the base after an `ALTER` shifts positions. **163 → 58 MB**; (i) **column-level `UNIQUE` too** (`$uq<pos>.sidx` — keyed by physical *position*, not name, so a `RENAME COLUMN` cannot point at a stale file): NULLs are exempt under SQL so they are never written (a written NULL would make the second one a duplicate — pinned), same overlay/base/verify shape. **58 → 36 MB.** **The design came from the PostgreSQL source**, not from tuning: buffers are page-granular with a partitioned hash + clock sweep (`storage/buffer/README`), `_bt_check_unique` descends the on-disk tree and binary-searches a *locked leaf page* rather than any key map (`nbtree/nbtinsert.c`), and an index entry is an 8-byte `IndexTupleData` header + MAXALIGN'd key + 4-byte line pointer ≈ **20 bytes on disk** (`access/itup.h`). Disk-first mode now holds **no per-row structure in memory at all** — rows, secondary indexes and primary keys are all mapped files, and what stays resident is bounded by the checkpoint interval rather than by row count. **No key set of any kind is resident**; what is left is the `.rdat` row-offset index, the catalog and the post-checkpoint overlays. Resident mode is unchanged by design.

**Doküman motoru belleği (AYRI mekanizma — `OXIDB_DISK_FIRST`, default AÇIK; SQL'inki `OXIDB_SQL_DISK_FIRST`, 0.41.33'ten beri O DA AÇIK; farklı depolama, farklı kod).** OxiBase dokümanları/storage/realtime'ı bu motordan servis ettiği için ayrıca ölçüldü: 1M doküman → boş 8 MB, yükleme sonrası 84 MB, **restart sonrası 52 MB**, tam tarama+filtre sonrası **92 MB**, diskte 141 MB. **Zaten SINIRLI** — 5 kat veri 1.7 kat bellek: her iki doküman cache'i de koleksiyonla ölçeklenen entry sayısıyla değil **sabit 128 MiB bütçeyle** boyutlanıyor (`doc_cache.rs`, `doc_bytes_cache.rs`), yani tarama onları doldurur ve DURUR — PostgreSQL'in `shared_buffers`'ıyla aynı şekil. Veriyle ölçeklenmeye devam eden: doküman başına offset index (SQL'deki `.rdat` satır-offset index'inin karşılığı).

**Chunked document scans — a scan no longer materializes one entry per document (`btree_storage.rs` `scan_chunked_while`).** The document key index is an `scc::HashMap`, so producing key order costs a pass over it; `scan_all_while`/`scan_bytes_while` paid that once and kept the **whole** key set (a `(u64, DocLocation)` per document — 24 B — plus a full sort) even when the callback stopped at the first match. That is the per-scan cost of every unindexed `find`, `count` and `aggregate`, not just a purge. `scan_all_chunked_while`/`scan_bytes_chunked_while` walk in **windows** instead: each window is one pass over the index keeping the smallest `limit` keys past the previous window's last (bounded max-heap, so the common case per key is one compare against its maximum). The window starts at 4096 — an early-stopping scan pays exactly that — and grows 8x to a cap of `count / 4`, so the pass count stays bounded as the collection grows. **A fixed byte budget was rejected**: it bounds memory but makes the passes grow with the collection, trading a bounded slowdown for an unbounded one (on 100M documents, 4 passes vs ~800). Measured in one session on 500k and 2M documents (`examples/scan_chunk_bench.rs`, counting allocator so this is live bytes, not allocator retention): **peak live 24 B/doc → 2 B/doc (12.6x), full walk 0.94-0.97x, stop-at-first-document 5-7x faster**; a divisor of 16 bought 0.5 B/doc but cost 0.77-0.80x, which is why it is 4. The full-walk cost is the extra index passes and shrinks as the callback does real work (with a per-document decode, what every real read path does: 0.96-0.99x). **Visibility, versus the un-chunked scans:** those fix the key set at `t₀`; this one re-reads the index per window, so a document inserted mid-scan *above* the current position is now seen — the phantom `docs/isolation.md` already admits for non-transactional readers, and the two consumers with a stronger guarantee do not take it from the scan (`snapshot_docs` resolves every id through the snapshot gate — a post-snapshot insert is `Prior(None)` and dropped, a mid-scan delete is recovered from `remembered_ids`, neither sourced from the scan; `aggregate` validates `changed_since` **after** the run and re-runs the slow path if anything wrote at all). Wired into the read paths only (`for_each_doc_arc_while`, the `Query::All` find fast path, `find_oxiwire_postfilter`); **index builds keep the un-chunked scans** — they now run under `index_build_barrier` (see below), so nothing can write while they scan and there is no window for a chunked walk to widen or narrow. Pinned by `chunked scan` unit tests in `btree_storage.rs`: differential against the un-chunked scan on both backends over a fixture larger than one window with **gapped keys** (contiguous ids hide a boundary off-by-one — a window resuming one key early or late still lands on a real key), early stop, mid-scan delete, and a window-size assertion that a collect-everything implementation fails while the differential tests stay green.

**Building a document index concurrently with writes corrupted it — fixed 0.42.13 (`btree_collection.rs` `index_build_barrier`).** Each builder scanned the collection, built the index in a local, and only then registered it under `field_indexes.write()` (composite/text/geo/vector: their own maps). A writer in that window took the same lock, found no such index, and maintained nothing — the index was published missing everything written since the build started. `create_index` is the worst of them: it opens with `values_as_slices()`, a snapshot of the whole collection, so **every** concurrent write is missed, not just those past the scan cursor. Reachable straight off the wire (`handler.rs` `create_index` → `OxiDb::create_index` → `Arc<BTreeCollection>`; there is no per-collection lock at the engine level and connections are thread-per-connection), and off REST (`POST /api/{col}/text_index`). `create_ttl_index` calls `create_index`, so a missed document is also never expired. **Measured, not argued** (`tests/index_build_race.rs`, 200k-document collection, release): 36 of 43 documents inserted during a build are unreachable by equality queries afterwards **and still unreachable after a restart** — disk-first persists the built `.mfidx` and opens it verbatim (only a crash-recovery `needs_reindex` rebuilds it), so the corruption is durable; in-RAM collections rebuild from a scan at open and self-heal. Re-issuing `create_index` does **not** repair it — the builders return `Ok(())` when the field is already in the map, so only `drop_index` + rebuild does. 46 of 56 documents *updated* during a build are worse than missing: the index holds the value the scan saw, a single-field equality is "fully indexed" so `is_fully_indexed` skips the post-filter, and the engine **returns a document the caller can see does not match** — a wrong answer, not an absent one. A UNIQUE index accepted 41 duplicate values written during its own build. **Deletes were already safe** and a passing test says so: the stale entry resolves to a document that is gone and every read path loads before returning, so stale entries self-correct — missing ones never do. **The first fix drained writers for the build** (`apply_barrier.write()` across scan-to-registration in all six builders — MongoDB's foreground build, 177 ms @ 200k / 916 ms @ 1M of writer stall). That barrier works for one specific reason: every write path holds `apply_barrier.read()` across its storage mutation **and** its index update (`insert`/`insert_many`/`insert_many_prepared`/`update_upsert_filtered_docs`/`find_and_modify`/`delete_docs`, and the transaction path via `in_flight_guard`; the two TTL evictors skip the barrier but hold `field_indexes.write()` across mutation+index-update — audited path by path). **Reads never take this lock and are unaffected.** **`create_index` (non-unique) is now the Postgres-`CONCURRENTLY` shape instead** — writers stall per *chunk*, not per build: (1) an empty staging index is registered in `field_indexes` under key `\0building:<field>` — `\0` is refused in real index field names, and **that mangled key is the entire reader-side gate**: every query path reaches field indexes *by name* (`fi.get`/`contains_key`; `query.rs` never iterates the map), so no query can see the partial index, while writers maintain indexes *by iterating* (`values_mut`), so every writer path maintains the staging index with zero new code in any of them (this also makes delete's `has_any_index` true during a build, which is required — writers must carry values to maintain it); (2) the work list is the id set snapshotted once unlocked (8 B/doc, vs the whole collection's bytes `values_as_slices` materialized — **a first version paginated with `keys_after` inside the exclusive section: an O(n) pass per chunk, measured as the whole stall, 140 ms @ 1M**); (3) backfill in 4096-doc chunks, each under `apply_barrier.write()` + `fi.write()` — fetch+decode+insert stay under one hold because reading a doc and indexing it must be atomic against a concurrent update of that doc, or the stale-entry direction returns; (4) publish moves it to the real key. One sweep converges: ids are monotonic, so inserts post-registration are writer-indexed; updates/deletes behind the cursor are writer-fixed, ahead of it backfill reads current state. **The caller still blocks to completion** (as in Postgres — CONCURRENTLY is non-blocking for *other* writers, not async for its caller), so "create returned ⇒ index serves queries" holds. `PagedFieldIndex.building` gates the paths that iterate *without* keying: `list_indexes` (which is what `save_index_metadata` serializes — so a crash mid-build reopens with no index rather than a partial one; "listed" and "complete" are the same event), the in-RAM `.fidx` save (loaded wholesale by field name on reopen — an unfiltered save is exactly how a crashed partial build would resurrect), and the disk persist tick. `index_build_serial` (Mutex) serializes builds per collection; `create_unique_index` takes it too — its `contains_key` check cannot see a same-field staging key. **UNIQUE builds stay blocking on purpose**: uniqueness cannot be enforced against an incomplete index, so a concurrent unique build could admit a duplicate it only discovers at publish. **Measured** (`examples/index_build_stall.rs`): worst concurrent-writer stall 916 ms → **~25 ms** (one chunk) at 1M docs, plus one publish-time spike proportional to the finished index's disk flush under `fi.write()` (~125 ms @ 1M, disk-first only) — the remaining honest cost. Pinned by `tests/index_build_race.rs` (6, release-only): the four concurrency tests (vacuity-asserted writers, originally proven red against the unfixed code), a mid-build query that must see every document at every moment (red when the staging index is registered under its real name), and a mid-build metadata save — forced via `drop_index` of another index, which doesn't serialize against builds — whose file must not name the building index (red when `list_indexes` stops skipping `building`; an earlier version of this test asserted "not listed until the thread exits", which is false — listing legitimately begins at publish, before the builder's persist/metadata afterwork).

**Instant (metadata-only) `ALTER TABLE ADD/DROP COLUMN` (`rows.rs`, ADR-0013 Phase D).** Both are **O(1)** — no row rewrite, no checkpoint — answering the "add/drop a column on a 500M-row live table with zero downtime" problem. The catalog stores the **physical** schema; `table_def` returns a **logical** view so the executor (whose scope is positional, `cols[i]↔cells[i]`) is untouched and never sees a dropped column. ADD appends a slot (old rows read back padded with the new column's default); DROP tombstones a column in place via a `Column.dropped` flag (Postgres `attisdropped`-style — the physical cell stays, projected out on read). `RowStore` projects physical→logical on read and exposes raw physical rows for index/snapshot work; writes expand logical→physical (`TableState::prepare_write`/`to_physical`, dropped slots = NULL placeholder); transactions read logical but log physical, translating a shifted UNIQUE position via `table_layout`. Durability rides on the WAL record alone (checkpoint skipped). A later checkpoint **compacts**: `RowStore::compact()` rewrites rows to the live columns and the tombstones are dropped from the catalog, reclaiming the space — the deferred O(n) rewrite folded into a checkpoint that rewrites every row anyway. `RENAME COLUMN` still rewrites/checkpoints eagerly. **`ALTER COLUMN <c> TYPE <ty>`** (PG `[SET DATA] TYPE`, MySQL `MODIFY COLUMN`) casts existing cells eagerly via the executor's CAST semantics (`RowStore::rewrite_slot`): a dry-run over all rows first — any uncastable value or over-length `VARCHAR(n)` aborts before the WAL append — then WAL + in-place rewrite + index rebuild + eager checkpoint; narrow (pre-ADD) rows are covered by casting the column default the fill template regenerates from. PRIMARY KEY / AUTO_INCREMENT / UNIQUE / FK-bound columns are rejected (a cast can collide previously-distinct key values).

**Streaming DML — a bulk `DELETE` no longer materializes the table (`executor.rs` `collect_dml_matches`).** `dml_candidates` reached an index only for `column = constant` conjuncts, so every other predicate — a range, an `IN`, an `OR` — fell through to `store.scan()`, which returns an owned `Vec<(u64, Vec<Value>)>` of **every row in the table**. On a table larger than memory that is not slow, it is fatal, and it happened **twice per statement** (`lock_matching_rows` scanned to take row locks, then the statement scanned again to find the same rows). Deleting 200M rows from a 1B-row table was not expressible at any batch size. Three changes:
- **`scan_visit_ids` / `index_visit_eq_ids` / `index_visit_range_ids`** (`store.rs`) stream `(row_id, cells)` **borrowed under the store's lock**, so the visitor MUST NOT re-enter the store — the executor only streams predicates `calls_store` proves free of subqueries and correlation (`Subquery`/`InSubquery`/`CorrScalar`/`CorrIn`); anything else keeps the materializing path, unchanged and correct. Deliberately **not** gated on `has_volatile`: `NOW()` is evaluated per row on the old path too, so it is no reason to refuse streaming — only re-entrancy is. `Transaction` inherits the materializing defaults on purpose: it buffers every write in RAM anyway, so streaming its reads would not save the OOM it is bounded by.
- **`DELETE ... LIMIT n`** (MySQL syntax; the parser already produced it, `ast.rs`+`parser.rs`). The visitor stops at the nth match, so a batch costs the rows it walked, not the table — this is what makes a purge loop possible. `ORDER BY` is **refused by name** rather than ignored: accepting it would promise a deletion order the executor does not implement, and with LIMIT that silently changes *which* rows go. Clause order is the parser's: `WHERE … RETURNING … LIMIT`.
- **Range predicates reach an index** (`index_visit_range_ids` → `SecondaryIndex::candidates_range` → `MappedIndex::range_first_col`). The `.sidx` is sorted **by decoded key tuple**, so `lower_bound` is a real lower bound and the walk stops at the first key past the high bound; the overlay `BTreeMap` is seeked the same way. Only the index's **first** column is bounded — a range on a later column of a composite index does not select a contiguous run, so serving it would mean walking the whole index, no better than the scan it replaces. Bounds on a second column keep the first and let the per-row recheck do the rest. As everywhere else here the base is a **hint**: every candidate is re-verified against the live row, so a row that moved out of range since the checkpoint is not deleted and one that moved in is.
**A DML statement holds a row lock on every row it writes, and `LIMIT` is why that had to be made true by construction.** Finding the rows happens twice — `lock_matching_rows`, then the statement's own match pass — and `LIMIT n` takes the *first* n matches in row-id order, so a row that starts matching in between (a concurrent committed UPDATE on a **lower** id) does not merely join the set, it pushes a locked row out of it. The first version returned from the locking fixpoint as soon as it held n rows, one pass, and the statement then wrote a row nobody had locked — defeating the writer-writer exclusion that loop exists to provide, with a third transaction's `SELECT … FOR UPDATE` as the victim. Two changes: the fixpoint **no longer short-circuits on LIMIT** (it converges like the un-limited case, costing one extra pass and over-locking a few rows the statement may not use — over-locking only delays other writers, under-locking loses their writes), and `lock_stragglers` locks anything in the final match set that the fixpoint missed, **before any write**, so a conflict is a clean lock error rather than a half-applied statement; that also closes the same gap on the un-limited path, where it predates LIMIT. **The gap is microseconds wide and needs three parties, so it is not reachable by racing threads** — `dml_lock_tests` (lib.rs) reaches it exactly, with a `Store` that delegates every call to a real engine and commits a chosen statement at the start of the Nth table scan, making the interleaving a parameter instead of a coin flip. Each test pins one fix: on the original code both are red (`deleted row 2 was never locked (locked: [3, 4], deleted: [2, 3])`), with only the fixpoint fix the second is still red, and the second asserts the scan it fires on really is the match pass so a change to the lock protocol breaks it loudly instead of firing somewhere harmless. Cells are kept only when something needs them (`RETURNING`, `UPDATE`'s assignments, an FK parent's cascade closure); otherwise a match costs 8 bytes, not a row. `SqlEngine::dml_rows_examined()` reports what the last DML statement walked — written once per statement, not per row — because "the index served this" and "this read the table" are otherwise indistinguishable from outside. **The masked-decode trap this shipped with, caught by sabotage:** the scan decodes only the predicate's columns, and the first version built that mask from `Expr::Col(i)` alone while a DML filter still carries `Expr::Column{name}` — so the mask came out **empty**, every cell read as `Value::Null`, and the statement silently matched **nothing**. It passed 16/16 tests, because rows still in the post-checkpoint overlay are handed over whole and ignore the mask: the bug is invisible until a checkpoint folds them to disk. `filter_col_mask` is now fail-safe (any node it cannot map ⇒ no mask ⇒ decode everything) and `a_streamed_scan_after_a_checkpoint_reads_the_columns_its_predicate_needs` pins it. `tests/t_streaming_dml.rs` (17), each fast path also checked against the same query in a shape that cannot use it.

**Still missing for a very large purge** (measured against the 1B-row case, not inferred): no `TRUNCATE`, no partitions, no `RENAME TABLE`, and no `INSERT … SELECT` — so rebuild-and-swap is not expressible inside the engine, and a recurring retention purge still wants time-sharded tables plus `DROP TABLE`. A checkpoint also still rewrites the whole changed table (hard-link reuse spares only untouched ones), so a long purge wants `OXIDB_SQL_CHECKPOINT_BYTES` raised and `OXIDB_SQL_REPLAY_FOLD_OPS` lowered — the tombstones live in the RAM overlay until a checkpoint folds them.

### Third engine — TSDB (`oxidb-tsdb/`)
A standalone time-series engine (InfluxDB-style), mounted like SQL. Off by default. Storage differentiator: each series (measurement × tag-set × field) is a **Gorilla-compressed** columnar stream (delta-of-delta timestamps + XOR floats; ~0.3 bytes/point on regular data), partitioned into sealed blocks so retention drops whole expired blocks.
- `OXIDB_TSDB` (`1`/`true`/`yes`/`on` to enable; default off — zero cost when unused). Per-database, like SQL.
- `OXIDB_TSDB_DATA` (default `${OXIDB_DATA}/tsdb` for the default db; named dbs at `${OXIDB_DATA}/<name>/tsdb`).

Persistence (`persist.rs`): a **versioned block snapshot + per-generation WAL**, with a `MANIFEST` as the atomic commit point (`blocks.<N>.tsb`, `wal.<N>.log`, `MANIFEST`). Every point is WAL-appended; a checkpoint seals active buffers, writes a fresh `blocks.<N+1>.tsb` snapshot (+fsync), atomically replaces the MANIFEST (temp+rename), then rotates the WAL. Recovery reads the MANIFEST's generation → snapshot + its WAL, so a crash on either side of the rename never double-counts; retention is durable (dropped blocks just aren't in the next snapshot). Auto-checkpoint past 8 MiB of WAL.

Fields are typed (float/**integer**/**boolean**/**string**); numeric values are stored as `f64` (ints exact to 2^53, bools 0/1), text in a separate `(ts, string)` path; the type is remembered per series and reported in query results. Numeric aggregations: mean/sum/min/max/count/first/last/**distinct** plus **`rate`** (per-second change, for counters) and **`percentile`** (`agg:"percentile"`+`p`, or shorthand `p95`; linear interpolation). Text-field aggregations: first/last/count/distinct.

**Continuous-aggregate rollups**: `add_rollup(measurement, interval, aggs)` materializes completed time buckets of every numeric series of a measurement into a derived measurement `<m>@<label>` with fields `<field>_<agg>` (e.g. `cpu@1m` `usage_mean`). Incremental via a persisted per-series watermark (crash-safe, no double-count on restart); the rule set persists in `rollups.json`. `refresh_rollups(now)` processes only fully-closed buckets. Roll from raw (1s→1m, 1s→1h); chaining is a caller concern.

Wire routing (`tsdb_bridge.rs`): `engine: "tsdb"` (or reserved `tsdb` command), `cmd: "tsdb"` with an `op`: `write` (points: measurement/tags/fields/ts — JSON bool→boolean, integer→integer, else float), **`write_lp`** (InfluxDB line protocol in an `lp` string; ms timestamps, `now()` when absent — `line_protocol.rs`), `query` (measurement + field + tag filters + `[start,end)` + optional `GROUP BY time(interval)` downsample + `group_by` tags + `agg`), `stats`, `retention` (cutoff), `checkpoint`, `rollup_add`/`rollup_refresh`/`rollups`. RBAC gates `tsdb` at `ReadWrite`; Read role is query-only. Node-local.

### Fourth engine — recommendations (`oxidb-rec/`, ADR-0025)
A standalone co-occurrence recommendation engine ("customers who bought this also bought"), mounted like SQL/TSDB: own files, own WAL, `engine: "rec"` / reserved `cmd: "rec"` routing (`rec_bridge.rs`), off by default (`OXIDB_REC=1`), per-database (`${OXIDB_DATA}/rec`, named dbs `${OXIDB_DATA}/<name>/rec`; `OXIDB_REC_DATA` overrides the default db). The work is an *index, not a query*: baskets ingest as pair-count increments independent of catalogue size; `related` is one sparse row lookup; scoring (LLR default — Dunning's G²; cosine/jaccard/lift/count as parameters, never a rebuild) is computed at query time from decayed counts. **Time**: 8 fixed buckets of `OXIDB_REC_BUCKET_SECS` (default 30d); the roll is **lazy** — each `Row` carries its slot-0 period and rotates O(8) on next touch, no global sweep exists (an eager sweep would have been a monthly multi-second stall, the foreground-index-build shape); checkpoint GCs fully-expired rows. **Idempotence**: `track` dedups per basket id against a seen-set **bucketed like the counters** — idempotence window = counting window, set bounded by one window (the unbounded alternative would have been this engine's own resident-index mistake). Ingest guards: basket-size cap (`OXIDB_REC_MAX_BASKET`, default 50, skipped-and-counted), intra-basket dedup, saturating u32 counters surfaced in `stats`. **Cold start returns empty** — no evidence is not a recommendation. Ops: `track` (idempotent), `related`, `for_basket` (cart page: summed scores, basket+exclude never appear), `stats`, `checkpoint`; RBAC Read tier gets the queries, writes need ReadWrite. **Persistence** (ADR §6): `MANIFEST` + `snap.<N>.rec` + `wal.<N>.log`, MANIFEST rename = the commit point, recovery = snapshot + WAL replay *through the ingest path* (replay IS ingestion; a doubled-on-disk WAL replays to the same state — tested at the file level), torn tail skipped, orphaned generations swept at open, `bucket_secs` guarded in the snapshot (a different width would re-interpret every period — refused by name), auto-checkpoint (`OXIDB_REC_CHECKPOINT_BYTES`, default 8 MiB). WAL flushes to the OS per record, no per-record fsync — stated v1 trade. **Not replicated in v1** (ADR §8, the gap TSDB already has; the fix is cheap later: idempotent track + commutative counters). Deterministic tie-break by item id. Tests: 27 crate (scoring math incl. "LLR shrugs at a single coincidence where cosine gives it a medal", lazy expiry, adversarial persistence) + 5 wire (`tests/rec_wire.rs`: routing, restart survival, off-by-default refusal naming the switch). Fixture lesson worth keeping: an item present in EVERY basket carries zero co-occurrence information — LLR scores it 0, correctly. **Phase 4**: COBRA procedures reach the other engines — `db.rec_*` and `db.vector_search` via the `NativeExt` hook (`oxidb_sql::NativeExt`, installed per engine by `native_ext.rs`; rec dispatch reuses `rec_bridge::native_call`, the same function the wire uses; the doc engine arrives through a startup-installed resolver). One dict argument mirroring the wire request; data-only boundary. En route: the Cobra CLI moved to portable format v2 (v1 + exported-names section) and the Rust VM refused every fresh `.cobrac` — it now reads v1..v2 and names the range when refusing v3+. **Phase 5**: validated on UCI Online Retail (541k real order lines, `examples/scoring_validation.rs`): count-vs-LLR overlap down to 2/10 on a rare probe (count's top = the global bestseller at co=2 — the §4 trap observed), cosine converges with LLR on head probes (9-10/10) and diverges exactly on small-margin probes (three-way 0.41 tie of one-off pairings vs LLR ranking the probe's sister product first). LLR default validated; ADR-0025 Accepted.

### MCP server (`oxidb-mcp/`, ADR-0024)
A standalone **Model Context Protocol** stdio binary on `oxidb-client` (no engine deps, no server changes) so AI hosts (Claude Code/Desktop, Cursor, …) can drive OxiDB directly. Hand-rolled JSON-RPC subset (`initialize` with version negotiation, `ping`, `tools/list`, `tools/call`; everything else `-32601` by name; newline-delimited framing; pre-2025-06-18 batches supported). Read tools across all three engines: `list_databases`/`list_collections` (+counts, skipped past 100 collections — stated)/`list_tables`/`describe_table`/`list_indexes` (doc **or** SQL), `find`/`count`/`aggregate`/`explain`, `sql_query` (advisory read-only gate: single statement, quote-aware `;` scan, leading-keyword allowlist — the real gate is the account's RBAC role), `tsdb_query`, `text_search`. Write tools (`insert`/`update`/`delete`/`sql_execute`) are **not registered** without `OXIDB_MCP_WRITES=1` (unregistered = `-32602`, protocol error); `delete` refuses an empty filter. Results are context-budgeted: `find` defaults to 50 rows, caps at 500, and a full page triggers an index-only `count` so truncation reports the true total (never a silent cap); `aggregate` truncates past 500 and says so. Env: `OXIDB_ADDR`/`OXIDB_USER`/`OXIDB_PASSWORD`, `OXIDB_MCP_DB` (pins every call to one database; conflicting `db` arg refused), `OXIDB_MCP_WRITES`. `--version`/`--help` answer and exit (without them the stdin loop looks like a hang — the check a downloader runs first).

**Phase 2 — hosted HTTP transport (0.42.8, `http.rs` + `rest_wire.rs`).** `OXIDB_MCP_HTTP_PORT` serves `POST /mcp/<project-ref>` with the project key as a bearer token (`OXIDB_MCP_UPSTREAM` = the REST listener, default `http://127.0.0.1:8080`; `OXIDB_MCP_DB` fixes the project and then **ignores the path ref**; `GET /mcp/health` needs no key). **It backs onto the REST surface, not OxiWire, on purpose**: REST is what verifies per-project JWTs, applies row-level rules and enforces the per-project rate limit, so forwarding the caller's key inherits all three instead of re-implementing them with a copy of the seal key. Every request builds its own `RestWire` from (path ref, header key) — no session state, so one tenant's key can never be applied to another's database. The `Wire` trait added for testability turned out to be the seam for the second transport: tool logic, truncation accounting and write gating are identical on both. `explain` is refused by name (a wire diagnostic with no REST equivalent). Tests: `tests/http_e2e.py` (19 checks) + `tests/rules_e2e.py` (8, proves a rule actually refuses the tool call).

**Two read-path holes this found (0.42.8, both shipped-code bugs, both red-first pinned):** (a) **`GET /api/{col}/count` never consulted the read rule** — `read:false` refused `find` with 403 but answered `count`, and since count takes an arbitrary `?q=` it was an **arbitrary-predicate disclosure oracle** (`count?q={"email":"…"}` = existence check; `$gte` binary-searches a number), all without ever seeing a document. Same class as the 0.39.21 `aggregate` gap, missed in that pass; now `handle_count_with_rules` refuses `None` and *filters* `Filter` (a count over the visible subset is exact, so refusing would be gratuitous). (b) **`rules::values_equal` compared JSON representations** — a rule literal parses as `f64` (`Number(1.0)`), a stored int is `Number(1)`, and `serde_json::Value` equality calls them different, so **every numeric rule comparison was wrong in both directions**: `read: "doc.hidden != 1"` published the drafts it meant to hide (fail-OPEN), `read: "doc.hidden == 0"` hid everything. Numbers now compare via `as_f64`; a missing field stays null (absent ≠ 0). Neither was findable by reading the MCP code — both came from asking "does a rule actually stop this?" and running it. Identifiers spliced into SQL are validated (`^[A-Za-z_]\w*$`); values always bind via `params`. Recommended setup: a **Read-role account**, so read-only is server-enforced. Tests: 22 unit (fake wire) + 4 stdio integration (spawned binary, offline — connections dial lazily) + `tests/live_e2e.py` (opt-in, 26 checks against a real server). Wire errors return as `isError: true` tool results the model can read and correct.
